# CNPA Web 邀请成员 · 历史邀请弹窗优化报告

## 1. 当前问题

邀请成员页在上一轮已改为候选列表全宽 + 确认弹窗，但「已发送邀请」仍**常驻在候选列表下方**，占用纵向空间。队长主要操作是搜索 → 邀请 → 确认，历史邀请属于低频查看场景，不应与候选列表同屏常驻。

## 2. 调整后的交互

| 场景 | 交互 |
|------|------|
| 页面主体 | 仅「邀请候选球员」全宽卡片 |
| 历史记录 | 标题右侧 **「历史邀请」** 按钮 → 打开弹窗 |
| 发送邀请 | 行内「邀请」→ 确认弹窗 → 确认邀请 |
| 发送成功 | 刷新候选列表；若历史弹窗已打开，同步刷新历史列表并回到第 1 页 |

## 3. 是否移除右侧「当前邀请」卡片

**是（延续上一轮）。** 本轮无该卡片。

## 4. 是否移除页面常驻「已发送邀请」列表

**是。** 已删除页面内「已发送邀请」`AccountPanel`，改为弹窗查看。

## 5. 候选球员列表布局

- 单卡片全宽展示
- 标题行右侧：`历史邀请` 按钮（`AccountPanel` `#extra` 插槽）
- 搜索区 + 表格 + 分页（每页 5 条）
- 操作列「邀请」按钮居中，不可邀请时置灰 + `title` 提示原因

## 6. 邀请确认弹窗

- 标题：**确认邀请球员**
- 展示：昵称、CNPA 球员编号、认证状态、当前球队、常用位置、平台游戏 ID、**当前是否可邀请**、**不可邀请原因**（如有）
- 邀请说明 textarea → `invitationMessage`
- 按钮：取消 / 确认邀请
- 失败时弹窗不关闭，展示 `inviteModalError`

## 7. 历史邀请弹窗

- 标题：**历史邀请**
- 宽度：`min(880px, 100%)`，窄屏自适应
- 结构：搜索区 → 状态筛选 → 表格 → 分页 → 关闭按钮
- 空状态：**暂无邀请记录**

## 8. 历史邀请搜索和筛选

### 搜索

- 关键词：球员昵称 / 邀请编号 / 邀请说明
- 点击搜索或 Enter 后 **pageNum 回到 1**

### 状态筛选

| UI 标签 | 后端 status |
|---------|-------------|
| 全部 | 不传 |
| 待响应 | 0 |
| 已接受 | 1 |
| 已拒绝 | 2 |
| 已失效 | 3（后端文案：已过期） |
| 已撤回 | 4（后端文案：已取消） |

筛选后 **pageNum 回到 1**。

### 搜索实现说明

- **无关键词**：走后端分页 + 状态筛选
- **有关键词**：按状态拉取全部页（每页 100 条上限），前端过滤后再 **客户端分页**（每页 5 条）

> 关键词搜索未改后端接口；邀请总量超过 100×N 页时，搜索范围为已拉取的全部记录。

## 9. 历史邀请分页

```ts
historyInvitePage = { pageNum: 1, pageSize: 5, total: 0 }
```

- 与候选列表分页 **互不影响**
- 弹窗关闭时 **重置** 搜索/筛选/分页
- 发送邀请成功后：若弹窗打开，历史列表刷新并回到第 1 页
- 末页无数据时自动回退上一页（无关键词时的后端分页模式）

## 10. 是否使用后端分页

| 场景 | 方式 |
|------|------|
| 历史邀请 · 无关键词 | **后端分页**（`GET .../invitation/page`，`currentPage` + `pageSize=5` + `status`） |
| 历史邀请 · 有关键词 | **前端分页**（全量拉取后 filter + slice） |
| 候选球员 | **后端内存分页**（沿用原逻辑，每页 5 条） |

## 11. 是否改动接口

**否。** 复用：

- `GET /basket/team/{teamId}/invitation/page`（`currentPage`、`pageSize`、`status`）
- `POST /basket/team/{teamId}/invitation`（`invitationMessage`）

未新增 `keyword` 参数。

## 12. 是否改动数据库

**否。**

3. **关键词搜索**在有关键词时为前端过滤 + 客户端分页；未改后端 `keyword` 参数。
4. 状态「已撤回」对应后端 `CANCELLED(4)` 文案为「已取消」，UI 筛选标签使用「已撤回」。
