# CNPA Web 邀请成员页交互优化报告

## 1. 当前问题

原「我的球队 → 邀请成员」页签采用左右分栏布局：

- **左侧**：邀请候选球员列表（搜索 + 表格 + 分页）
- **右侧**：「当前邀请」卡片 + 邀请说明 + 发送邀请按钮 + 「已发送邀请」列表

存在以下交互问题：

1. 右侧「当前邀请」占用较大空间，候选表格被挤压变窄。
2. 队长需先在左侧「选择」球员，再到右侧填写说明并发送，步骤冗余。
3. 「当前邀请」与「已发送邀请」堆叠在右侧，信息层次不清晰。
4. 操作流程不符合「点选即邀请」的自然预期。

## 2. 交互调整前后对比

| 维度 | 调整前 | 调整后 |
|------|--------|--------|
| 布局 | 左 65% 候选 + 右 35% 当前邀请/已发送 | 全宽纵向：候选列表 → 已发送列表 |
| 邀请流程 | 选择 → 右侧确认 → 发送邀请 | 点击「邀请」→ 弹窗确认 → 确认邀请 |
| 邀请说明 | 固定在右侧 textarea | 在确认弹窗内填写 |
| 当前邀请卡片 | 有 | **已移除** |
| 候选操作按钮 | 「选择 / 已选择」 | 「邀请」（不可邀请时置灰 + title 提示原因） |
| 已发送邀请 | 右侧卡片列表 | 候选列表下方全宽表格 + 分页 |

## 3. 是否移除了右侧「当前邀请」卡片

**是。** 已完全删除「当前邀请」面板及相关状态（`selectedInvitePlayerId`、`selectedInvitePlayer`、`inviteMessage`、右侧发送按钮）。

## 4. 候选球员列表布局调整

- 使用 `.team-invite-stack` 纵向全宽布局，取消 `.team-invite-layout` 左右 grid。
- 候选表格增加 `.team-table--invite`，操作列固定宽度（108px），「邀请」按钮使用主色样式。
- 不可邀请行增加 `.team-table__row--disabled` 半透明样式。
- 提示文案补充已选人数与规则区间（分页每页 5 条，由 `TEAM_TAB_PAGE_SIZE = 5` 控制）。

## 5. 邀请确认弹窗展示字段

弹窗标题：**确认邀请球员**

展示字段：

| 字段 | 数据来源 |
|------|----------|
| 球员昵称 | `nickname` / `gameNickname` |
| CNPA 球员编号 | `playerNo` |
| 认证状态 | `certificationStatusText` |
| 当前球队 | `currentTeamStatusText` |
| 常用位置 | `positionCode` + `positionName` |
| 平台游戏 ID | `platformAccountSummary` / `platformGameId` |
| 是否已加入其他球队 | 由 `currentTeamId` 推导（是/否） |
| 是否已存在邀请 | 候选列表已过滤待处理邀请，默认可邀请项为「否」 |

弹窗提示文案：

> 请确认球员信息无误后发送邀请。邀请发送后，球员将在消息通知中确认是否加入球队。

## 6. 邀请说明处理方式

- 弹窗内 textarea，占位：**可选，向球员说明邀请原因**
- 调用原有 `POST /basket/team/{teamId}/invitation` 接口
- 请求体字段 `invitationMessage`（已有支持），有内容则传递，空则不传
- **未改接口语义，未改后端**

## 7. 已发送邀请列表位置和分页

- 位置：候选球员卡片**下方**，间距约 20px（`.team-invite-stack { gap: 20px }`）
- 展示：全宽表格
- 分页：`sentInvitePage`，每页 **5** 条，独立分页器
- 空状态：**暂无邀请记录**
- 发送成功后：`sentInvitePage.pageNum = 1` 并刷新列表
- 末页撤回后回退：沿用原有 `loadSentInviteList` 逻辑（当前页无数据且 pageNum > 1 时自动回退上一页）

表格字段（按现有接口能力）：

| 列 | 说明 |
|----|------|
| 被邀请球员 | `inviteeNickname` |
| 球员编号 | 接口未返回球员编号，显示 `-`（遗留见第 13 节） |
| 平台游戏 ID | 接口未返回，显示 `-` |
| 邀请状态 | `invitationStatusText` |
| 发送时间 | `createTime` |

> 说明：原页面无「撤回邀请」操作，本轮未新增；接口亦未提供撤回能力。

## 8. 是否使用后端分页

| 列表 | 分页方式 |
|------|----------|
| 候选球员 | **后端内存分页**：`pageCandidatePlayers` 先查全量再 `subList`，传 `currentPage` / `pageSize=5` |
| 已发送邀请 | **后端数据库分页**：`pageTeamInvitations` 使用 MyBatis-Plus `selectPage` |

前端均传 `currentPage` + `pageSize: 5`，两个分页状态互不影响。

## 9. 是否改动接口

**否。** 仅复用：

- `GET /basket/team/{teamId}/candidate-player/page`
- `GET /basket/team/{teamId}/invitation/page`
- `POST /basket/team/{teamId}/invitation`

## 10. 是否改动数据库

**否。** 无 migration、无表结构变更。

## 14. 遗留问题

1. **已发送邀请列表**缺少球员编号、平台游戏 ID：当前 `TeamInvitationItemResp` 未返回这些字段，表格暂显示 `-`。若产品需要展示，需后端扩展响应（本轮按要求未改接口）。
2. **候选球员分页**为后端内存切片，球员量大时性能取决于全量查询；本轮未改数据库与接口。
3. **撤回邀请**功能仍不存在（与原页面一致）。
