# 22. 接口与页面总索引

> 本文件对应 `核心业务/核心实现.md` 的“接口与页面总索引”要求。内容来自 2026 年 7 月 31 日对 `basketball-web`、`basketball-admin`、`basketball-web-ui`、`basketball-admin-ui` 的静态盘点；未启动 Web/Admin 服务，未使用真实 Token、权限账号或浏览器 Network 面板联调。因此“真实接口”表示前端源码调用实际 HTTP API，不代表接口已验收通过。

## 1. 业务定位

本索引用于把核心业务模块、后端入口、前端页面和权限边界关联起来，便于联调、权限测试、接口回归和后续拆除遗留生成式 CRUD。

索引分为四个访问面：

1. **官网公开面**：首页、赛事、数据、球队、球员、公告、名人堂和合作伙伴；访客可访问，但只能读取已公开数据。
2. **官网会员面**：注册登录、资料、认证、平台账号、消息、球队、报名、阵容、比赛数据、争议和异常申请；默认要求会员登录。
3. **官网队长面**：建队、成员管理、邀请/申请处理、报名/阵容、赛事阵容与比赛数据提交；除登录外还必须由服务端校验当前有效队长授权及对象归属。
4. **后台管理面**：赛事赛季、赛程、比赛数据审核、统计结算、处罚、内容、权限范围与审计；要求后台登录和 `@PreAuthorize` 权限码，并应校验赛事范围。

本文件只列出篮球业务的**核心专用接口和核心页面**。旧的 `Basket*Controller` 生成式 CRUD 不作为推荐业务入口；第 17 项已记录其 `/basket/team/**` 白名单绕过风险，仍需单独封禁或下线。

## 2. 最终业务规则

1. Web 端核心接口必须按公开、会员、队长和当前用户归属划分，不得只用前端隐藏按钮代替后端校验。
2. Admin 端核心接口必须具备后台登录和权限码校验；涉及特定赛事的操作还应校验管理员赛事范围。
3. 公开 Controller 必须显式标记 `@NoLoginRequest`，并只返回公开赛事、公开赛季、已发布赛程、已确认赛果/统计和已发布内容。
4. 每个 Web UI、Admin UI 核心页面都应标注是否调用真实接口、是否仍有 Mock 或空壳入口。
5. 会员个人资料、认证、平台账号、消息和我的赛事等接口，必须从登录上下文取得当前会员，不允许客户端传任意会员 ID 越权读取。
6. 队长管理接口必须验证有效授权、授权绑定球队、赛事/赛季有效性和目标对象归属；普通成员、其他球队队长和过期队长不得调用成功。
7. 关键写接口应以专用业务 Controller / Service 为唯一入口；遗留 CRUD 不得绕过状态机、审计、快照、并发控制或权限校验。
8. 当前第三批范围优先完成 P0 联调和 M01–M05 页面可用性，不应把 M06 数据争议和 M07 弃赛异常写成已验收完成。

## 8. 权限规则

1. **公开 API：** `BasketPublic*Controller` 已标注 `@NoLoginRequest`，登录/队长/Admin 均不要求；但 Service 必须限制公开赛事、赛季、比赛、内容和统计。
2. **认证 API：** 注册、验证码、密码登录/重置等为显式豁免入口；会话、退出、账户资料、安全、消息和设置要求当前会员登录。
3. **会员私有 API：** 当前会员 ID 应从 `UserContext` / Token 取得，资料、文件、消息、认证、平台账号、我的赛事均不得按请求参数读取他人数据。
4. **队长 API：** 建队、队伍成员管理、邀请处理、入队申请处理、赛事报名、阵容保存和比赛数据提交要求当前用户具有运行时有效队长授权，并且授权、球队、报名、比赛和赛季归属一致。
5. **普通成员：** 可以提交/撤回自己的申请、响应自己的邀请、查看本人赛事/报名只读信息；不能处理别人申请、管理别队成员、保存队伍报名阵容或提交非本队比赛数据。
6. **Admin API：** 需后台登录，Controller 使用 `@PreAuthorize("@ss.hasPermi(...)")`。赛事、赛季、比赛、处罚、审核和内容操作还应核实管理员是否具有目标赛事的授权范围。
7. **遗留 CRUD：** `/basket/team/**` 的生成式 Controller 白名单过宽，是第 17 项的 P0 风险。已登录普通会员可能绕过专用 Service 的归属、队长、状态、审计和并发控制；其接口不可作为合法前端调用契约。

## 9. 并发与幂等

1. 本索引只记录入口，不把“前端防连点”当作并发控制。报名、邀请/申请处理、队长授权、赛程生成、Submission 提交/审核和统计结算的最终保障在后端唯一约束、状态条件更新、行锁、分布式锁和幂等记录。
2. Web 队长报名、队长处理申请、比赛数据提交和重提，应在 UI 请求中展示 loading 并在冲突后刷新状态；后端仍必须拒绝重复成功。
3. Admin 报名审核、比赛数据审核、赛程生成和结算操作应只允许一个状态转换或一个有效批次；UI 需要对“已被其他管理员处理/任务执行中”作明确提示。
4. 公开接口无写入幂等需求，但依赖上游发布/审核/统计同步的事务一致性。否则首页、赛果、统计和排行可能短暂读到不同步数据。
5. 争议、异常、处罚和荣誉生成涉及异步/多步骤流程，需在其专项联调中确认重复点击、任务重试和审计消息不会重复生效。

## 12. 已知问题和风险

1. **P0 — 遗留团队 CRUD 可绕过专用权限。** `GeneratedCrudAccessInterceptor` 对 `/basket/team/**` 的宽白名单，使生成式团队、成员、邀请和申请 Controller 可能直接可用；本索引已将它们排除出合法业务入口，但代码层风险仍在。
2. **P0 — Submission P0 数据库迁移状态未确认。** 前端 `matchData.ts` 和后台 `matchAudit.ts` 已形成接口面，但若 `cnpa-match-data-submission-p0-migration.sql` 未执行，提交/审核/同步链路不能视为可用。
3. **P0 — 公开数据过滤不一致。** 首页近期已结束比赛缺少 `dataStatus=CONFIRMED` 条件，公开比赛详情比分与明细统计过滤口径不同，可能泄露审核中数据。
4. **P1 — 公开查询参数未满足三维要求。** `eventId / seasonId / platformCode` 未形成统一公共 API 过滤规范，前端也缺少一致的查询上下文。
5. **P1 — 页面真实 API 不等于页面闭环完成。** 多数页面的源码已请求后端，但未验证菜单权限、状态按钮、空态、错误态、上传下载和真实数据库字段是否完全匹配。
6. **P1 — 赛事/阵容/球队语义复杂。** 长期球队、赛事球队、报名阵容和赛季阵容对应不同数据层；若前端或接口混用 ID，会造成历史数据污染或越权。
7. **P1 — M06/M07 范围管理。** 数据争议、比赛异常页面和接口已出现，但根据原始分批计划属于后续第四批；不得将“接口存在”写成“业务验收通过”。
8. **P2 — 缺少统一接口契约。** 当前路径、参数和响应模型分散在 Java Controller 与 TypeScript API 文件，容易出现改动后前后端不同步。
9. **P2 — Web 页面遗留占位。** `EventTeamManagementView.vue` 存在 `mockOnly` 导航分支；季后赛对阵图为无数据空态，均需产品确认和完整联调。
10. **P2 — Admin 接口权限细粒度较多。** `@PreAuthorize` 权限码虽完整，但菜单、角色、数据范围、赛事范围与操作审计是否保持一致尚未验证。

## 13. 下一步建议

### P0

1. 优先封禁或移除 `/basket/team/**` 遗留生成式 CRUD 白名单，确保前端只可通过本索引列出的专用团队业务接口写数据。
2. 执行并记录 Submission P0 migration，随后以“队长提交 -> 管理员审核 -> 正式结果 -> 统计/排行 -> 公开页面”的路径完成第一条端到端接口回归。
3. 统一公开比赛读取条件，修复首页和详情中审核中数据的泄露风险，并对全部 `BasketPublic*Controller` 增加同口径回归测试。
4. 建立六类账号（访客、普通成员、有效队长、失效队长、其他队队长、管理员）的权限矩阵自动化测试。

### P1

1. 统一公共查询上下文，补齐并验证 `eventId`、`seasonId`、`platformCode` 的关联筛选、默认值和公开范围校验。
2. 将 Web/Admin API 模块、Controller 路由和请求/响应 DTO 生成或维护为 OpenAPI 文档，作为发布前契约测试来源。
3. 完成 M01–M05 页面真实数据联调，尤其检查赛事/球队 ID、分页、筛选、加载失败、空态、文件上传和权限提示。
4. 对 Admin 赛事范围权限做服务层回归，不把 `@PreAuthorize` 和菜单可见性当作数据权限保障。

### P2

1. 清理或替换 `mockOnly` 导航与临时空态，并对暂未实现的季后赛对阵图提供明确产品文案和接口计划。
