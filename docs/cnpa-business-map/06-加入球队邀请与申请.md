# 加入球队邀请与申请

> 范围：队长邀请认证球员、普通认证球员申请加入公开球队、邀请响应、申请取消、队长处理申请、成员关系写入与通知。长期球队本体见 `05-长期球队与成员管理.md`；离队/踢人/转会期见 `07-退出球队踢人转会期.md`。

## 1. 业务定位

长期球队补充成员有两条正式入口：

1. **队长邀请**：队长从候选认证球员中发出邀请，被邀请人自行接受或拒绝。
2. **普通用户申请**：未加入有效长期球队的认证球员，对公开、已审核、正常且未满员的球队提交申请，由该球队队长通过或驳回。

两条路径最终都通过 `TeamMemberJoinHelper` 写入 `basket_team_member`，并维护当前成员槽位、当前球队和球队人数。邀请/申请是长期球队成员关系流程，不应直接代替单届赛事的补员、转会、阵容锁定审批。

## 2. 最终业务规则

1. 只有认证通过的球员才能被邀请、接受邀请或申请加入球队。
2. 一个球员任一时刻只能加入一支有效长期球队；已有有效球队关系的用户不能继续邀请加入或申请加入其他球队。
3. 只有已审核、正常、公开招募且未满员的长期球队可以接受外部申请。
4. 队长可以邀请认证球员，不能邀请自己、重复邀请同一待处理对象，也不能邀请已在有效球队中的球员。
5. 邀请需要被邀请人自行接受或拒绝；邀请过期后不能接受。
6. 普通用户可以取消自己仍处于待处理状态的加入申请；队长只能处理自己球队的待处理申请。
7. 通过邀请或申请前后都必须再次校验认证状态、成员唯一归属、球队状态、人数上限和赛事锁定/报名限制，不能只在创建流程校验。
8. 长期球队不按平台隔离。历史非 `GENERAL` 球队的终端匹配逻辑仅为兼容，不能把 PC/PS/XBOX 当作长期球队归属条件。
9. 阵容锁定后，邀请、申请和通过成员变更应按赛事规则限制；如果当前未完整实现，必须标为待测试/差异。
10. 邀请、申请、响应、处理、成员写入和通知均应可追溯。

## 7. 状态机

### 队长邀请

```text
PENDING(待响应)
  ├── 被邀请人接受 ──> ACCEPTED(已接受) ──> 写入 TEAM_MEMBER
  ├── 邀请人拒绝 ──> REJECTED(已拒绝)
  ├── 超过 expire_time ──> EXPIRED(已过期)
  └── 发送方取消（枚举存在，当前业务入口未确认）──> CANCELLED(已取消)
```

邀请接受使用条件更新：仅邀请 ID、被邀请会员、`PENDING`、未删除同时匹配时才可更新；更新失败返回“邀请状态已变更”。

### 加入申请

```text
PENDING(待处理)
  ├── 申请人取消 ──> CANCELLED(已取消)
  ├── 本队队长通过 ──> APPROVED(已通过) ──> 写入 TEAM_MEMBER
  └── 本队队长驳回 ──> REJECTED(已驳回)
```

通过邀请/申请后成员关系写为 `ACTIVE`，加入来源分别为 `INVITE`、`APPLY`；成员后续离队/移除状态为 `LEFT`、`REMOVED`，不属于本模块审批状态。

## 8. 权限规则

1. 创建邀请、查看本队邀请和处理本队申请均要求当前用户是该长期球队的有效队长，后端使用 `requireTeamCaptain` 校验。
2. 接受/拒绝邀请仅允许 `invitee_member_id` 本人；取消申请仅允许 `applicant_member_id` 本人；他人 ID 应返回无权操作。
3. 申请加入前必须通过球员认证、未被限制、未存在有效长期球队成员关系；队长也因已有球队关系不能加入其他球队。
4. 可被申请球队必须为 `ACTIVE + APPROVED + PUBLIC + 未满员`；邀请接受时也会复核球队可加入状态。
5. 申请通过和邀请接受均应在写成员前再次校验一人一队、认证状态和容量，防止页面打开后状态变化造成绕过。
6. 长期球队在当前最终模型下为 `GENERAL`，不应按平台限制申请/邀请；历史非 `GENERAL` 数据的终端/平台匹配仅是兼容分支。
7. 阵容锁定、转会期和进行中报名的限制不能只放在前端。当前邀请/申请 Service 未见统一赛事锁定校验，属于待补验证边界。

## 9. 并发与幂等

| 场景 | 当前机制 | 结论 |
|---|---|---|
| 同队同人重复邀请 | `assertNoPendingInvitation` 查询 `PENDING` | 有业务层防重；无 pending 唯一键，双请求需并发验证 |
| 同队同人重复申请 | `assertNoPendingApplication` 查询 `PENDING` | 有业务层防重；无 pending 唯一键，双请求需并发验证 |
| 同一邀请重复响应 | `UPDATE ... WHERE invitee_member_id AND status=PENDING` | 条件更新可阻止二次接受/拒绝 |
| 同一申请重复处理 | 申请状态校验和处理流程 | 需要验证条件更新是否在 Mapper 层完整使用，双队长/双击不应重复入队 |
| 接受邀请/通过申请并发 | `assertEligibleToJoinTeam` + `active_member_slot` 唯一键 | 数据库可防一人入多队；需要捕获唯一键冲突并返回业务提示 |
| 最后一个名额并发加入 | 读取 `current_member_count` 后写成员/重算 | 只有业务层容量校验时可能竞态，需加锁或条件更新验证 |
| 邀请过期与接受并发 | `expireIfNeeded` + 条件更新 | 过期时间临界点需测试，避免已过期邀请仍写成员 |
| 通知写入 | 业务消息服务 | 需确认通知失败是否影响主事务及是否允许重试 |

## 12. 已知问题和风险

1. **P0：待处理邀请/申请没有数据库级业务唯一键。** 当前只通过查询 `PENDING` 记录防重；并双击可能产生重复流程，需要实际并发测试或补充唯一槽位。
2. **P0：最后一个名额并发通过存在风险。** 邀请接受和申请通过都要先检查人数，若没有行锁/条件更新，两个请求可能同时认为仍有名额。
3. **P1：锁定阵容后的邀请/申请规则未统一下沉。** 当前 Service 主要检查认证、成员归属、球队状态和容量，未见统一赛事 roster lock 校验；这与最终规则有差异。
4. **P1：历史终端匹配兼容逻辑仍在邀请/申请流程中。** 对 `GENERAL` 团队会绕过，但必须防止未来数据或代码把长期球队重新按平台分割。
5. **P1：邀请 `CANCELLED` 状态没有对应发送方取消业务入口。** 若运营需要撤回邀请，应补充权限、状态机、通知和幂等规则；当前不能凭枚举认定功能已完成。
6. **P2：申请处理在 Web 队长端完成。** 当前无独立 Admin 入队审核页；若后续要求管理员复核，需要新增流程而非复用现有队长处理接口。

## 13. 下一步建议

### P0

1. 对同队同人待处理邀请/申请和最后名额并发通过建立数据库级或锁级兜底，并把唯一键异常转换为稳定业务提示。
2. 对邀请接受和申请通过补齐端到端用例：认证、唯一成员归属、容量、成员关系、当前球队、人数计数和通知必须同时正确。
3. 明确并测试锁定阵容后是否禁止发起/通过邀请和申请；不能让长期成员流程绕开已锁定赛事阵容。

### P1

1. 明确邀请取消是否需要实现；若需要，补充“仅发送方、仅待响应、写取消时间/原因、通知接收人”的业务规则。
2. 把历史 `game_terminal` 匹配逻辑限制在迁移兼容层，长期团队业务默认只使用 `GENERAL`。
3. 在 UI 中明确展示“认证未通过、已有球队、满员、私有/未审核、锁定中”等不可加入原因，并保持以后端返回为准。

### P2

1. 增加邀请/申请运营审计列表，支持按球队、申请人、状态、操作人和时间追溯。
2. 后续在 `07` 中统一处理直接离队、队长移除、转会期和赛事阵容变更的边界。
