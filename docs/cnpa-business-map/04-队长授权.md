# 队长授权

> 范围：管理员为认证球员授予、编辑、绑定球队、收回和自动失效赛事/赛季队长授权，以及 Web 端查询当前授权。队长创建球队、报名和管理操作见后续球队与报名文档。

## 1. 业务定位

队长授权是赛事级管理资格，不是永久身份，也不是会员注册后的默认角色。管理员确认线下缴费后，针对具体赛事赛季为已认证球员授予授权；授权可以先不绑定球队，待队长创建并通过审核的长期球队后再绑定。授权绑定球队后，队长只能在该赛事/赛季和该球队范围内执行管理、报名等动作。

当前实现的核心约束是：

1. 目标球员必须已经通过球员认证。
2. 必须选择授权赛季并确认缴费。
3. 同一会员同一赛季只能有一条有效授权。
4. 同一球队同一赛季只能有一条有效队长授权。
5. 赛事结束后，授权自动变为已过期；Web 端不能申请队长授权。

## 2. 最终业务规则

1. 队长授权由后台管理员手动授予，Web 端不提供申请队长入口。
2. 只有认证通过的正式球员才能被授予队长授权。
3. 授权必须绑定具体赛事/赛季；授权哪个赛季，只能管理和报名该赛季对应的赛事。
4. 授权有效期由赛季/赛事结束时间决定，不是永久有效；赛事结束后必须失效。
5. 新赛事需要重新完成线下缴费确认和后台授权，旧赛事授权不能自动迁移到新赛事。
6. 队长授权可以在建队前暂不绑定球队；绑定球队后，球队必须是该球员本人担任队长的有效球队。
7. 同一会员同一赛季不能重复拥有有效授权；同一球队同一赛季不能存在两个有效队长授权。
8. 队长才能创建、编辑和管理自己的球队、审核入队申请、代表球队报名赛事以及进行授权范围内的赛事操作。
9. 其他赛事、其他球队、授权过期、授权收回或球员被限制时，后端必须拒绝队长操作。
10. 授权授予、绑定球队、编辑、收回、过期都必须记录操作人、时间、前后状态、原因和通知。

## 7. 状态机

### 授权状态

`CaptainQualificationStatusEnum`：

```text
                ┌──────────────┐
                │   REVOKED    │
                └──────▲───────┘
                       │ 管理员收回
GRANT ──> ACTIVE ──────┤
  │       │            │
  │       └──赛事结束──> EXPIRED
  │
  └──可选绑定球队：NULL team_id -> team_id
```

实际状态值为：`REVOKED(0)`、`ACTIVE(1)`、`EXPIRED(2)`。

### 运行时有效性

即使数据库状态仍为 `ACTIVE`，运行时还应继续检查：

1. `is_current` 是否符合当前业务查询语义。
2. `valid_from` 是否已生效、`valid_to` 是否已过期。
3. 对应赛季是否已结束或禁用。
4. 授权球员是否仍为认证通过、是否被处罚限制。
5. 查询的 `seasonId` 与 `teamId` 是否与授权记录匹配。

## 8. 权限规则

1. 只有 Admin 角色拥有 `list/query/grant/edit/revoke` 等队长授权权限；Web 端不能自行申请或修改授权。
2. `grant` 只接受认证通过球员，并强制确认缴费；未认证球员或未缴费请求必须失败。
3. 绑定球队时，管理员只能把授权绑定到该会员本人担任队长的球队，不能替他绑定别人的球队。
4. 队长操作自己的长期球队时，需要校验有效队长授权和球队归属；操作赛事时还必须精确匹配 `seasonId`。
5. 授权未绑定球队时，可以允许队长创建/绑定自己的球队；绑定其他球队、其他赛季或其他会员球队必须失败。
6. 授权收回或过期后，已有前端页面、旧 token、隐藏按钮均不能继续获得管理权限，必须由后端运行时校验拦截。
7. 普通成员只能查看赛事/球队公开信息，不能调用队长创建、编辑、报名、审核申请或赛事阵容管理接口。

## 9. 并发与幂等

| 场景 | 当前机制 | 结论 |
|---|---|---|
| 同会员同赛季重复授予 | Service `countActiveByMemberIdAndSeasonId` + `active_grant_slot` 唯一键 | 有双层防重，需并发插入测试 |
| 同球队同赛季重复授权 | Service `countActiveByTeamIdAndSeasonId` + `team_active_grant_slot` 唯一键 | 有数据库兜底，需验证绑定与授予同时发生 |
| 同一授权重复收回 | 仅允许 `ACTIVE` 收回 | 第二次应失败，需断言日志和通知不重复 |
| 同一授权重复绑定球队 | 仅允许未绑定授权，且校验同赛季球队唯一 | 有基础防重，需测试管理员双击 |
| 授权与报名并发 | 报名权限由 `findActiveGrantForEvent`/`requireValidQualificationForEvent` 运行时判断 | 需验证收回/过期后同时到达的报名请求 |
| 赛季结束批量过期 | `expireBySeasonFinish` 批量更新并写日志 | 需验证任务重复运行不会重复通知或改变历史时间 |
| 多赛季授权 | 业务查询支持 `seasonId`，数据库槽位按赛季唯一 | `grant` 会调用 `clearCurrentByMemberId`，`is_current` 多赛季语义必须专项核对 |

## 12. 已知问题和风险

1. **P0：`is_current` 的多赛季语义需要确认。** 授权唯一槽位按 `seasonId + memberId` 支持多赛季，但授予时调用 `clearCurrentByMemberId`；如果某些 Web/球队逻辑只查 `is_current=1`，后授予的赛季可能影响前一赛季的“当前授权”查询。
2. **P0：自动过期触发链路需确认。** Service 已有 `expireBySeasonFinish`，但必须确认赛季结束任务或状态变更流程确实调用，不能只依靠查询时临时判断。
3. **P1：授权有效期、赛季状态、球员处罚是三套运行时条件。** 任何一层漏校验都会造成过期或受限队长继续管理。
4. **P1：授权绑定球队前后的权限边界需统一。** 未绑定授权可用于建队，但已绑定后只能管理绑定球队；所有 Controller/Service 应统一使用 `requireValidQualificationForEvent` 或等价 owner 校验。
5. **P1：Admin 编辑接口可修改备注和缴费信息，但产品是否允许修改有效期尚未明确。** 不能通过备注编辑绕过重新授权或续费规则。
6. **P2：通知不是授权状态本身。** 消息发送失败不应导致授权回滚，但必须可在日志或运营后台发现。

## 13. 下一步建议

### P0

1. 使用两个赛季做多授权回归，重点验证 `is_current`、`seasonId` 精确查询和报名/球队权限不能跨赛季。
2. 验证赛季结束真实任务调用 `expireBySeasonFinish`，并检查授权、日志、通知三层结果。
3. 对授予、绑定、收回和报名同时请求做并发测试，确认唯一键异常不会留下半条授权或错误日志。

### P1

1. 统一所有队长业务的运行时校验入口，禁止部分接口只查“全局 current”而不查赛事/球队。
2. 补充授权过期、收回、球员处罚和认证状态变化的接口级越权测试。
3. 明确缴费确认的证据字段和续费/新赛季授权规则，避免把 `payment_confirmed` 当成永久身份。

### P2

1. 增加授权审计查询和导出，支持按会员、赛季、球队、状态和操作人追溯。
2. 在后续 `05`、`08`、`09` 文档中分别引用队长授权作为建队、赛事结构和报名的共同前置条件。
