# 20. 当前待测试总清单

> 本清单汇总 `00-业务总览.md`、`02-球员档案与球员认证.md` 至 `18-并发幂等.md` 的静态核查结论，以及 `核心业务/核心实现.md` 的验收要求。截至 **2026 年 7 月 31 日**，本轮没有执行真实数据库迁移、双账号浏览器联调、接口自动化或并发压测；“代码确认”不等同于用户验收通过。

## 1. 业务定位

本文件是第三批 P0 联调验收和后续页面可用性完善的统一入口。它把跨模块测试按依赖和风险排序，避免在数据库结构不完整、权限边界未闭合或正式结果口径不一致时，只验证页面“能打开”。

建议按“数据库迁移与基础账号 → 认证/球队 → 报名与赛程 → 比赛数据 Submission → 统计公开 → 权限与并发”的顺序执行。任一 P0 前置失败时，应暂停依赖其结果的后续用例并先修复根因。

## 2. 最终业务规则

1. 所有需要的 `basket_*` 表、字段和索引必须先完成迁移并通过结构核对，不能用代码编译成功代替数据库可用。
2. 球员认证、游戏平台身份、队长授权、长期球队成员关系、赛事报名、赛事阵容和比赛数据必须形成可追溯的业务链路。
3. 报名审核通过后的赛事球队、名单、赛程和历史展示必须使用赛事/赛季快照，不能被长期球队后续改名、换 Logo、换成员污染。
4. 比赛数据只能经 Submission 提交、审核、正式结果同步和统计结算后公开；审核中、驳回或草稿数据不得进入赛果、统计和排行榜。
5. 所有私有写操作必须在后端校验登录、角色、对象归属、状态和有效期；旧 CRUD 不得绕过专用业务链路。
6. 重复点击、网络重试和多操作人并发不得创建重复报名、重复授权、重复赛程、重复 Submission 或重复统计。
7. 官网页面必须使用真实公开接口；草稿赛程、未确认赛果、Mock 数据和过期快照均不得对外展示。

## 7. 状态机

```text
球员认证：DRAFT/SUBMITTED -> APPROVED | REJECTED
队长授权：有效 -> 撤销/过期/赛季结束
入队申请：PENDING -> APPROVED | REJECTED | WITHDRAWN
赛事报名：DRAFT -> SUBMITTED -> REVIEWING -> APPROVED | REJECTED
赛程：DRAFT -> PUBLISHED -> OFF_SHELF；比赛：SCHEDULED -> FINISHED/CANCELLED
比赛数据：SUBMITTED -> APPROVED(CONFIRMED) | REJECTED -> 新版本 SUBMITTED
争议/异常：申请 -> 审核中 -> 通过/驳回 -> 修订或终止
处罚：生效 -> 到期/撤销；统计：待结算 -> 结算中 -> 已完成/失败
```

测试时必须记录每次状态变更前后的数据库值、接口返回、审计记录和公开页面结果；仅验证页面提示不构成状态机验收。

## 8. 权限规则

1. 未登录访问私有接口应返回 `401`；普通成员、非本队队长、过期/撤销队长、非赛事范围管理员和非本场参赛者的越权请求应返回 `403` 或稳定业务错误。
2. 认证、平台账号、资料、消息、文件和隐私设置必须只允许本人查询或变更。
3. 报名、阵容、入队申请、邀请、成员管理和比赛数据提交必须同时验证当前用户、球队归属、授权有效期、赛事/比赛状态。
4. 管理员审核、处罚、赛程和结算必须验证权限码与赛事范围；不能只依赖前端路由守卫。
5. 必须对旧 `/basket/team/**` 生成式 CRUD 做专项负向测试；在该绕过未修复前，团队相关 P0 用例不能视为端到端通过。

## 9. 并发与幂等

1. 需要并发验证的核心对象包括认证审批、游戏平台账号、入队申请、报名、报名审核、队长授权、赛程生成、Submission 提交/审核和赛季结算。
2. 每个并发用例至少使用两个独立会话或两个并发 HTTP 请求，并检查：成功数、失败码、主/子表记录数、最终状态、审计条数、统计值和公开结果。
3. 关键保护包括报名/阵容/授权/Submission 的唯一索引、审核状态条件更新、赛季/比赛行锁、`basket_stat_sync_record` 幂等键和结算 Redis 锁。
4. 应额外模拟网络超时重试、重复点击、唯一键冲突、事务回滚、死锁/锁等待超时及 Redis 锁过期；不得只测试正常成功路径。

## 12. 已知问题和风险

### P0

1. **Submission P0 migration 尚未被本轮执行确认。** 缺少表、列或索引时，Web 提交、Admin 审核、正式结果和统计同步不能进行真实验收。
2. **`/basket/team/**` 遗留 CRUD 白名单过宽。** 该路径可能绕过球队、成员、申请、邀请等专用权限、状态和审计控制。
3. **长期球队退出/踢人规则未完全收敛。** 直接删除成员与“转会期 + 申请 + 审核”的最终规则存在差距。
4. **赛事快照闭环未做数据库实测。** 长期球队资料/成员变化可能污染赛事历史、赛程或公开展示。

### P1

1. 后台旧比分/技术统计确认与 Submission 审核后的正式结果可能形成双权威路径。
2. 报名 Service 的同赛季预检与数据库按平台唯一的索引口径不同；不同平台并发报名的规则需明确。
3. 首页近期赛果静态核查未见 `data_status=CONFIRMED` 过滤，可能提前暴露审核中比分。
4. 公开 API 尚未完整体现 `eventId / seasonId / platformCode` 三维查询；球队比赛页也存在先拉取大页再前端筛选风险。
5. 全局审计、历史快照字段、展示派生统计和 Mock 清理尚未端到端确认。

### P2

1. 结算 Redis 锁的 TTL、续租及原子释放机制需要压测验证。
2. 软删除参与部分唯一索引，重建记录后历史关联、恢复和查询口径需要回归。
3. 文档目录当前缺少 `01-账号注册登录与用户资料.md` 与 `19-前台首页赛事数据展示.md` 的成品；后续测试结果应补回对应模块文档，避免总清单无来源可追溯。
