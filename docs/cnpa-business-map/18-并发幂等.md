# 18. 并发幂等

> 本文对应 `核心业务/核心实现.md` 中“并发幂等”验收项。结论仅来自 Java、Mapper 与 SQL 迁移的静态核对，未进行并发压测、数据库事务隔离验证或真实接口联调。

## 1. 业务定位

并发幂等保障同一业务事实不会因重复点击、网络重试、定时任务重入或多个操作人同时处理而被重复创建、重复审核、重复生成或重复结算。

本项目的核心目标包括：一支球队不会生成重复报名、一条申请不会被重复处理、一项队长授权不会重复生效、一场比赛只保留一个有效数据提交、一份比赛数据不会重复累计统计、一个赛季不会并发生成两套赛程，也不会并发重算两套积分和排行榜。

实现必须同时依赖数据库唯一约束、状态条件更新、行锁/分布式锁、事务边界和幂等记录。仅在 Service 里“先查询再插入”不能单独构成并发安全。

## 2. 最终业务规则

1. 同一球队、同一赛事赛季、同一参赛端重复报名必须只保留一条有效报名；重复点击和并发请求均不得产生多条记录。
2. 报名处于审核中或审核通过后，重复保存阵容不得覆盖已审核阵容；需要变更时必须走受控的重提/变更流程。
3. 入队申请、赛事报名审核和比赛数据审核必须只允许从可处理状态转换一次；两个操作人同时审核时，只有一个成功。
4. 同一用户在同一赛事赛季的有效队长授权必须唯一；同一球队在同一赛事赛季的有效队长授权也必须唯一。
5. 同一比赛只能存在一个待审核或已审核通过的有效比赛数据提交；同一队长重复提交、主客队长同时提交以及管理员同时审核都不得重复生效。
6. 比赛数据审核通过后的正式比赛数据、统计、积分、排行榜和公开缓存更新必须具备幂等保护；重复触发不得重复累计。
7. 同一赛季重复生成赛程必须被阻断，或在明确“强制重新生成”的事务中先安全删除旧草稿后再生成；不得保留重复批次和重复比赛。
8. 同一赛季的统计/积分重算必须串行执行；任务失败、锁超时和重试不得造成双重结算或半完成数据长期对外可见。

## 3. 当前实现结论

| 场景 | 代码确认 | 当前结论 |
| --- | --- | --- |
| 同平台重复报名 | `basket_tournament_registration` 有 `(season_id, team_id, platform_code, is_delete)` 唯一索引；报名创建前也查询既有记录 | 同队、同赛季、同平台有数据库兜底；仍需并发实测错误返回。 |
| 一赛季重复报名 | 专用服务 `assertNoExistingRegistration` 按球队、赛季和阻断状态查询，但不带平台条件 | 业务层意图是一赛季仅一条；该查询是“先查后写”，数据库却允许不同平台并存，存在并发与规则口径不一致风险。 |
| 报名阵容重复保存 | 专用保存入口要求报名可编辑，并检查报名阵容锁定状态；审核通过后不允许直接改 | 状态保护存在；需验证并发保存时不会互相软删/覆盖。 |
| 入队申请处理 | 按申请 ID、`PENDING` 状态条件更新；更新 0 行即提示状态已变化 | 两个队长同时处理同一申请应只成功一个。 |
| 报名审核 | 审核通过/驳回使用 `updateStatusIfMatch`，更新失败提示可能已被其他管理员处理 | 具备状态竞争保护。 |
| 队长授权 | 授权前计数检查；数据库存在会员/赛季和球队/赛季有效授权槽位唯一索引 | 数据库可兜底重复有效授权；Service 未见对唯一键冲突的专门转换，需验证并发时是否返回友好业务错误。 |
| 比赛数据提交 | 提交时锁比赛行、检查当前有效提交，并依赖有效提交槽位唯一索引；捕获 `DuplicateKeyException` | 同一队长或主客队长并发提交应只保留一份有效提交。 |
| 比赛数据审核 | 审核时锁提交记录和比赛行，并用提交状态条件更新 | 两管理员并发审核同一 submission 应只成功一个，后续官方数据同步处于同一事务链。 |
| 统计同步 | `basket_stat_sync_record` 以“比赛 + 正式结果 + 同步类型”构造幂等键，插入唯一键冲突返回 `false` | 同一同步来源不会重复触发结算；不同同步类型仍可能各自重算，应确认业务预期。 |
| 赛程生成 | 事务内对赛季行 `SELECT ... FOR UPDATE`，检查现有批次/比赛；明确强制重生时先删草稿 | 通过数据库行锁串行化同一赛季生成，保护较完整。 |
| 数据结算 | 使用 Redis 赛季级分布式锁，锁内全量重建积分、统计和排行 | 能防止正常入口的同赛季并发重算；锁 TTL 和释放方式需继续评估。 |

### 用户手测记录

本轮未使用两个浏览器会话、两个后台账号或并发压测脚本触发真实竞争；未检查唯一索引异常、事务回滚、锁等待、Redis 锁超时、重复审计或统计结果。因此没有可标记为人工验收通过的并发场景。

### 待联调/待测试

应先执行双请求并发测试：报名、入队申请处理、报名审核、队长授权、主客队比赛数据提交、比赛数据审核、赛程生成和赛季结算。每个场景均需同时检查 HTTP 结果、业务状态、子表数据、审计记录和统计数据。

## 5. 后端实现

### 报名与阵容

1. `TeamRegistrationBusinessServiceImpl.createDraft` 在事务内校验队长、赛季、平台、报名资格与既有报名后插入草稿。
2. 同平台重复报名有数据库唯一索引兜底；Service 的 `assertNoExistingRegistration(teamId, seasonId)` 会阻断草稿、已提交、审核中、已通过和已驳回记录。
3. 报名详情、更新、阵容保存、提交、撤回和删除草稿均先验证当前用户是该报名的授权队长。
4. 保存阵容时先验证报名可编辑、未锁定、人数与成员去重，再从该报名所属球队加载活动成员；无效成员不会进入报名阵容。
5. 审核通过后，报名阵容由状态/赛事阵容锁限制直接修改，后续变更应走阵容变更流程。

### 申请与审核

1. 入队申请处理使用 `id + PENDING + is_delete=0` 条件更新；第二个处理者得到“申请状态已变更”的失败结果。
2. 后台报名审核通过和驳回使用 `updateStatusIfMatch`，仅允许 `SUBMITTED` / `REVIEWING` 等可审核状态流转；更新 0 行会拒绝重复审核。
3. 比赛数据审核通过和驳回使用 `selectByIdForUpdate` 锁定 submission、锁定比赛行、检查待审核状态，并使用 `updateStatusIfMatch` 更新提交状态。
4. 审核通过后再写审核日志、同步正式比赛数据、通知和统计结算；这些步骤均处于标注 `@Transactional` 的服务方法链中。

### 队长授权

1. 授权服务先检查用户和球队在赛季中的有效授权数量，再将旧授权标记为非当前并插入新授权。
2. 数据库通过有效授权槽位唯一索引防止同一会员/赛季或同一球队/赛季同时存在两条当前有效授权。
3. Service 未见对并发插入产生的 `DuplicateKeyException` 做专门的业务错误转换；并发时数据库能阻止重复，但接口提示和审计完整性须实测。

### 比赛数据、统计与结算

1. 官网比赛数据提交通过比赛行锁、有效提交查询和唯一提交槽位协同控制；唯一键冲突被捕获并转换为“已有提交中的数据”。
2. 管理员审核时再次锁定 submission 和 match，防止审核与另一个审核/提交交错。
3. 审核通过生成正式结果后，`BasketMatchStatSyncServiceImpl` 先写入 `basket_stat_sync_record`；同幂等键的重复写由唯一键捕获并返回不再同步。
4. `BasketDataSettlementServiceImpl` 采用赛季级 Redis 锁，锁内全量重建积分榜、球队统计、球员统计和排行榜，完成后清理公开缓存。

### 赛程生成

1. `BasketScheduleGenerateServiceImpl.generateDraftSchedule` 在事务内先对赛季执行 `selectByIdForUpdate`，然后检查已发布赛程、已有生成批次和已有比赛。
2. 非强制生成时发现已有批次或比赛直接拒绝；强制重新生成时只允许删除旧草稿后重建。
3. 自动生成任务也复用同一生成服务，因而与手工生成共享赛季行锁。

## 6. 前端实现

1. 前端的防重复点击、按钮 loading、二次确认只能降低误操作，不能作为幂等保证；所有结论以后端状态、唯一索引和锁为准。
2. 报名、申请处理、审核、队长授权、比赛数据和赛程生成页面应在请求期间禁用重复提交，并在收到“已被其他人处理/已有有效记录”后刷新列表或详情。
3. 报名阵容页面必须依据后端 `canEdit`、`rosterLocked` 和状态提示禁用编辑；即使前端绕过，后端仍应拒绝不可编辑状态。
4. 前端请求目前并非所有场景都携带统一的客户端幂等键；报名、申请、审核和比赛数据主要依赖服务端状态与数据库约束。
5. 结算、自动排程等后台任务应展示“正在执行/被锁定/已完成/失败”状态，不能让用户仅凭按钮点击判断是否重复执行。

## 7. 状态机

```text
入队申请：PENDING --通过/驳回--> APPROVED / REJECTED
                         ^ 同一状态条件更新只允许一次

赛事报名：DRAFT -> SUBMITTED -> REVIEWING -> APPROVED
                   |                         |
                   +------> REJECTED <--------+
报名可编辑状态与审核通过后的阵容锁共同限制重复覆盖。

比赛数据提交：SUBMITTED / 审核待处理 --通过/驳回--> APPROVED / REJECTED
REJECTED --重提--> 新版本 SUBMITTED，旧版本 SUPERSEDED
同场只能存在一个有效提交槽位。

赛程：无批次 --生成草稿--> DRAFT 批次 --发布--> PUBLISHED
已有批次/比赛时拒绝再次生成；强制重生仅先清理草稿。

赛季统计：未锁定 --获得 Redis 锁--> 全量重建 --释放锁--> 未锁定
```

状态条件更新只能保证“同一状态不可重复转移”；若副作用不与状态更新处于同一事务或没有独立幂等记录，仍可能发生状态成功而统计/消息等副作用重试的问题。

## 8. 权限规则

1. 并发保护不替代权限校验。报名、阵容、入队申请和比赛数据的状态更新必须先验证当前用户或管理员是否有操作对象的权限。
2. 管理员审核接口除权限注解外，应在 Service 中验证赛事范围；状态条件更新不能防止有权限码但无赛事范围的管理员处理别的赛事数据。
3. 队长授权、报名和比赛数据提交均应在事务起点读取当前用户和当前有效队长资格；不得使用前端传入的操作人 ID 或过期缓存的授权结果。
4. 第 17 项记录的 `/basket/team/**` 遗留 CRUD 绕过会直接跳过业务状态机、唯一性预校验和归属校验；该漏洞修复前，本篇许多并发结论不能作为端到端保障。

## 9. 并发与幂等

### 已实现机制

1. **数据库唯一索引**：报名、报名球员、有效队长授权、比赛数据提交及其子表、统计同步记录等关键对象已有唯一约束。
2. **状态条件更新**：入队申请、报名审核、比赛数据审核等操作以旧状态作为 `WHERE` 条件，更新失败即可识别已被其他操作人处理。
3. **悲观行锁**：赛程生成锁赛季行；比赛数据审核锁提交与比赛行；官网比赛数据提交锁比赛行。
4. **分布式锁**：赛季统计重算通过 Redis `setIfAbsent` 获取 30 分钟锁，防止正常入口并行重建同一赛季。
5. **幂等记录**：统计同步记录以唯一 `idempotency_key` 保证同一正式结果、同一同步类型不重复触发。
6. **事务**：报名创建、申请处理、审核、赛程生成、比赛数据审核与结算重建等关键服务使用 `@Transactional(rollbackFor = Exception.class)`。

### 尚需验证的机制边界

1. 报名 Service 的“先查后插入”与数据库“按平台唯一”规则不完全一致；同队同赛季不同平台并发时是否允许多条报名，必须由产品规则和数据库约束统一决定。
2. 队长授权先计数后插入，最终依赖唯一索引阻止并发重复；需确认唯一键异常不会以 `500` 暴露给前端，也不会留下“旧授权已清 current、新授权未写入”的异常状态。
3. 赛程生成依赖同一数据库的赛季行锁而非批次表的赛季唯一索引；通过专用服务调用时有效，直接写库或其他未加锁入口仍可能产生重复批次。
4. Redis 结算锁的 TTL 固定为 30 分钟，释放逻辑采用“先读 token 再删除”而非原子 compare-and-delete；超时后锁被其他任务获取时，旧任务理论上可能误删新锁。

## 10. 已通过项

### 代码静态确认

1. 赛事报名、报名球员、有效队长授权、比赛数据提交、提交明细和统计同步均存在关键唯一索引。
2. 入队申请、报名审核和比赛数据审核均存在状态条件更新，重复处理会失败。
3. 比赛数据提交/审核和赛程生成均使用数据库行锁；赛季统计重算使用 Redis 分布式锁。
4. 统计同步使用唯一幂等记录，重复审核通过不会按同一同步类型重复触发结算。
5. 报名审核、比赛数据审核、赛程生成和结算等关键链路已声明事务边界。

### 用户手测记录

本轮未进行双请求并发压测或事务回滚验证，**暂无可认定为人工验收通过的并发测试记录**。

2. 同一已批准 submission 被重复调用审核通过；确认正式结果、`basket_stat_sync_record`、积分榜、球队/球员统计和排行榜均不重复增长。
3. 使用不同同步来源对同一正式比赛结果重复触发，确认全量重建的结果稳定且不产生重复历史记录。
4. 同一赛季同时发起两次结算/重算，确认第二请求被 Redis 锁阻断；模拟超过 30 分钟的任务和异常退出，验证锁不会误删或永久残留。
5. 强制重生成草稿赛程与发布赛程并发执行，确认不会误删已发布比赛或产生半套赛程。

### P2

1. 模拟数据库唯一键异常、死锁、锁等待超时和事务回滚，检查接口返回、重试策略、审计记录及子表清理。
2. 验证多实例部署下赛程生成的数据库锁和结算 Redis 锁是否使用同一数据源/Redis 集群。
3. 检查按钮连点、网络超时重放、消息队列重复投递和定时任务重入下的幂等表现。

## 12. 已知问题和风险

### P0

1. **遗留球队 CRUD 可绕过并发控制。** 第 17 项已确认 `/basket/team/**` 的生成式 CRUD 白名单过宽；它可直接写球队、成员、入队申请等数据，绕过专用 Service 的状态条件更新、唯一性预检、审计和事务副作用。修复前不能声称团队相关业务端到端幂等。
2. **报名唯一规则存在口径不一致。** 专用 Service 按“球队 + 赛季”阻断报名，但数据库唯一索引按“球队 + 赛季 + 平台”约束。并发的不同平台请求可能同时通过查询并落库，是否允许多平台报名必须明确并统一实现。
3. **赛程批次缺少赛季级数据库唯一约束。** 当前正确性依赖 `SELECT ... FOR UPDATE` 与专用服务路径；若未来新增生成入口、脚本或跨库写入，可能绕过锁生成重复批次/比赛。

### P1

1. 队长授权采用“计数检查 → 清旧 current → 插入新授权”，并发时主要靠唯一槽位索引兜底；未见专门 `DuplicateKeyException` 转换，错误体验及旧授权恢复需压测验证。
2. Redis 结算锁的 30 分钟 TTL 可能短于超大赛季重算时长；释放操作不是 Lua 原子比较删除，锁过期并被新任务获取后存在旧任务误删新锁的理论窗口。
3. `basket_stat_sync_record` 的幂等键包含同步类型。相同正式结果从不同来源触发时会被视为不同幂等操作；虽全量重建应保持结果一致，但可能重复产生审计、缓存清理或额外负载。
4. 报名创建和队长授权等部分路径仍包含“先查询后写”，数据库约束之外的业务规则无法仅靠查询保证。
5. 未发现统一的全局幂等键协议、重试次数、死锁重试或锁等待监控；各模块实现方式不一致，后续扩展容易遗漏。

### P2

1. 结算结果以全量重建保证最终一致性，但需要确认重建过程中公开查询是否读取到中间态，以及缓存清理失败的降级策略。
2. 多处唯一索引将 `is_delete` 纳入键，软删除后允许重建记录；需要验证历史审计、外键关联和恢复操作不会误指向新旧两条业务记录。
3. 自动赛程生成会捕获异常并记录警告；若失败原因持续存在，缺少任务级幂等状态、告警与人工恢复入口会增加运维排查成本。

## 13. 下一步建议

### P0

1. 先修复 `/basket/team/**` 遗留 CRUD 绕过，确保所有团队写入只能通过专用 Service，再对并发用例做验收。
2. 明确报名是否允许同队同赛季多平台报名：允许则将 Service 预检改为带平台；不允许则增加 `(season_id, team_id, is_delete)` 唯一约束并处理历史数据。
3. 为赛程批次增加赛季级有效批次唯一约束或锁记录，形成“数据库约束 + 行锁”的双重保护。
4. 对队长授权、报名创建、申请创建等“先查后写”入口统一捕获唯一键异常并转换为稳定业务错误，避免并发请求返回裸数据库异常。

### P1

1. 将 Redis 结算锁改为带续租/看门狗的成熟分布式锁，使用 Lua 原子 compare-and-delete；锁 TTL、超时、重入、失败恢复和监控应配置化。
2. 将关键副作用纳入明确的幂等设计：状态更新、正式结果发布、统计同步、消息通知、审计写入和缓存清理分别定义业务键与重试策略。
3. 为赛程生成、审核、结算和统计同步建立并发集成测试，至少覆盖成功/冲突/异常回滚/锁超时/多实例五类场景。
4. 增加数据库死锁、唯一键冲突、锁等待超时和 Redis 锁持有时间的指标与告警。

### P2

1. 形成项目级幂等规范：客户端幂等键格式、服务端唯一索引命名、状态条件更新模板、异常码和审计字段统一。
2. 为自动任务增加可查询的运行批次、执行状态、重试次数、失败原因和人工重跑入口。
3. 定期复核软删除参与唯一键后的数据修复策略，避免重新创建记录时破坏历史关联与统计追溯。
