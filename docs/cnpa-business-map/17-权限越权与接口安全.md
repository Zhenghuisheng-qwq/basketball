# 17. 权限越权与接口安全

> 本文件对应 `核心业务/核心实现.md` 中“权限越权”验收项。结论来自管理端、官网端 Java 代码及路由静态核查；未执行真实账号、Token、数据库和浏览器联调，不能将“代码存在”视为安全验收通过。

## 1. 业务定位

权限安全的目标不是隐藏页面按钮，而是确保每个写操作和私有读操作在后端同时满足：已登录、具备相应角色或授权、对象归属正确、状态允许、有效期未过、请求数据与当前业务范围一致。

本项目存在两套主要边界：

1. **管理端**：使用 Spring Security 的 `@PreAuthorize` 权限码与赛事范围校验管理后台操作。
2. **官网会员端**：`LoginInterceptor` 校验会员 Token 并写入 `UserContext`；专用业务服务使用当前会员 ID、球队成员关系和队长授权判断归属。

此外，`GeneratedCrudAccessInterceptor` 用于阻断旧生成式 CRUD，防止它绕过专用业务流程。该拦截器的白名单配置是本模块当前最重要的风险点。

## 2. 最终业务规则

1. 所有非公开接口必须后端登录校验；公开接口必须显式标注，且只能返回允许公开的数据。
2. 普通会员调用创建球队、更新球队、移除成员、处理入队申请、报名、保存阵容、提交比赛数据等管理操作，应被拒绝；创建球队仅允许持有运行时有效且未绑定球队的队长授权者。
3. 队长只能管理自己被授权且归属正确的球队/赛季/报名记录；不得操作其他队长的球队、报名、成员或入队申请。
4. 队长授权必须在每个关键写入口重新判断状态、缴费、球员认证、开始/结束时间、赛季状态和授权绑定球队；授权撤销、过期或赛季结束后不得继续使用。
5. 私有资料、通知、文件、平台账号及资料变更记录必须仅限当前会员本人访问；请求不得允许客户端传入任意会员 ID 绕过归属。
6. 报名必须验证队长身份、球队归属、赛季开放状态、赛事平台已开放和阵容成员归属；不得把其他球队成员放入阵容。
7. 比赛数据只能由已认证、属于该比赛参赛队且具有该报名队长身份的人提交；非本场队长、普通队员和未参与该比赛者必须失败。
8. 旧生成式 CRUD 不得写球队、成员、入队申请、报名、比赛数据、通知、个人资料等领域对象；业务只能通过专用 Controller / Service 进入。

## 3. 当前实现结论

### 代码确认

1. 官网端 `LoginInterceptor` 默认拦截 `/basket/**`；除显式 `@NoLoginRequest` 的认证和官网公开接口外，缺少 Token、Token 失效或认证版本失效均返回 `401`。认证成功后将会员 ID 写入 `UserContext`，请求结束后清理 ThreadLocal。
2. 专用账号中心、资料、消息、文件、游戏平台账号、球队、报名、入队申请、成员管理和比赛数据接口不接收任意会员 ID，而是从 `UserContext.getRequiredUserId()` / `getRequiredMemberId()` 取得当前用户。
3. 专用建队接口 `/basket/team/create` 会校验运行时有效队长授权、授权尚未绑定球队、球员认证和当前成员资格；球队更新/Logo 绑定要求当前用户为该球队队长。
4. 专用报名流程会校验当前用户、队长授权、授权绑定球队、报名记录的 `captainMemberId`、赛季开放状态和开放的 `platformCode`；保存报名阵容时会按报名所属球队加载活动成员，其他球队成员无法通过该专用入口进入阵容。
5. 专用入队申请处理要求当前用户是目标球队队长；撤回申请要求申请人为当前用户。球队成员更新、移除和候选成员查询也经专用服务进行球队管理校验。
6. 账户消息详情和标已读使用 `receiverId + 当前 memberId` 查询；游戏平台账号变更历史由 Controller 固定传入当前会员 ID，服务再按该会员的已认证球员查询。
7. 专用比赛数据提交要求当前用户已认证、比赛已结束，并从已审核报名记录中确认其为本场主/客参赛球队的队长；非本场队长会返回 `403`。
8. `GeneratedCrudAccessInterceptor` 能阻断大多数旧生成式 CRUD 路径，如报名、比赛数据、通知和会员资料的 `getByPage`、`getById`、`addOrUpdate`、`delete/*`、`deleteByIds`。未登录调用会先被登录拦截为 `401`，已登录调用通常会被该拦截器拒绝为 `403`。
9. **严重例外：** 拦截器对整个 `/basket/team/` 前缀直接放行。生成式 `BasketTeamController`、`BasketTeamMemberController`、`BasketTeamJoinApplicationController`、`BasketTeamInvitationController` 等仍暴露在这一前缀下，且其 CRUD 代码未见当前用户、队长授权或对象归属校验。已登录普通会员可绕过专用流程直接调用这些遗留接口，风险极高。

### 用户手测记录

本轮未以普通会员、有效队长、过期队长、其他球队队长和管理员分别登录并调用接口；也未实际伪造 `teamId`、`registrationId`、`receiverId`、`memberId`、`platformCode`、阵容成员 ID 或比赛 ID。因此所有拦截结论仍需通过 HTTP 状态码、返回信息、数据库变化和审计记录进行实测。

### 待联调/待测试

应优先验证 `/basket/team/**` 生成式 CRUD 白名单绕过，再验证专用球队、报名、入队申请、消息、资料变更、阵容和比赛数据接口的对象级授权。

## 5. 后端实现

### 登录与请求上下文

1. `LoginInterceptor` 注册到 `/basket/**`，只有认证、公开官网接口及显式标记 `@NoLoginRequest` 的方法可匿名访问。
2. Token 解析后校验会员 ID 和认证版本；认证版本失效会撤销 Token 并拒绝请求。
3. 当前会员 ID 写入 `UserContext`，业务服务通过 `getRequiredUserId()` / `getRequiredMemberId()` 取得，不信任客户端传入的会员 ID。

### 专用业务授权

| 业务 | 专用服务主要校验 | 静态结论 |
| --- | --- | --- |
| 创建球队 | 有效队长资格、资格未绑定球队、球员认证、可加入球队资格 | 专用接口具备后端校验。 |
| 更新球队/Logo | 当前用户 + `requireTeamCaptain(teamId)` | 专用接口具备对象归属校验。 |
| 赛事报名 | 当前用户、活动成员、有效赛事队长授权、授权绑定球队、赛季开放、平台开放、报名唯一性 | 专用接口具备主要校验。 |
| 报名详情/编辑/阵容/提交 | 报名 `captainMemberId` 必须为当前用户，且其赛事授权仍有效并绑定该队 | 专用接口具备对象归属校验。 |
| 入队申请处理 | 当前用户必须为目标球队队长，申请状态必须允许处理 | 专用接口具备对象和状态校验。 |
| 退出/踢人/成员更新 | 当前用户、球队队长或成员身份、成员归属、状态和转会期规则 | 需结合各场景继续联调。 |
| 消息读取/标记已读 | `receiverId` 与当前会员 ID 同时匹配 | 已实现对象归属查询。 |
| 平台账号/变更历史 | Controller 固定当前会员 ID；服务按当前会员的已认证球员查找 | 已实现用户边界。 |
| 比赛数据提交 | 当前用户已认证、比赛存在且结束、提交者为本场参赛球队队长、当前无有效提交 | 已实现主要校验与数据库锁。 |

### 旧 CRUD 防护

`GeneratedCrudAccessInterceptor` 按 URL 识别生成式 CRUD 后缀并返回 `403`，目的是迫使外部请求走专用 Controller。该机制对 `/basket/tournament/registration/**`、`/basket/match/**`、`/basket/message/**`、`/basket/member/profile/**` 等路径有效。

但其 `/basket/team/**` 白名单过宽，使所有以该前缀开头的生成式 CRUD 同样被放行；这是当前代码与“旧 CRUD 写接口必须失败”规则的直接冲突。

## 6. 前端实现

1. 管理端多数后台操作通过 `v-hasPermi` 隐藏无权限按钮，Controller 同时使用 `@PreAuthorize`；前端隐藏只改善体验，真正授权依赖后端。
2. 官网端球队、报名、消息、个人资料、平台账号和比赛数据页面调用专用 API，接口本身从登录 Token 的 `UserContext` 取当前用户。
3. 官网前端不应保存或拼接可篡改的 `memberId` 作为个人中心、消息、资料变更历史的查询条件；当前专用接口设计基本符合这一原则。
4. 前端不能防止用户直接构造 HTTP 请求；因此对 `/basket/team/**` 遗留 CRUD 的白名单漏洞，任何按钮隐藏、路由守卫或页面限制都无法缓解。

## 7. 状态机

权限判定不是独立状态机，而是由登录态、队长资格、对象归属和业务状态共同决定：

```text
未登录 / Token 失效
  └─ 私有接口 → 401

已登录普通会员
  ├─ 本人资料、本人消息、本人申请 → 允许（满足对象归属）
  ├─ 专用建队 / 报名 / 队伍管理 → 403，除非满足队长资格与对象归属
  └─ 旧生成式 CRUD → 应为 403

运行时有效队长
  ├─ 管理已绑定球队、对应赛季报名 → 允许
  └─ 管理其他球队 / 其他报名 → 403

队长资格被撤销、过期、未缴费、未认证、未到生效期或赛季结束
  └─ 需在每次关键操作重新判定为无效 → 403
```

当前专用球队和报名管理通过 `CaptainQualificationValiditySupport` 判断授权状态、缴费、认证、有效起止时间及赛季结束状态。比赛数据提交只按已审核报名中的 `captainMemberId` 判断本场队长，未见同样调用完整队长资格有效期校验，需重点验证。

## 8. 权限规则

### 管理端

1. 后台 Controller 普遍通过 `@PreAuthorize("@ss.hasPermi(...)")` 区分查询、新增、编辑、审核、发布、生效、撤销等权限；敏感写入口不应仅在前端配置按钮权限。
2. 赛事范围相关服务会使用赛事管理员范围校验；应对列表、详情、编辑、审核和删除等每种操作分别测试是否覆盖，而不是仅验证创建入口。

### 官网会员端

1. 登录拦截负责会员身份认证，`UserContext` 负责当前会员边界。
2. `CaptainPermissionServiceImpl` 的运行时队长有效性会校验：资格为当前、状态为有效、未撤销/过期、缴费确认、球员认证通过、有效时间范围及赛季未结束。
3. `requireTeamCaptain` 同时校验授权绑定团队和当前球队；`requireRegistrationCaptain` 还校验报名记录的队长字段、赛季和球队绑定。
4. 消息使用 `receiverId + memberId`，平台账号使用 `platformAccount.playerId + 当前会员球员`，报名阵容使用 `registration.teamId + active teamMemberIds` 限制对象范围。

### 例外与缺口

`GeneratedCrudAccessInterceptor` 对 `/basket/team/**` 的整体放行使生成式团队、成员、邀请和入队申请 CRUD 不受上述专用服务约束。其控制器/服务是直接 `IService` 写库模板，未见 `UserContext`、队长资格、团队归属或状态流转校验。

## 9. 并发与幂等

1. 登录上下文采用请求级 ThreadLocal，并在 `afterCompletion` 清理；异常处理链路仍需压测验证不会发生线程复用串号。
2. 入队申请处理使用“申请 ID + PENDING 状态”条件更新，两个队长同时处理时应只有一个成功。
3. 比赛数据提交会锁定比赛行、检查有效提交，并捕获唯一键冲突；同时提交通常只能保留一个待审核提交。
4. 报名创建会校验既有报名和平台开放状态；具体唯一索引、重复请求异常返回和跨端并发结果应在第 18 项文档及联调中验证。
5. `/basket/team/**` 生成式 CRUD 绕过不仅是授权问题，也绕开了上述状态条件更新、唯一性检查、审计和事务副作用，可能产生无法修复的脏数据。

## 10. 已通过项

### 代码静态确认

1. 官网私有 API 默认要求登录；公开接口使用显式 `@NoLoginRequest` 标识。
2. 当前会员、队长资格、球队成员、报名队长、消息接收人和平台账号所有者在多个专用服务中已有后端归属校验。
3. 专用报名阵容保存会按报名所属球队加载活动成员，无法通过该入口使用其他球队成员。
4. 专用比赛数据提交会拒绝普通队员和非本场参赛球队队长。
5. 旧生成式报名、比赛数据、通知及会员资料 CRUD 已具备统一拦截入口。

### 用户手测记录

本轮未执行真实 Token、权限码或多账号测试，**没有任何安全场景可标记为人工验收通过**。

## 12. 已知问题和风险

### P0

1. **`/basket/team/**` 生成式 CRUD 白名单绕过。** `GeneratedCrudAccessInterceptor` 对整个前缀直接返回允许；而遗留 `BasketTeamController`、`BasketTeamMemberController`、`BasketTeamJoinApplicationController` 等直接数据库 CRUD 未见用户、队长和对象归属校验。已登录普通用户可能创建/篡改/删除任意球队、成员或入队申请。
2. **同一路径存在专用与生成式控制器。** 专用 `/basket/team/create`、`/{teamId}`、成员和入队申请接口与生成式 `/getByPage`、`/addOrUpdate`、`/delete/*` 并存，容易在前端、脚本或攻击请求中走错入口；旧入口必须彻底下线或严格拒绝。
3. **比赛数据队长有效期可能未被完整复核。** `PlayerMatchDataServiceImpl` 提交时通过已审核报名记录中的 `captainMemberId` 判断队长，但未见调用完整的 `requireValidQualificationForEvent`；授权已过期/撤销后是否仍可提交需要立即验证并补强。

### P1

1. 生成式 CRUD 拦截器以 URL 后缀字符串识别接口，白名单和路径变更容易产生遗漏；它不是基于 Controller 注解、路由注册或资源类型的强制策略。
2. 生成式团队 CRUD 的删除使用 `GET /delete/{id}`，即使修复权限也不应保留破坏性 GET 接口，以免被预取、爬虫或跨站请求误触发。
3. 官网 CORS 当前允许任意来源模式并允许携带凭证；需结合部署域名、Cookie/Token 传输方式和 CSRF 防护复核，避免跨站调用私有接口。
4. `@NoLoginRequest` 是显式放行机制，缺少统一白名单清单和自动化检查时，后续开发误标公开会造成回归风险。
5. 管理端的权限注解与服务层赛事范围复核并非所有模块均已逐条确认；仅靠菜单权限不能防止已获某项权限的管理员跨赛事操作。

### P2

1. 多个错误场景返回“对象不存在”而非统一 `403`，可能对已登录攻击者泄露对象是否存在；需要按隐私等级统一错误策略。
2. 个人资料、平台变更历史和消息内容含敏感信息，应复核日志、缓存、导出和异常信息是否遵守脱敏与最小化返回原则。
3. 账号安全与权限拒绝事件虽然有部分日志，但未见统一的失败授权审计、限流和告警策略，难以及时发现批量越权尝试。

## 13. 下一步建议

### P0

1. 立即删除 `GeneratedCrudAccessInterceptor` 对 `/basket/team/**` 的整体放行；默认拒绝所有生成式 CRUD，仅允许明确列出的专用业务路由。
2. 下线、删除或仅限内部管理网访问遗留生成式 `BasketTeam*Controller`；至少把其 `addOrUpdate`、删除和批量删除改为无条件 `403`，并清理前端/脚本调用。
3. 在比赛数据提交、重提、状态查询等入口统一调用当前赛事队长授权有效性校验，不能只信任报名表历史队长字段。
4. 建立自动化权限矩阵测试：以未登录、普通会员、本人、其他人、有效队长、过期队长、后台管理员、跨赛事管理员为维度，覆盖所有读写 API。

### P1

1. 将“认证、对象归属、队长授权、赛事范围、状态机”封装为可复用的服务端授权策略或注解，避免 Controller/Service 手工遗漏。
2. 用路由元数据或 Controller 注解替代字符串后缀拦截；启动时输出旧 CRUD 暴露清单，CI 中若新增可写生成式接口则失败。
3. 为每个高风险写操作记录拒绝原因、操作者、目标对象、客户端 IP、请求追踪 ID，并对连续拒绝/批量访问配置告警和限流。
4. 收紧生产 CORS 为受信任域名与必要方法/头；根据 Token 存储方式补齐 CSRF、SameSite、Origin/Referer 校验策略。

### P2

1. 统一 `401`、`403`、不存在和状态不允许的返回规范，兼顾客户端可用性与对象枚举防护。
2. 定期对 `@NoLoginRequest`、后台 `@PreAuthorize`、赛事范围校验和下载/导出接口进行静态扫描与人工复审。
3. 在安全测试环境使用代理包和自动化脚本执行本篇待测清单，并将发现的越权路径作为发布阻断条件。
