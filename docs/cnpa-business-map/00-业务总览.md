# CNPA 核心业务总览

> 本文只基于当前仓库中的 Java、Vue、SQL 与已有审计文档整理；“用户手测通过”与“代码确认”分别标注。本文不修改业务代码、数据库或接口。

## 1. 业务定位

CNPA 是篮球赛事平台官网，由四个独立部署模块组成：

| 模块 | 职责 | 当前入口/配置证据 |
|---|---|---|
| `basketball-web` | 官网会员、球队、报名、公开赛事与 Web 业务 API | `com.zhs.MiniApplication`；`application.yml` 配置端口为 `8881` |
| `basketball-web-ui` | 官网、个人中心、队长操作页面 | `src/main.ts`、`src/router/index.ts`、Vite 代理指向 `8881` |
| `basketball-admin` | 管理员审核、赛事运营、赛程、统计与内容管理 | `com.zhs.RuoYiApplication`；`application.yml` 配置端口为 `8080` |
| `basketball-admin-ui` | 若依管理后台页面 | `src/main.ts`、`src/router/index.ts` |

业务目标是将长期球队与单届赛事参赛数据区分：长期球队保存队伍资产、成员和队史；报名审核通过后应形成赛事球队/赛事阵容快照；比赛和统计应以已确认的赛事数据对外公开。

## 2. 最终业务规则

1. 主链路为：账号注册登录 → 用户资料 → 球员认证 → 平台游戏账号 → 队长授权 → 长期球队 → 入队 → 赛事报名 → 赛事阵容锁定 → 赛程 → 比赛数据提交/审核 → 正式结果、积分与公开数据。
2. 账号以邮箱为唯一登录标识；认证通过前只是普通会员，不能加入球队或进入报名阵容。
3. 球队不按 PC、PS、Xbox 分割；平台账号和赛事平台资格属于球员/赛事报名维度。
4. 队长授权按赛事/赛季生效，不是永久身份；只能管理已授权赛事。
5. 长期球队每名成员任一时刻只能有效归属一队；人数目标为 5–8 人，位置 `PG/SG/SF/PF/C` 仅展示，不作为报名阻断条件。
6. 报名审核通过后应使用 EventTeam/EventPlayer（当前代码中的赛事球队、赛季阵容等）承载快照，历史比赛不应被长期球队改名或换人污染。
7. 比赛数据正常链路为队长提交、管理员审核；只有确认数据才能进入正式比分、统计、积分榜和官网公开查询。
8. 争议、异常比赛、处罚、公告和业务审计均必须保留可追溯记录；M06 数据争议与 M07 弃赛异常不应被误记为当前 Submission P0 已完成内容。

## 7. 状态机

| 领域 | 状态/枚举 | 主要流转 | 证据 |
|---|---|---|---|
| 球员认证 | `DRAFT → SUBMITTED → REVIEWING → APPROVED/REJECTED`，可 `CANCELLED` | Web 草稿/提交，Admin 审核 | `PlayerCertStatusEnum` |
| 队长授权 | `ACTIVE / REVOKED / EXPIRED` | 管理员授予、收回、到期失效 | `CaptainQualificationStatusEnum` |
| 球队审核 | `PENDING → REVIEWING → APPROVED/REJECTED` | 创建后后台审核 | `TeamAuditStatusEnum` |
| 邀请/入队申请 | 待响应/处理 → 接受/通过、拒绝、取消或过期 | 被邀请人响应、队长处理申请 | `TeamInvitationStatusEnum`、`TeamJoinApplicationStatusEnum` |
| 长期成员 | `ACTIVE → LEFT/REMOVED` | 当前可直接离队或队长移除 | `TeamMembershipStatusEnum` |
| 赛事阵容变更 | `PENDING → APPROVED/REJECTED/WITHDRAWN` | 转会、补员、队长移交 | `RosterChangeStatusEnum` |
| 比赛数据 | submission 待审核/通过/驳回与正式 `CONFIRMED` 分层 | 提交、驳回重提、审核同步正式层 | Submission P0 服务与迁移 SQL |

## 8. 权限规则

1. Admin 端 Controller 使用 `@PreAuthorize("@ss.hasPermi(...)")`，例如球员认证、队长授权、球队审核、赛程、比赛数据审核和处罚管理。
2. Web 端通过 `UserContext`、会员会话和 Service 层 owner 校验限制个人中心、球队、报名及比赛数据操作。
3. 队长创建/编辑球队、处理申请、报名和赛事阵容操作应由有效 `basket_captain_qualification` 校验；未认证用户不能进入有效球队成员或赛事阵容。
4. `GeneratedCrudAccessInterceptor` 用于阻断 Web 端不应直接暴露的生成式 CRUD 写操作；仍需用 HTTP 黑盒测试验证每条敏感写接口。
5. 前端按钮隐藏不是权限证据，所有跨用户、跨球队、跨赛事操作必须以 Service 层校验为准。
