# 长期球队与成员管理

> 范围：长期球队本体、创建、编辑、球队审核、队长成员、普通成员、人数和归属约束。邀请/申请单独见 `06-加入球队邀请与申请.md`；退出、踢人和转会期单独见 `07-退出球队踢人转会期.md`；单届赛事球队/阵容快照见后续报名文档。

## 1. 业务定位

长期球队是线下组织或长期运营的球队资产，用于保存球队资料、队长、成员、邀请/申请、历史参赛和队史内容。它不等于某一届赛事的 EventTeam，也不应被某个平台绑定。单届赛事报名审核通过后形成的赛事球队、赛季阵容和比赛快照必须与长期球队后续改名、换人相互隔离。

当前 Web 端提供“我的球队、创建、详情、编辑、Logo、成员列表、成员更新、候选球员”；Admin 端提供球队审核、审核记录和相关运营查询。创建球队时系统会把当前有效队长授权绑定到新球队，并为创建者写入队长成员关系。

## 2. 最终业务规则

1. 长期球队本体不与 `PC/PS/XBOX` 某一平台绑定；平台只影响赛事报名资格和球员游戏账号。
2. 只有拥有有效队长授权且已认证的球员才能创建长期球队。
3. 每个有效长期球队需要后台审核；审核通过后才能被公开浏览、接受入队申请并用于正式赛事报名。
4. 一个球员任一时刻只能加入一支有效长期球队；队长也不能加入其他球队。
5. 球队成员上限为 8 人；正式赛事阵容最少 5 人、最多 8 人，不能强制要求五个位置齐全。
6. 长期球队的队长、成员、地区、简介、Logo 和公开状态是长期资产；单届赛事的展示名称、阵容、队长和分组应使用赛事快照层。
7. 普通成员只能查看球队概览和自身允许的信息；只有队长能编辑球队、管理成员、邀请、处理加入申请和代表球队报名。
8. 阵容/报名锁定后，成员调整不得绕过赛事规则；邀请、申请、离队和踢人要按锁定和转会规则约束。
9. 创建、编辑、审核、成员加入/离开/移除、队长变更等关键操作都应保留可追溯记录。

| 8 人上限 | ✓ |  |  | ✓ | `team.max_member_count` 默认 8、申请/邀请候选校验 | 并发接纳成员时需验证不会超过上限 |
| 长期球队最少 5 人 |  | ✓ |  | ✓ | 赛事报名审核使用 `CnpaRosterConstants.MIN_ROSTER_COUNT=5` | 创建和球队审核可在 1 人时通过，不等同最终长期球队规则 |

| 阵容锁定后长期成员操作拦截 |  | ✓ |  | ✓ | 直接离队/移除会检查进行中的报名；赛事阵容变更另有流程 | 邀请/申请及长期成员操作未见统一“赛事锁定”拦截 |

**结论：** 长期球队创建、审核、成员归属和 8 人上限已有业务实现；“长期球队至少 5 人”当前只在正式报名阵容审核中得到强制校验，不能写成球队审核已强制 5 人。长期成员离队/移除又与最终审核/转会期规则存在差异，已在 `07` 继续说明。

## 7. 状态机

### 球队审核与球队状态

```text
创建球队：team_status=ACTIVE，audit_status=PENDING

PENDING ──开始审核──> REVIEWING ──通过──> APPROVED
                               └──驳回──> REJECTED

球队运行状态：ACTIVE(正常) / DISABLED(禁用) / DISSOLVED(解散)
```

`TeamAuditStatusEnum`：`PENDING(0)`、`APPROVED(1)`、`REJECTED(2)`、`REVIEWING(3)`。  
`TeamStatusEnum`：`DISABLED(0)`、`ACTIVE(1)`、`DISSOLVED(2)`。

### 长期成员状态

```text
队长创建球队/邀请接受/申请通过
          │
          ▼
       ACTIVE(在队)
        │       │
     主动离队    队长移除
        ▼       ▼
     LEFT(离队) REMOVED(被移除)
```

成员角色为 `CAPTAIN` 或 `MEMBER`；成员阵容类型为 `OFFICIAL` 或 `TRIAL`。当前直接离队/移除流程不会自动等同于赛事阵容变更审核，详见 `07`。

## 8. 权限规则

1. 创建球队要求当前会员具有有效队长授权、已认证球员档案，并且没有其他有效长期球队成员关系。
2. 编辑球队、绑定 Logo、更新成员、查询候选球员、处理邀请/申请等队长操作必须通过 `requireTeamCaptain` 或等价 owner 校验，不能仅比较前端传入的 `teamId`。
3. 普通成员可查询自己所属球队的允许信息，但不应看到或调用球队管理入口；非成员访问私有球队详情应被服务层拦截。
4. Admin 审核要求若依权限 `basket:teamAudit:list/query/audit`；审核通过还会核验队长成员存在、队长已认证并具有当前有效队长资格。
5. 已认证是加入长期球队的前置条件；候选球员查询也过滤未认证和受处罚限制玩家。
6. 平台账号不能作为长期队归属权限条件；它只在赛事平台阵容校验中生效。
7. 队长不能直接移除自己或其他队长；当前普通成员离队、队长移除仍由直接成员接口实现，最终审核/转会期限制另见 `07`。

## 9. 并发与幂等

| 场景 | 当前机制 | 结论 |
|---|---|---|
| 同名球队创建 | Service 预查询 + `uk_team_name_delete` | 有数据库兜底，需把重复键转为稳定业务错误 |
| 同人加入多队 | `TeamMembershipSupport` 写 `active_member_slot` + `uk_team_member_active_member_slot` | 支持一人一有效长期球队；迁移和历史脏数据需确认 |
| 队长创建球队 | 有效授权校验、未绑定授权校验、成员唯一约束、同事务写球队/成员/授权绑定 | 多赛季授权和重复创建需并发测试 |
| 8 人上限 | 当前人数判断、`current_member_count` 更新 | 主要是业务层校验，邀请/申请并发接受需验证不超员 |
| 球队审核 | `updateAuditStatusIfMatch` 条件更新 | 双管理员审核时只有一人应成功，审核记录和通知不得重复 |
| 成员离队/移除 | 状态变更、清空 active slot、重算 `current_member_count` | 当前直接变更，需与进行中报名及锁定阵容并发测试 |
| 队长绑定授权 | 授权侧有效槽位和队伍唯一槽位 | 需测试建队自动绑定与管理员手工绑定并发冲突 |

## 10. 已通过项

1. 需求文档记录：队长创建球队、后台审核球队、编辑球队信息、邀请用户、参加赛事通过。
2. 需求文档记录：队伍成员审核通过；未认证用户不能加入球队或参加赛事通过。
3. 需求文档记录：每个球队只要人数足够即可，不强制五个位置齐全通过。
4. 当前代码确认：创建球队固定保存 `game_terminal = GENERAL`，表定义将该字段标记为“已废弃-历史比赛终端，球队本体不绑定平台”。
5. 当前代码确认：创建球队会创建队长成员关系、更新球员当前球队、写安全日志，并绑定当前队长授权。
6. 当前代码确认：Admin 审核通过会写审核记录、站内消息、当前成员人数，并确保正式球队编号。

| P1 | 审核通过球队 | 尝试修改队名、Logo、简介、地区、公开状态 | 仅允许当前代码允许的字段；不影响赛事快照 | Team update/Logo API |
| P1 | 私有球队、普通成员、外部用户 | 查询详情、成员列表、候选人 | 仅拥有应有的可见性，不能越权管理或读取私有信息 | `/basket/team/{id}`、成员接口 |
| P1 | 已报名或锁定阵容成员 | 尝试成员更新、离队、移除、邀请/申请 | 验证报名/锁定限制是否完整生效 | 团队成员和报名/阵容 Service |
| P1 | PC/PS/XBOX 账号组合 | 创建/浏览/加入长期球队 | 平台账号不改变长期球队归属或可浏览范围 | Team 与 Platform API |
| P2 | 长期球队队长变更场景 | 执行/模拟转移 | 验证 `basket_team_captain_history`、授权和成员角色是否一致 | 队长历史/授权流程 |

## 12. 已知问题和风险

1. **P0：长期球队最少 5 人未在创建/审核阶段强制。** 当前 Admin 审核只校验有效队长、认证和队长资格；5–8 人校验位于赛事报名审核，不应误写为长期球队审核已实现。
2. **P0：长期成员直接离队/移除与最终审核规则存在差异。** 当前接口会直接改变成员状态，只在成员参与进行中报名时拦截；转会期、申请审核、锁定阵容等详见 `07`，不能视为已完全满足最终规则。
3. **P1：`current_member_count` 是冗余计数。** 成员申请/邀请/移除并发时需验证它始终与有效成员实际数量一致。
4. **P1：平台去绑定仍有遗留兼容字段/查询。** 表中保留 `game_terminal`，部分历史代码仍可能读取；必须坚持长期球队创建保存 `GENERAL`，赛事平台从赛季配置和球员账号取得。
5. **P1：赛事快照边界需持续验证。** 长期球队名称、Logo、队长、成员在赛后变更不应污染 `basket_team_season_profile`、赛季阵容和比赛展示。
6. **P2：长期球队队长变更历史表的完整业务闭环尚未在本模块确认。** 不能把存在表结构当成转移流程已经完成。

## 13. 下一步建议

### P0

1. 明确产品口径：长期球队审核是否必须达到 5 人；若必须，应在审核或报名前置流程中明确唯一责任点，避免审核通过后才发现不合格。
2. 用并发邀请/申请通过用例验证 8 人上限、`active_member_slot` 和 `current_member_count` 的一致性。
3. 对所有长期球队管理接口进行 owner 越权测试：普通员、其他队长、非成员和过期队长均不得管理。

### P1

1. 在 `07` 的退出/踢人流程中收敛直接成员变更接口：对转会期、报名中、阵容锁定、审核记录和通知建立统一规则。
2. 按 `09` 核对长期球队与赛事球队/阵容快照的写入和引用，确保历史比赛不受长期资料变更污染。
3. 清理或隔离任何把长期球队 `game_terminal` 当作报名平台的遗留回退逻辑。

### P2

1. 补齐长期球队队长交接的审计、授权迁移和成员角色联动测试。
2. 在管理后台增加长期球队与赛事球队的明显区分，避免运营人员直接修改长期数据影响赛事历史。
