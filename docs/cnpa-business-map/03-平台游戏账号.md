# 平台游戏账号

> 范围：正式球员在 PC、PS、Xbox 平台的游戏身份绑定、平台账号新增、游戏 ID 修改、审核、历史记录，以及赛事阵对目标平台账号的资格校验。球员认证主流程见 `02-球员档案与球员认证.md`。

## 1. 业务定位

平台游戏账号是“球员在某个平台上的游戏身份”，不是长期球队属性。一个认证球员可以在多个平台拥有游戏账号；球队本体不因平台拆分。赛事报名时，系统根据赛事开放的 `platformCode`，检查阵容内每名球员是否拥有该平台的有效游戏账号。

当前实现把平台账号分成三层：

1. `basket_player_platform_account`：当前生效的平台账号主数据。
2. `basket_player_platform_change_request`：新增平台或修改游戏 ID 的待审核流程。
3. `basket_player_platform_identity_history`：首次绑定和修改后的身份历史。

## 2. 最终业务规则

1. 一个认证球员可以绑定多个平台游戏账号。
2. 平台标准值为 `PC`、`PS`、`XBOX`；平台别名需要统一规范化后再保存和比较。
3. 同一个球员在同一个平台只能有一个有效游戏账号。
4. 同一个平台的规范化游戏 ID 不能被多个球员同时占用。
5. 新增平台账号和修改游戏 ID 都必须由本人提交申请，并经过后台审核；不能由前端直接写正式账号表。
6. 只有认证通过的球员才能管理平台游戏账号；未认证用户不能新增、修改或查询平台身份。
7. 平台账号用于赛事报名/阵容资格校验，但不改变长期球队归属；没有目标平台账号的球员不能进入该平台赛事阵容。
8. 平台账号变更必须记录原 ID、新 ID、平台、申请人、审核人、审核时间、审核结果和证明材料。
9. 驳回或待审核状态不能被当作有效参赛账号；只有 `ACTIVE` 账号可通过当前平台身份校验。

## 7. 状态机

### 当前平台账号

`PlatformAccountStatusEnum`：

```text
PENDING(0) ──审核通过──> ACTIVE(1)
    │                       │
    └────审核驳回──> REJECTED(3)
                            │
                            └──失效/停用──> INVALID(2)
```

认证审核通过创建首个平台账号时，代码将账号写为 `ACTIVE`，并标记为 `is_primary`；后续新增平台账号通过变更审核后写入 `ACTIVE`，不作为主平台。

### 平台变更申请

`PlatformChangeStatusEnum`：

```text
PENDING(0) ──通过──> APPROVED(1)
    │
    ├──驳回──> REJECTED(2)
    └──撤回──> WITHDRAWN(3)
```

变更类型为：

- `ADD_PLATFORM`：为已认证球员新增一个平台账号。
- `CHANGE_GAME_ID`：修改已有有效平台账号的游戏 ID。

### 身份历史

`PlatformIdentityHistoryChangeTypeEnum`：

- `INITIAL_BIND`：认证通过或迁移回填时的首次绑定。
- `UPDATE_GAME_ID`：平台账号审核通过后的游戏 ID 修改。

## 8. 权限规则

1. 只有已登录且球员认证状态为 `APPROVED` 的会员，才能调用新增平台、修改游戏 ID、查询平台账号和历史接口。
2. 修改游戏 ID 时，Service 必须确认目标 `platformAccountId` 属于当前球员；他人账号返回无权操作。
3. Admin 列表、详情、通过、驳回使用 `basket:playerPlatformChange:list/query/audit` 等权限；前端隐藏按钮不构成安全边界。
4. 赛事报名和阵容选择必须在后端按目标赛事的 `platformCode` 查询该球员账号，只有 `ACTIVE` 才能进入该平台阵容。
5. 没有当前平台账号的球员可以继续作为其他平台赛事候选人；平台本体不应限制长期球队浏览和归属。
6. 普通队员不能借助平台账号接口修改自己的赛事报名平台；报名平台属于赛事报名流程，由队长和报名 Service 校验。

## 9. 并发与幂等

| 场景 | 当前机制 | 结论 |
|---|---|---|
| 同一平台待审核申请重复提交 | `assertNoPendingChange(playerId, platform)` | 有 Service 层拦截；当前迁移脚本没有看到 pending slot 唯一键，需要并发测试 |
| 同平台游戏 ID冲突 | 生效账号查询 + 待审申请查询 + `uk_platform_normalized_active` | 有双层防护；唯一键的 `is_delete` 语义需要与失效账号复用策略确认 |
| 同一球员同一平台重复绑定 | `assertPlatformNotBound` | 主要是查询校验，当前表索引 `idx_platform_player` 非唯一，存在并发重复绑定风险 |
| 同一申请双管理员审核 | Admin `requirePendingRequest` + `updateStatusIfMatch(PENDING)` | 业务上具备条件更新，需验证账号写入和状态更新异常时事务回滚 |
| 首次绑定历史重复 | `initial_bind_slot` 唯一键 + `writeInitialBind` | 有幂等槽位；需验证重复迁移和重复审批 |
| 同一账号连续改号 | 每个平台只允许一个 pending change，原账号必须 `ACTIVE` | 有基础防护；需验证审批中原账号展示、再次提交和驳回后的重试 |
| 赛事阵容平台校验 | 查询 `platformCode` 下账号，判断 `PlatformIdentityStatusEnum.ACTIVE` | 逻辑明确；需验证账号审批与报名审核同时发生时的最终状态 |

## 10. 已通过项

1. 需求文档记录：一个用户可绑定多个平台账号，同一个平台只允许一个账号，用户测通过。
2. 当前代码确认：平台列表固定返回 `PC/PS/XBOX`，未绑定平台显示未绑定状态。
3. 当前代码确认：新增平台和修改游戏 ID 都要求已认证球员、规范化平台/游戏 ID、证明文件，并生成待审核申请。
4. 当前代码确认：赛事报名阵容候选人会检查当前目标平台是否存在有效 `ACTIVE` 平台身份；未绑定、待审核或驳回均不可选择。
5. 当前单元测试已覆盖：无冲突 ID 可用、生效账号冲突、待审核变更冲突、按球员查询首次绑定历史。

## 12. 已知问题和风险

1. **P0：同一球员同一平台的唯一性未完全下沉到数据库。** 当前主表存在按平台和游戏 ID的唯一键，但 `idx_platform_player` 是普通索引；并发提交不同游戏 ID可能绕过 Service 查询并产生两个平台账号。
2. **P0：平台账号迁移脚本必须执行。** `cnpa-batch3-migration.sql` 和 `cnpa-platform-identity-history-migration.sql` 不执行时，新增平台、历史记录和认证审批联调均不可靠。
3. **P1：唯一键名与实际列语义存在差异。** `uk_platform_normalized_active` 使用 `(platform, normalized_game_id, is_delete)`，没有把 `account_status` 纳入约束；失效账号是否允许同 ID重新绑定，需要明确产品口径。
4. **P1：`/eligibility` 当前不是赛事资格接口。** 它只根据球员 `player_status` 判断是否受限；具体赛事/平台资格由报名和阵容 Service 另行校验，前端不能把两个概念混为一谈。
5. **P1：长期球队与平台身份必须解耦。** `TeamRegistrationBusinessServiceImpl` 使用平台身份筛选报名阵容，但球队本体不能因此只属于某一平台。
6. **P2：当前没有解绑平台账号业务入口。** 如果未来需要转移或删除平台身份，必须定义对历史报名、已锁定阵容和比赛快照的影响，不能直接物理删除。
