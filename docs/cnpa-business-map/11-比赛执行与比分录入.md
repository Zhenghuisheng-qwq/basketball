# 11. 比赛执行与比分录入

## 1. 业务定位

本模块负责比赛从已排期进入执行、记录分节比分、提交比赛结果、确认/重开比分以及判负等后台兜底操作。它解决“比赛何时开始、何时结束、主客队谁获胜、每节和加时得分是多少、操作是否留痕”的问题。

正常生产链路仍应以“队长提交完整比赛数据 → 管理员审核 → 正式结果、统计和积分生效”为主。本模块的后台录分/比分确认是赛事运营兜底能力，不应被误认为已经替代第 12 点的完整数据审核与公开链路。

## 2. 最终业务规则

1. 比赛状态至少包括未开始/已排期、进行中、已结束、已取消、已延期；异常状态当前没有正式枚举时必须显式标为待扩展。
2. 仅授权后台人员可以开始、延期、取消、录入分节比分、提交比分、确认比分、重开比分和判负；每次状态或比分修改都必须记录操作者、时间、前后状态和原因。
3. 比分由分节比分汇总而来。常规时间同分必须进入加时，最终应能确定胜负；主客队结果和获胜方必须与总分一致。
4. 提交比分后比赛结束，比分处于待确认/待审核状态；确认后才可视为该兜底路径下的已确认比分。完整比赛数据、官方结果、统计、积分榜和排行榜仍需遵循后续审核/结算规则。
5. 已提交/已确认结果若要修改，必须按明确的驳回、重开或官方修订流程操作并填写原因；不能直接覆盖历史结果。
6. 判负时获胜球队必须是本场主队或客队，系统使用规则定义的判负比分和主客结果；弃赛/异常裁定属于特殊流程，不能与正常比分录入混淆。

## 3. 当前实现结论

### 代码确认

1. `MatchStatusEnum` 已实现 `DRAFT`、`SCHEDULED`、`RUNNING`、`FINISHED`、`POSTPONED`、`CANCELLED` 六种状态；没有独立的“异常”状态。
2. `BasketMatchScheduleController` / `BasketMatchScheduleServiceImpl` 已提供排期、开始、延期和取消接口。开始仅允许 `SCHEDULED → RUNNING`；延期允许已排期或进行中；取消允许草稿、已排期或已延期。
3. `BasketMatchScoreController` / `BasketMatchScoreServiceImpl` 已提供查询、保存分节、提交比分、确认比分、重开和判负接口。管理页可维护四节与加时节比分，并显示比赛/数据状态。
4. 保存分节比分会软删当前比赛的旧分节记录后重新插入，并写 `SCORE_SAVE` 状态日志；提交比分会汇总分节、统计加时次数、写主客总分/胜负/比赛结束状态，并把数据状态置为 `SUBMITTED`。
5. 确认比分只将 `basket_match.score_confirmed` 置为 1，并写 `SCORE_CONFIRM` 日志；它没有在该服务中把 `data_status` 改为 `CONFIRMED`、生成官方结果或触发积分榜/统计结算。
6. 重开比分要求数据状态为 `SUBMITTED` 且必须填写原因，会把数据状态设为 `REOPENED`、比赛状态从 `FINISHED` 回退为 `RUNNING` 并写状态日志。
7. 判负要求指定球队为本场主/客队，使用规则常量生成胜负比分与 `FORFEIT_WIN/FORFEIT_LOSS` 结果，并写为比赛结束、数据已提交状态。
8. 状态日志由 `BasketMatchValidationServiceImpl.writeStatusLog` 记录到 `basket_match_status_log`，包含操作前后状态、变更类型、原因、操作者、操作人名称和时间。

### 用户手测记录

本次仅完成静态代码和页面核对，未实际启动后台、未使用真实权限账号执行开始/录分/提交/确认/重开/判负，也未验证数据库中的日志与比分。因此下列功能均不能记为用户手测通过。

| --- | --- | --- |
| `basket_match` | 比赛主记录 | 保存主客总分、获胜队、加时数、判负队、比赛状态、数据状态、`score_confirmed`、结果状态和实际起止时间。 |

| `basket_match_official_result` | 官方正式结果 | 完整数据审核通过、争议/异常修订等后续链路生成；比分确认接口本身不创建。 |
| `basket_stat_change_record` | 数据状态变更留痕 | 完整数据确认/官方修订链路会写入；本模块的单纯分节保存主要依赖状态日志。 |
| `basket_match_data_submission` 及子表 | 完整比赛数据提交 | 第 12 点常规审核来源；与后台比分兜底形成两条需要明确衔接的链路。 |
| `basket_stage_standing`、赛季统计/排行表 | 结算产物 | 不是录分时直接更新，应在正式结果确认后的结算链路中更新。 |

## 5. 后端实现

1. 赛程执行接口在 `BasketMatchScheduleController`：列表、详情、排期、延期、取消、开始和删除由 `IBasketMatchScheduleService` 提供，状态更新使用期望来源状态的条件更新。
2. 录分接口在 `BasketMatchScoreController`：`GET /{matchId}/score`、`PUT /{matchId}/period-score`、`POST /score/submit`、`POST /score/confirm`、`POST /score/reopen`、`POST /forfeit`。
3. `BasketMatchScoreServiceImpl.savePeriodScores` 仅允许比赛状态为进行中或已结束，且数据状态可编辑；校验节次编号/类型后覆盖保存分节比分。
4. `submitScore` 读取所有分节并汇总总分和加时数。常规时间同分且没有加时会被拒绝；成功后调用 `applyFinalScore` 同步比赛主表和 `basket_match_team`，并写“提交比分、比赛结束”两条日志。
5. `applyFinalScore` 根据主客总分计算获胜长期球队 ID、主客 `WIN/LOSS` 或 `FORFEIT_WIN/FORFEIT_LOSS`，再更新比赛总分、加时数、判负方、比赛状态和数据状态。
6. `confirmScore`、`reopenScore`、内部 `rejectScore` 均有状态前置校验。注意 `rejectScore` 虽在服务接口中实现，但当前 `BasketMatchScoreController` 和分数管理页没有暴露对应 HTTP/UI 入口。
7. 完整数据审核通过后由第 12 点的 `BasketMatchDataSubmissionApplyServiceImpl` 同步正式统计、把数据状态置为 `CONFIRMED`、发布官方结果并触发结算。该链路是“影响积分榜”的正式入口。

## 6. 前端实现

1. 后台比分页为 `basketball-admin-ui/src/views/cnpa/competition/score/index.vue`，配套 API 为 `src/api/basket/matchScore.ts`。
2. 页面支持按比赛 ID 加载、维护四节默认比分、增加/删除加时节、保存、提交、确认、重开和判负；按钮使用 `basket:score:*` 权限指令控制显示。
3. 页面预览总分来自当前前端分节列表，提交前未见独立的“最终胜负/状态影响”预演组件；服务端是最终校验与写入依据。
4. 重开弹窗要求原因；判负页要求填写获胜球队 ID，但当前输入方式不是从主客球队名称中选择，误填风险需靠服务端归属校验和后续 UI 改进控制。
5. `schedule-manage` 页面也能进行部分比赛状态/比分维护，存在与专用比分页职责重叠；应明确哪个页面是正式运营入口，避免不同入口绕过相同的状态与审计规则。

## 7. 状态机

### 比赛状态

`DRAFT` → `SCHEDULED` → `RUNNING` → `FINISHED`

- `SCHEDULED → RUNNING`：后台开始比赛。
- `SCHEDULED/RUNNING → POSTPONED`：延期；`POSTPONED → SCHEDULED`：重新排期。
- `DRAFT/SCHEDULED/POSTPONED → CANCELLED`：取消。
- `RUNNING/FINISHED → FINISHED`：分节比分提交或判负会落为已结束；比分重开时当前实现允许 `FINISHED → RUNNING`。

异常状态尚未在 `MatchStatusEnum` 中实现，应视为待扩展而非现有功能。

### 比赛数据状态

`DRAFT/REOPENED/REJECTED` → `SUBMITTED` → `CONFIRMED`

- 后台提交比分或判负：写为 `SUBMITTED`。
- 后台确认比分：当前只置 `score_confirmed=1`，数据状态仍为 `SUBMITTED`。
- 完整比赛数据审核通过：第 12 点链路置 `CONFIRMED`，同时写正式数据、官方结果和结算。
- 重开比分：`SUBMITTED → REOPENED`，比赛回到进行中。

## 8. 权限规则

1. 比赛列表/详情、排期、开始、延期、取消、删除分别由 `basket:match:list/query/schedule/start/postpone/cancel/remove` 控制。
2. 分数查询、编辑、提交、确认、重开由 `basket:score:query/edit/submit/confirm/reopen` 控制；判负当前复用 `basket:score:edit`。
3. 前端权限指令仅改善界面，服务端 `@PreAuthorize` 才是最终约束；所有调用还要经过比赛/状态/主客归属校验。
4. 后台比分录入属于高风险兜底权限，应与普通赛程维护、完整数据审核、官方修订权限分离，并限制可操作的赛事范围。
5. 队长提交完整数据不使用本模块的后台分数权限，而由第 12 点 Web 接口按认证、赛事阵容和队长资格控制。

## 9. 并发与幂等

### 已实现保护

1. 开始、排期、延期、取消和部分数据状态变更使用带来源状态的 Mapper 条件更新，重复操作会失败而非盲目覆盖。
2. 确认比分要求数据状态仍为 `SUBMITTED`，重开也要求同一状态；在同一请求间能避免部分重复确认/重开。
3. 所有比分写入、判负和状态回退均标注事务；主表、主客队结果、分节数据和日志可在单次服务调用内回滚。

### 待验证或补强

1. 分节保存先软删再批量插入，没有以比赛行锁或数据版本控制保证并发编辑；两个管理员同时保存时可能发生最后写入覆盖。
2. `updateScores` 只按比赛 ID 更新，不校验期望比赛状态或数据版本；提交比分与判负/重开并发时需要用真实数据库专项验证。
3. `submitScore` 的状态日志把“操作前状态”固定记为 `RUNNING`；当已结束比赛处于可编辑数据状态后再次提交时，日志前状态可能不准确。
4. 需验证 `score_confirmed` 与 `data_status`、`result_status`、官方结果和结算之间的口径，避免“页面显示已确认”但官网结果/积分榜仍未正式生效的认知和数据不一致。

## 12. 已知问题和风险

### P0

1. **加时后仍可平局。** 当前提交逻辑仅拦截“无加时的同分”，存在加时节已录入但最终仍同分时仍可提交的可能；篮球比赛最终胜负规则应要求加时后继续加时直至分出胜负，或明确允许平局的赛事类型。
2. **比分确认并不等于正式结果确认。** `confirmScore` 仅更新 `score_confirmed`，未同步 `CONFIRMED` 数据状态、官方结果或积分结算；若运营人员把按钮理解为“结果正式生效”，会造成前台/榜单与后台认知不一致。
3. **异常状态缺失。** 需求列出异常为待扩展，当前状态机没有实现，异常比赛只能借助延期、取消、判负或后续特殊流程表达，无法形成统一闭环。

### P1

1. **并发覆盖风险。** 分节比分保存和总分写入缺少统一版本/CAS 校验；高并发或多管理员操作时可能出现最后写入覆盖和日志顺序不一致。
2. **日志前状态可能不准确。** 重复提交比分时日志使用固定 `RUNNING` 作为前状态，而实际比赛可能已经是 `FINISHED`。
3. **驳回路径未完整暴露。** 服务层存在 `rejectScore`，但没有对应 Controller/UI；产品流程中的“驳回比分”无法通过已发现入口使用。
4. **判负原因非强制。** 请求允许不填原因并使用默认说明；正式弃赛/判负裁定通常应强制填写依据、证据和裁定人。

### P2

1. 专用比分页以比赛 ID 与获胜球队 ID 输入为主，可用性和误操作防护较弱；应改为赛事筛选、比赛选择和主客队名称选择。
2. 当前缺少专门的比分/状态流转自动化测试文件，核心状态与并发场景需要补充单元和集成测试。

## 13. 下一步建议

### P0

1. 统一定义“比分提交、比分确认、完整数据审核、官方结果发布、积分结算”的状态与按钮文案；若比分确认不应生效，应明确标注为“确认待审核比分”，避免误用。
2. 修复最终平局校验：任何非允许平局的篮球比赛在提交时必须确保总分不同；若存在特定赛制允许平局，应由赛事规则显式配置。
3. 为分节保存、提交、确认、重开和判负增加比赛版本/CAS 或行锁策略，补齐并发冲突的业务错误和端到端测试。

### P1

1. 补齐比分驳回的 Controller、权限、页面、驳回原因和通知，或明确废弃服务接口并把流程统一到重开。
2. 让专用比分页使用赛事—阶段—比赛级联选择、主客名称展示和只读状态保护，减少 ID 录入错误。
3. 将判负/异常裁定迁移到独立的异常流程，强制原因、附件、权限和官方结果/结算重算审计。
4. 明确 `schedule-manage` 与比分页的职责，所有比分变更必须复用同一个服务层和审计策略。

### P2

1. 补充状态机、加时、判负、重开、日志和并发覆盖的自动化测试，并在联调环境验证与第 12、13 点统计链路的一致性。
2. 根据赛事规则扩展异常状态、实时计分、裁判确认、比赛记录导入和复核工作台。
