# 球员档案与球员认证

> 范围：会员成为正式球员前后的认证申请、材料、后台审核、永久球员档案、审核留痕与首个平台账号初始化。平台账号后续新增/修改的完整规则另见 `03-平台游戏账号.md`。

## 1. 业务定位

注册会员不自动成为正式球员。会员需在 Web 端提交球员认证，管理员审核通过后，系统写入或更新永久球员档案、生成永久球员编号，并将本次认证中的首个平台游戏账号写入有效平台账号表。认证状态是加入长期球队、接受邀请、申请加入和进入赛事阵容的重要前置条件。

当前实现由 Web 端负责“本人申请、材料、提交、撤回、查看当前状态”，Admin 端负责“开始审核、通过、驳回、查看审核记录”。

## 2. 最终业务规则

1. 注册成功仅为普通会员，不自动成为正式球员。
2. 会员必须主动发起球员认证；审核通过后才拥有永久球员档案和永久球员编号。
3. 未认证会员不能加入球队、接受邀请、申请加入球队或进入赛事报名阵容。
4. 认证申请应支持草稿、提交、审核中、通过、驳回、撤回；驳回后可以重新申请。
5. 审核材料、审核人、审核时间、审核意见和前后状态必须可追溯。
6. 篮球位置 `PG/SG/SF/PF/C` 作为球员资料与阵容展示字段，不得作为赛事报名“五个位置必须齐全”的阻断条件。
7. 一个会员对应一个永久球员档案；认证通过产生的玩家身份应在对应平台保持唯一。
8. 平台游戏资料的首次绑定和后续变更都应保留历史记录；后续变更需要走独立平台账号流程。

## 7. 状态机

### 认证申请状态

`PlayerCertStatusEnum`：

```text
DRAFT(0) ──提交──> SUBMITTED(1) ──开始审核──> REVIEWING(2)
   │                    │                              │
   │                    └────────撤回──────────────────┤
   └──编辑/补充材料                                  
REJECTED(4) <──驳回── REVIEWING/SUBMITTED ──通过──> APPROVED(3)
   │                                                      │
   └──重新提交：创建新的 SUBMITTED 申请                  └──不可再次申请

SUBMITTED/REVIEWING ──撤回──> CANCELLED(5)
```

### 档案与平台账号状态

| 对象 | 状态/字段 | 主要流转 |
|---|---|---|
| `basket_player_profile.certification_status` | 与认证结果同步 | 审核通过设为已认证；驳回时已有档案会更新为驳回状态 |
| `basket_player_profile.player_no` | 永久编号 | 审核通过首次生成；已有档案缺失编号时补齐 |
| `basket_player_platform_account.account_status` | `0` 待审核、`1` 生效、`2` 失效、`3` 驳回 | 认证通过创建首个有效账号；后续变更走平台账号审核 |
| `basket_player_platform_change_request.request_status` | 待审核、通过、驳回、撤回 | 新增平台/修改游戏 ID 的独立流程 |

## 8. 权限规则

1. Web 认证接口依赖登录会员上下文；查询、草稿、材料、提交和撤回均应限制为本人当前申请，代码使用 `UserContext` 获取当前会员。
2. Admin 审核接口以若依权限注解限制：`basket:playerCert:list`、`query`、`audit`；平台变更审核另有 `basket:playerPlatformChange:*` 权限。
3. 审核通过前，球队候选、邀请、加入申请与赛事阵容相关业务应检查 `BasketPlayerProfile.certificationStatus == APPROVED`；未认证用户不能依靠前端隐藏绕过。
4. 审核通过会校验同平台标准化游戏 ID 是否已被有效账号占用；这项校验在 Admin Service，而不是仅靠 UI。
5. 审核记录仅允许管理员查询；会员可查看本人当前认证状态和通知，不应读取其他会员的申请、材料或审核意见。

## 9. 并发与幂等

| 场景 | 当前机制 | 结论 |
|---|---|---|
| 认证开始审核、通过、驳回 | `updateStatusIfMatch` 以原状态条件更新，并要求单行成功 | 可避免第二位管理员在状态已变化后重复成功；需双管理员实测 |
| 提交与撤回竞态 | Web Service 对可提交/可撤回状态做条件更新 | 已有基础保护；需验证提交与审核同时到达时的结果 |
| 驳回后重新提交 | `submitFromRejected` 创建新申请而非覆盖历史申请 | 保留版本历史；需验证重复点击不会创建多条有效申请 |
| 永久档案 | `basket_player_profile.member_id` 的唯一归属（以当前 DDL/Mapper 为准）与 `upsertProfile` | 一个会员应只拥有一份永久档案；并发首次审批需验证唯一键异常处理 |
| 首个平台账号 | 审批前 `countActiveByPlatformAndNormalized` 校验，迁移表有 `uk_platform_normalized_active` | Service 校验加数据库唯一键双层防重；需要已执行 migration |
| 平台账号历史 | `initial_bind_slot` 唯一键 | 防止首次绑定历史重复写入 |

## 12. 已知问题和风险

1. **P0：平台账号相关表来自迁移脚本。** 若 `cnpa-batch3-migration.sql` 或平台身份历史迁移未执行，认证审批创建首个平台账号/历史会失败或无法联调。
2. **P1：永久档案与平台账号存在历史字段重叠。** `basket_player_profile` 同时保留 `game_terminal/game_account`，而独立平台账号表支持多平台；必须明确前者是兼容/展示快照，后者才是多平台资格权威数据。
3. **P1：认证申请中的 `position_code` 为必填字段。** 当前最终规则只明确“不作为报名五位置齐全校验”；仍应测试其不会被下游错误用作报名人数或位置阻断条件。
4. **P1：Web 端存在 `player-verification` 与 `player-identity` 两组入口。** 当前需在联调时确认是否为兼容路由、重复页面或仍残留 Mock，避免状态来源分叉。
5. **P1：撤回与审核并发未见集成测试报告。** 虽有状态条件更新，仍需验证通知、审核日志和安全日志在失败分支不会重复写入。
6. **P2：KYC/身份证/手机号并非当前实现范围。** 不能将认证材料误描述为实名核验，也不能在文档中虚构敏感字段能力。
