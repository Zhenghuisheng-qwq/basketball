# 19. 前台首页、赛事页与数据页展示

> 本文件对应 `核心业务/核心实现.md` 中第 22 项“首页、赛事页、数据页展示”。结论来自 2026 年 7 月 31 日对官网前端、公开 Controller、Service 与实体查询的静态核查；未启动应用、未使用真实公开数据，也未执行浏览器或数据库联调。因此“代码确认”不等同于用户手测通过。

## 1. 业务定位

官网公开展示模块把已对外公开的赛事、赛季、赛程、赛果、公告和统计数据提供给未登录访客。它应保证展示内容真实、查询范围明确、草稿和审核中数据不泄露，并让历史赛季按当时的统计快照可追溯。

模块覆盖四类页面能力：

1. 首页：运营 Banner、近期赛程/赛果、最新公告、榜单及赛季摘要。
2. 赛事页：按公开赛季查询赛程、赛果、积分榜、球队、赛季领袖和比赛详情。
3. 数据页：按公开赛季读取球队/球员排行与赛季汇总，不使用前端 Mock 作为业务数据来源。
4. 球队页：展示球队已公开且已审核通过的历史赛果及关联赛季数据。

## 2. 最终业务规则

1. 首页应展示当前公开赛事或赛季对应的 Banner、近期赛程和已发布公告。
2. 赛事页必须能展示公开赛季的赛程和赛果；草稿、未发布或不属于公开赛季的比赛不得展示。
3. 数据页的球队统计、球员统计和排行榜必须来自实际后端统计/排行数据，不能以 Mock 代替。
4. 已结束比赛仅在比赛数据审核状态为 `CONFIRMED` 后，才可作为公开赛果、公开比赛明细和公开统计的来源。
5. 正在审核、驳回或尚未提交的数据，不得在首页近期赛果、赛事赛果、比赛详情、球队赛果或数据页中泄露比分、统计与排行增量。
6. 历史赛季/历史排行应使用统计快照、排名快照或业务快照，不能以当前可变资料覆盖当时结果。
7. 球队页应能展示球队相关公开比赛，并支持按赛季缩小范围。
8. 公开查询维度需覆盖 `eventId`、`seasonId`、`platformCode`；任一筛选条件均须由服务端校验其公开范围。
9. 公告仅能展示已发布、到达发布时间且未下线的内容。
10. 所有公开接口都应显式豁免登录，但只能输出已经满足公开条件的数据。

## 7. 状态机

公开展示并不改变业务状态，只读取满足下列状态组合的数据：

| 对象 | 字段/状态 | 可公开条件 | 当前实现结论 |
| --- | --- | --- | --- |
| 赛事 | `publicStatus` | 所属赛事公开 | `requirePublicSeason()` 会同时校验 |
| 赛季 | `publicStatus`、赛季状态 | 赛季公开，当前赛季可被首页/数据中心自动选择 | 已实现基础校验 |
| 赛程发布 | `publishStatus` / 兼容 `publicStatus` | 已发布，或旧口径已公开 | 首页未来赛程和赛事赛程已使用 |
| 比赛进度 | `SCHEDULED`、进行中、`FINISHED` 等 | 赛程可读；赛果必须已结束 | 赛程接口未区分未开始与已结束 |
| 数据审核 | `dataStatus`：提交/审核中/驳回/`CONFIRMED` | 赛果、比赛统计、排行增量仅 `CONFIRMED` | 赛果页、球队赛果和统计明细正确；首页近期赛果遗漏 |
| 公告 | 草稿/已发布/下线 | `PUBLISHED`、`publishTime <= now`、未到下线时间 | 公告公开服务已过滤 |
| 排行快照 | `snapshotDate` | 读取该赛季及排行类型最新可用快照 | 已实现，但需验证快照生成时点 |

推荐公开状态流转：赛程草稿 -> 已发布 -> 可展示赛程；比赛结束 -> 数据提交 -> 审核中 -> `CONFIRMED` -> 可展示赛果/详情统计/累计统计/排行；撤销公开或下线后应即时从公开查询消失。

## 8. 权限规则

1. 公开首页、赛事、数据、球队和公告 Controller 使用 `@NoLoginRequest`，访客可以读取满足公开条件的数据。
2. 公开不代表无范围校验：赛季查询应先经过 `BasketPublicSupport.requirePublicSeason()`；球队查询应经过公开球队校验；比赛详情应先确认比赛本身及其赛季可公开。
3. 公共接口不提供写操作；赛事配置、赛程发布、比赛数据审核、统计计算、Banner 与公告维护仍只能由后台具备相应权限的人员完成。
4. `eventId`、`seasonId`、`platformCode` 等传参必须在服务端关联校验，不能仅依赖前端下拉项。当前主要覆盖 `seasonId`，另外两个维度需要补齐。
5. 对已结束但数据审核中的比赛，应至少隐藏比分、胜负与明细统计；仅隐藏球队/球员技术统计不足以满足“审核中比赛数据不展示”。

## 9. 并发与幂等

本模块以只读公开查询为主，没有独立的写入幂等键。展示正确性依赖上游流程的事务和状态原子性：

1. 赛程发布、比赛数据审核、统计重算和排行快照生成必须在事务边界内完成，避免前台读到“比赛已确认、统计尚未累计”或“排行快照半生成”的中间态。
2. 公开查询应在同一口径下判断 `publishStatus/publicStatus`、`matchStatus`、`dataStatus` 与赛季公开状态，避免不同接口显示不一致。
3. 排行按 `snapshotDate` 一次取最新日期后再查同日记录，能避免单次列表混入多个快照日期；仍需保证快照生成任务具备去重、完整标识和失败恢复。
4. 首页聚合由多个查询组成，未见跨查询一致性快照。高频写入时可能出现 Banner、近期赛果、榜单和摘要短暂不一致，可接受与否需产品定义。
5. `BasketPublicTeamServiceImpl.pageMatches()` 先做数据库分页再剔除非公开赛季记录，且未回写总数；这不是写入并发问题，但会造成公开分页空页或总数不准。

## 10. 已通过项

以下为**代码静态确认**，不是用户手测记录：

1. 首页、赛事页、数据页和球队比赛页的主要数据请求均指向官网公开 API，不以页面 Mock 作为正常业务数据来源。
2. 公开赛季校验同时考虑赛季及所属赛事的公开状态。
3. 赛事赛果分页、球队比赛分页、公开比赛球队统计和球员统计均包含 `FINISHED + CONFIRMED` 条件。
4. 公告公开查询会过滤未发布、未到发布时间和已下线内容，并按置顶/重要/发布时间排序。
5. 数据中心排行榜以 `basket_team_rank`、`basket_player_rank` 的最新 `snapshotDate` 为读取口径。
6. 季后赛对阵图组件明确保持空态，不以 Mock 对阵图冒充真实赛程。

4. 比赛详情：直接访问审核中比赛 ID，检查接口和页面是否暴露比分、胜负、状态、球队统计或球员统计。
5. 数据页：以数据库已确认比赛、赛季累计表和排行榜快照对账，核验积分、胜负、均值、排行和 `snapshotDate`。
6. 历史赛季：修改球队名称、Logo、球员昵称/头像后检查历史页面是否仍满足“使用历史快照”的产品期望。
7. 球队比赛：验证有无未来赛程展示需求；验证传入 `seasonId` 的后端筛选、前端赛季切换、总数和第 2 页数据。
8. 公告：验证置顶、重要、发布时间、下线时间、详情、前后篇和首页最新公告的一致性。
9. Banner：验证当前赛事/赛季配置变更后首页主视觉是否随之改变，而不是始终使用静态图。
10. 请求维度：验证 `eventId`、`seasonId`、`platformCode` 的组合查询、越权/非公开参数、空结果与跨赛事数据隔离；当前接口预计不完整。
11. 浏览器 Network 与全局前端检索：确认加载、错误、空态、超 100/200 条数据和所有公开页均无遗留 Mock 展示。

## 12. 已知问题和风险

1. **P0 — 首页审核中赛果泄露：** `BasketPublicHomeServiceImpl.listRecentMatches()` 的已结束比赛分支没有 `dataStatus=CONFIRMED` 限制。只要比赛已发布/公开且状态为 `FINISHED`，审核中、驳回或其他未确认数据可能进入首页近期比赛。
2. **P0 — 公开比赛详情比分口径过宽：** 详情服务仅在统计明细层限制 `FINISHED + CONFIRMED`；若已结束比赛已公开但尚未确认，比分/状态仍可能返回。需要按最终公开规则统一限制或脱敏。
3. **P1 — 查询维度不完整：** 公开赛程与赛果 API 以 `seasonId` 为主，未形成 `eventId / seasonId / platformCode` 的统一服务端过滤能力，无法完整满足需求第 12 条。
4. **P1 — 赛事赛程与赛果职责可能混淆：** 赛程查询没有显式排除 `FINISHED`，赛事赛程页可能同时出现已经结束的比赛；需明确产品定义并在 Service 层固定条件。
5. **P1 — 首页 Banner 动态性不足：** 后端有 Banner 数据接口，但首页仍引用静态 `home_top.png`；“当前赛事 Banner”是否真正由赛事/赛季配置驱动尚未证明。
6. **P1 — 历史快照不完全：** 排行数值使用快照，但队名、Logo、球员昵称/头像从当前实体回读。若业务要求视觉资料也历史可追溯，需在快照中保存展示字段或提供版本关联。
7. **P1 — 前端字段准确性：** 数据页存在平均值乘场次等前端派生字段，且个别球员字段使用 `0` 或 `--` 占位。数据源真实不等于每个展示字段真实，应与接口字段逐项对账。
8. **P2 — 前端加载上限与本地过滤：** 赛事页固定拉取 100 条，球队页固定拉取 200 条且未传 `seasonId`，赛季数据量增长时会出现截断、额外传输或前端筛选不准。
9. **P2 — 球队比赛分页总数：** 后端数据库分页后再过滤非公开赛季，`total` 未随过滤结果调整，可能造成公开页总数与实际记录不一致。
10. **P2 — 季后赛对阵图缺口：** 组件无公开对阵图接口，仅显示空状态；不是 Mock 风险，但会导致阶段展示不完整。

## 13. 下一步建议

1. 优先修复首页近期赛果和公开比赛详情：统一采用“赛季公开 + 赛程已发布 + `FINISHED + CONFIRMED`”的公共谓词，并为审核中比赛做回归测试。
2. 明确赛程与赛果的产品边界：赛程列表只展示未开始/进行中，赛果列表只展示已结束且已确认；如需“全部比赛”，新增显式接口或状态筛选参数。
3. 为公共列表统一补齐并服务端验证 `eventId`、`seasonId`、`platformCode`，同时确保三者关联关系合法且公开。
4. 将首页主 Banner 改为以当前公开赛事/赛季的运营配置为唯一来源，静态图仅作为无配置时的降级资源。
5. 用已确认比赛作为唯一统计输入，建立统计回算、排行快照生成和公开读取的一体化一致性回归用例。
6. 若历史展示需完整复盘，为排行/赛季历史快照补充球队名称、Logo、球员展示名和头像等冗余字段；否则在产品文案中明确展示当前资料。
7. 改造前端分页：赛事页和球队页交给服务端按条件分页，传递 `seasonId`，删除固定 100/200 条全量拉取。
8. 完成第 18 项并发幂等文档与相应实现核查后，再为本模块补充“审核确认—统计—排行—首页”链路的并发一致性测试。
