# 12. 比赛数据提交、审核与公开

## 1. 业务定位

本模块把“比赛结束后的原始填报”与“对外生效的正式结果”分离。正常路径由参赛球队队长在 Web 端提交双方完整比赛数据，管理员在后台审核；审核通过后才同步比分、分节、球队单场数据、球员单场数据、官方结果和后续积分/统计。管理员代录或修正属于兜底路径，不应替代队长提交—审核的常规流程。

本文仅覆盖 M01～M05 的比赛数据提交、审核与公开闭环；M06 数据争议、M07 弃赛/异常属于后续轮次，不混入本篇已实现范围。

## 2. 最终业务规则

1. 仅已认证、属于本场参赛球队且拥有当前赛事队长资格的成员可以提交；普通队员、非本场球队成员均不得提交。
2. 一场比赛只需要一方队长提交。首份有效提交进入审核中后，另一方和提交方都不能重复创建有效提交。
3. 提交仅允许在比赛结束后进行；提交内容应包含最终比分、分节比分、双方球队统计、球员统计及至少一份完整比赛结算截图等材料。
4. 审核中数据不得编辑；审核驳回后只能由原提交球队队长修订并重新提交，且必须生成新版本、关联上一版本，保留历史。
5. 管理员审核通过前，提交数据不是正式数据，也不得作为官网比赛结果、统计、积分榜或排行榜的依据。
6. 审核通过后，应在同一事务链路中写入正式比赛数据、确认比分和胜负、生成/更新官方结果，并触发统计结算；任何一步失败都不得留下“已审核通过但正式数据不完整”的状态。
7. 官网比赛结果只展示已确认（`CONFIRMED`）的正式数据；已排期赛程可按赛程发布状态展示，但草稿/审核中/驳回的提交内容不得公开。
8. 审核驳回必须填写原因；提交、重提、通过、驳回、正式数据生效都应可追溯到提交版本、操作者、时间和备注。

## 3. 当前实现结论

### 代码确认

1. Web 端 `BasketPlayerMatchDataController` 已提供“我的比赛、提交详情、提交、状态查询、驳回后详情、重新提交”接口；`PlayerMatchDataServiceImpl` 会锁定比赛行并校验比赛已结束、用户已认证、用户属于参赛球队且具备赛事队长资格。

6. 公开比赛结果接口 `BasketPublicMatchServiceImpl.pageResult` 明确要求比赛已结束且 `data_status=CONFIRMED`；公开的球队/球员单场统计也过滤为已确认数据。

## 5. 后端实现

1. Web 接口在 `basketball-web`：`BasketPlayerMatchDataController` 调用 `PlayerMatchDataServiceImpl`，负责身份、赛事名单、队长资格、比赛结束、提交/重提状态和提交数据构造。
2. 提交服务以 `selectByIdForUpdate` 锁定比赛，首次提交校验不存在有效提交；重提校验前一版本已驳回且提交人仍是原提交球队的赛事队长。提交后写入主表、分节、球队统计、球员统计、材料和 `SUBMIT/RESUBMIT` 审核日志，并将比赛数据状态置为已提交。
3. `BasketMatchDataSubmissionValidationServiceImpl` 校验分节总分与最终比分、双方球队完整性、球员归属与重复、技术统计非负、命中/出手关系、理论得分、球员汇总与球队汇总一致性，以及存在有效结算截图。
4. Admin 审核服务对提交和比赛分别加锁；通过前再次校验比赛已结束、提交仍为待审、没有其他有效提交以及全部子表数据。状态更新使用“期望状态 + 期望审核状态”的条件更新，失败即提示已被其他管理员处理。
5. 通过审核后，应用服务同步正式分节、正式球队/球员统计、比赛比分、胜负和主客队结果，写比赛状态日志与统计变更记录，发布 `basket_match_official_result`，再由 `BasketMatchStatSyncServiceImpl` 的同步记录决定是否调用 `BasketDataSettlementServiceImpl.rebuildMatch`。
6. 驳回要求非空原因，更新提交为 `REJECTED`、比赛数据状态为驳回，写审核日志并通知原提交队长；当前正式数据不会由驳回操作写入。
7. 管理员数据修正能力存在于 `BasketMatchOfficialDataCorrectionServiceImpl`，当前主要被争议/异常服务调用；它是后续特殊流程，不应绕开常规审核审计后直接作为日常录分入口。

4. 后台审核按钮还受 `v-hasPermi` 控制；即使前端显示按钮，服务端仍以接口权限和提交状态为最终准入条件。

## 7. 状态机

### 提交版本状态

`DRAFT` → `SUBMITTED（审核中）` → `APPROVED（审核通过）`

`SUBMITTED（审核中）` → `REJECTED（驳回）` → `新版本 SUBMITTED（审核中）`

补充终态：旧版本可为 `SUPERSEDED`，取消场景可为 `CANCELLED`。常规审核接口只允许 `SUBMITTED + PENDING` 转为通过或驳回。

### 比赛数据状态

`DRAFT` → `SUBMITTED` → `CONFIRMED`；审核驳回时转为 `REJECTED`；后续特殊修订可进入 `REOPENED`。本篇的正式公开门槛是 `CONFIRMED`，不是“存在提交记录”。

### 官方公开结果

审核通过 → 正式数据同步 → 生成/替换当前 `basket_match_official_result`（公开）→ 幂等触发单场结算。任何数据争议、异常弃赛和官方修正后的替换规则属于后续专项流程。

## 8. 权限规则

1. Web 提交者必须通过已认证球员检查，属于比赛所在赛事阵容，并是主队或客队的已审核报名队长；仅查看提交状态也要求属于本场参赛球队。
2. 提交时服务端从当前登录人推导成员、球员和队长球队，不能相信前端传入的提交人、球队或比赛归属。
3. Admin 待审列表需要 `basket:matchAudit:list`，详情/版本需要 `basket:matchAudit:query`，审核通过和驳回分别需要 `basket:matchAudit:approve`、`basket:matchAudit:reject`。
4. 管理员代录/官方修正必须限定为显式的后台能力并留下修订来源、理由和操作者；不能让普通前台接口以管理员身份绕过审核。
5. 官网接口为免登录公开接口，但结果和统计必须由服务端过滤为已公开赛季、公开比赛和已确认数据；提交原文、审核意见和驳回原因不应暴露给无关用户。

## 9. 并发与幂等

### 已实现保护

1. 提交时锁定比赛行，审核时锁定提交行和比赛行；数据库唯一键限制每场只能有一条审核中或已通过的有效提交。
2. 重提采用版本号和前版本关联，正常提交会拒绝有效提交已存在的比赛；审核中不支持通过前台接口编辑。
3. 审核通过/驳回使用条件更新，仅当提交仍为 `SUBMITTED + PENDING` 才能成功，避免两个管理员重复审核。
4. 审核通过、审核日志、正式数据同步、官方结果发布和结算调用处于事务链路；统计同步通过 `basket_stat_sync_record` 的幂等键避免重复执行同一官方结果同步类型。

### 待验证或补强

1. 需要在已执行 migration 的真实 MySQL 中验证并发首次提交：应用层查询、行锁与 `uk_match_active_submission` 冲突时是否能得到统一、可识别的业务错误，而不是裸 SQL 异常。
2. 需要验证审核通过后结算重算失败时整笔事务是否回滚，包括提交状态、正式比分、官方结果、统计同步记录和通知。
3. `basket_match_data_audit` 扩展列若未迁移，提交/审核日志写入将无法满足追溯要求；部署顺序必须先数据库、再服务端、再前端。
4. 官方结果替换、官方纠错、争议和异常流程都可能触发重算，必须验证不同 `syncType` 的幂等键不会遗漏必要重算，也不会双重累计。

### P1

1. **长期 ID 与赛事快照并存。** 提交主表和正式统计主要保存长期 `teamId/playerId`，而比赛已具备 EventTeam 快照；需要确认提交时所有名单/队长资格都以赛事阵容快照校验，避免长期资料变更或跨赛事混入。
2. **官网赛程可见性兼容分支。** 公开赛程查询兼容“已发布”或历史 `publish_status=0 && public_status=1` 的比赛。结果页另加 `CONFIRMED` 过滤；需验证旧数据兼容不会意外公开未审核的比赛数据。
3. **官方结果修订号需专项回归。** 审核通过、争议修订和异常判定都会调用官方结果发布。应验证当前结果替换、历史结果保留、修订号递增和统计重算口径。

2. 建立端到端验收脚本：完成比赛 → 一方队长提交 → 管理员通过/驳回 → 重提 → 官网结果与统计核验，并覆盖事务失败回滚与重复请求。
3. 为提交、审核、正式同步、官方结果发布和结算重算增加跨表一致性巡检，发现“已通过但未确认/未结算”时给出可定位的修复任务而不是静默不一致。

### P1

1. 把赛事 EventTeam/EventPlayer 快照、队长授权和比赛名单作为提交与审核的唯一资格来源，并补充跨赛季/跨平台/长期资料变更回归用例。
2. 为公开接口加入覆盖赛程、结果、详情和统计的安全回归，严格验证 `CONFIRMED`、比赛公开状态、赛事公开状态与官方结果状态。
3. 为管理员代录、官方修正、争议和异常建立互斥状态及统一审计/结算入口，确保任何正式结果变更都能重算且可追溯。

### P2

1. 完善审核页的差异对比、风险提示、材料预览、版本切换和大数据量分页体验。
2. 扩展单元/集成测试到并发提交、并发审核、数据库唯一键冲突、统计幂等、官方结果版本与缓存失效场景。
