# 15. 处罚管理

## 1. 业务定位

处罚管理用于对球员、长期球队、赛事球队或账号作出纪律处理，并将处理结果转换为报名、转会、队长资格、比赛名单、参赛资格和积分等业务限制。它既是纪律档案的一部分，也是赛事流程中的实时校验来源。

本模块的核心闭环应为：创建处罚事实 → 审核/生效 → 生成当前限制 → 在报名、阵容、转会等入口拦截 → 记录处罚及消耗/撤销留痕 → 在球员或球队档案中可追溯。

## 2. 最终业务规则

1. 处罚至少覆盖警告、禁赛、取消资格，以及后台可配置的其他处罚；每条处罚必须明确对象、原因、措施、生效范围和有效期。
2. 处罚对象可为球员、长期球队、赛事球队或账号；球员处罚进入球员档案，球队处罚进入球队档案。
3. 警告保留档案和操作日志，通常不应产生业务拦截；禁赛期间球员不得进入比赛阵容，并应按实际受影响的比赛消耗场次。
4. 取消资格应明确影响范围：至少应阻断相应赛季的报名、阵容或参赛关系；球队停赛还应阻断球队参赛。
5. 处罚生效、撤销、到期、禁赛场次消耗及积分扣减均必须可追溯；撤销应恢复未被其他有效处罚覆盖的资格。
6. 如处罚需要公开说明，应可关联公告，并能在处罚详情或公告详情相互定位。
7. 处罚审核、状态更新、限制快照写入、积分调整和操作日志应处于同一事务，且状态流转与重复提交必须受控。

## 3. 当前实现结论

### 代码确认

1. 后台已有处罚记录创建、查询、生效、撤销和禁赛场次消耗接口；创建后状态为 `DRAFT`，生效后为 `ACTIVE`，撤销后为 `REVOKED`。
2. 已实现的措施编码包括 `WARNING`、按场禁赛、按日期禁赛、扣分、报名禁令、转会禁令、比赛资格取消、赛事取消资格、球队停赛、球员资格停赛和队长禁令。
3. 处罚生效时会向 `basket_discipline_restriction` 写入当前限制快照；报名、Open 报名、阵容变和比赛名单保存已接入部分限制校验。
4. 球员永久档案按 `playerId` 查询处罚记录，球队永久档案按 `teamId` 查询处罚记录，处罚已能进入这两类档案接口返回值。
5. 创建、生效、撤销会写统一业务审计；控制器也使用 RuoYi `@Log` 记录新增和更新操作。禁赛消耗另写专用消耗日志。
6. 扣分处罚在生效时按处罚记录生成一条带幂等键的 `basket_point_adjustment`，可被积分榜调整链路使用。
7. 当前代码存在限制快照覆盖、有效期未参与限制查询、禁赛消耗与名单拦截相冲突等风险，尚不能视为处罚闭环已完整验收。

### 用户手测记录

本次仅完成静态代码、页面和 SQL 核对；未实际创建警告、禁赛或取消资格处罚，未检查数据库落库、前后端提示、档案展示、报名/阵容拦截、扣分结果和审计页面。因此没有可标记为人工验收通过的处罚功能。

### 待联调/待测试

需以具有不同权限的后台账号和真实赛季、球队、球员数据，分别验证警告、禁赛、取消资格、球队停赛、撤销、到期、扣分和公告关联的完整链路。

## 4. 相关数据库表

| 表/对象 | 用途 | 关键内容 |
| --- | --- | --- |
| `basket_discipline_record` | 处罚主记录 | 对象类型与 ID、赛季/比赛、处罚措施、原因、禁赛/扣分、状态、有效期、决定/审核/撤销信息、公告 ID、幂等键。 |
| `basket_discipline_restriction` | 当前限制快照 | 报名、转会、队长、名单、参赛许可和剩余禁赛场次；关联当前生效处罚。 |
| `basket_discipline_suspension_log` | 禁赛场次消耗 | 处罚、比赛、会员、消耗数量和按“比赛 + 会员”生成的幂等键。 |
| `basket_point_adjustment` | 积分扣减 | 赛季、球队、关联处罚、负向调整积分、原因、操作人和幂等键。 |
| `basket_business_audit` / `basket_business_audit_field` | 统一业务审计 | `DISCIPLINE` 模块的创建、生效、撤销摘要、原因和状态字段变化。 |
| `sys_oper_log` | 框架操作日志 | 处罚新增、生效、撤销和手工消耗接口的控制器操作记录。 |

`basket_discipline_record` 的基础建表位于 `sql/basketball.sql`，限制快照、禁赛消耗、积分调整及扩展字段由 `docs/sql/cnpa-batch6-migration.sql` 增加。

## 5. 后端实现

| 入口 | 权限 | 当前行为 |
| --- | --- | --- |
| `GET /basket/discipline/list` | `basket:discipline:list` | 按赛季、赛事、球队、球员、会员、对象类型、状态、措施和关键词查询。 |
| `GET /basket/discipline/{id}` | `basket:discipline:query` | 返回处罚详情及关联赛季、球队、球员基础信息。 |
| `POST /basket/discipline` | `basket:discipline:add` | 校验标题、原因、处罚类型/措施和处罚对象，创建草稿并写创建审计。 |
| `POST /basket/discipline/{id}/activate` | `basket:discipline:activate` | 条件更新为生效，写限制快照、按需写扣分记录和生效审计。 |
| `POST /basket/discipline/{id}/revoke` | `basket:discipline:revoke` | 仅允许撤销生效记录，停用限制快照并写撤销审计。 |
| `POST /basket/discipline/consumeSuspension` | `basket:discipline:consume` | 根据比赛和会员消耗一场禁赛并写专用消耗日志。 |

主要实现位于 `BasketDisciplineServiceImpl`、`BasketDisciplineRestrictionSupport` 和 `BasketDisciplineController`：

1. `MATCH_SUSPENSION`、`MATCH_ELIGIBILITY_CANCEL` 会将 `allow_lineup` 置为不允许；前者同时写入剩余禁赛场次。
2. `DATE_RANGE_SUSPENSION`、`EVENT_DISQUALIFICATION`、`PLAYER_QUALIFICATION_SUSPENSION` 会将 `allow_lineup` 和 `allow_participation` 置为不允许。
3. `REGISTRATION_BAN`、`TRANSFER_BAN`、`CAPTAIN_BAN` 分别控制对应资格；`TEAM_SUSPENSION` 控制报名和参赛许可；`WARNING` 与单纯 `POINT_DEDUCTION` 不写限制标记。
4. 赛事报名审核会检查长期球队、球员和账号的报名限制；Open 报名审核检查球员和账号；转会/自由人加入检查转会限制；队长转让检查队长限制；保存比赛名单检查球员/账号名单限制。

## 6. 前端实现

后台页面位于 `basketball-admin-ui/src/views/cnpa/discipline/penalty/index.vue`，API 位于 `basketball-admin-ui/src/api/basket/discipline.ts`。

1. 页面支持按赛季、状态和关键词查询，展示处罚编号、对象类型、措施、状态、剩余禁赛、扣分和生效时间。
2. 页面支持创建、查看详情、将草稿生效和撤销生效处罚；措施下拉项与后端枚举基本一致。
3. 新建表单仅输入赛季 ID、球员 ID、球队 ID 等原始 ID；未提供账号 ID、赛事球队 ID、比赛 ID、有效期、处罚内容、公告关联和幂等键输入。
4. 页面仅将 `DRAFT` 显示为可生效，没有处罚审核通过/驳回、到期完成、禁赛消耗日志、关联公告跳转或限制快照查看功能。
5. 永久球员档案和永久球队档案页面可消费档案接口返回的处罚记录；本次未做浏览器手测确认其实际展示效果。

## 7. 状态机

当前代码实际使用的状态流转如下：

```text
创建
DRAFT --生效--> ACTIVE --撤销--> REVOKED

枚举中还定义 PENDING、APPROVED、COMPLETED、REJECTED、CANCELLED，
服务允许 PENDING / APPROVED 直接生效，但当前未发现创建后进入这些状态的接口或后台页面。
```

禁赛场次的辅助流转：

```text
ACTIVE 且剩余场次 N
  --比赛名单确认触发消耗--> N - 1
  --剩余场次归零且名单限制为 0--> 停用当前限制快照
```

当前未发现根据 `effective_end_time` 自动停用限制快照、将处罚置为 `COMPLETED` 或恢复被覆盖限制的定时/事务处理。

## 8. 权限规则

1. 控制器已按列表、详情、新增、生效、撤销、禁赛消耗分别配置 `basket:discipline:*` 权限，前端按钮也使用对应权限控制。
2. 创建处罚时，如传入赛季，服务会检查当前管理员是否拥有该赛季所属赛事的管理范围。
3. 生效、撤销、详情和列表服务本身未见同等赛事范围复核；应确认权限体系是否在更外层统一限制，避免仅凭 ID 跨赛事读取或处理处罚。
4. 后台表单允许任意输入对象 ID，服务只校验“至少存在一个对象 ID”，未核验 `targetType` 与对象字段是否匹配，也未核验对象、比赛和赛季之间的归属关系。

## 9. 并发与幂等

1. 创建支持客户端 `idempotencyKey`，并有数据库唯一索引；服务先查询后插入，重复请求通常会被拒绝，但并发冲突的友好错误仍需联调确认。
2. 生效和撤销均使用“当前状态匹配”的条件更新，能避免两个管理员对同一记录重复生效或撤销。
3. 禁赛消耗使用“比赛 + 会员”幂等键和唯一索引，可避免同一比赛对同一会员重复写消耗日志。
4. 禁赛剩余场次更新不是带 `remaining > 0` 条件的原子扣减；不同比赛并发确认时可能读取相同剩余值并发生丢失更新，应补充乐观锁或条件更新。
5. 限制快照每个对象/赛季仅保留一个当前有效记录；新处罚生效会先停用旧快照，撤销新处罚后不会自动恢复旧处罚对应的限制。

## 12. 已知问题和风险

1. **公告关联未闭环**：主表和详情 DTO 有 `announcementId`，但创建请求、插入 SQL 和后台页面均未提供该字段，当前无法通过现有处罚流程建立公告关联。
2. **审核流程未闭环**：虽然状态枚举包含 `PENDING`、`APPROVED`、`REJECTED`，但当前创建直接为草稿，页面直接生效，未发现处罚审核通过/驳回接口与页面。
3. **有效期未真正参与限制校验**：限制快照查询只按对象、赛季和 `active_flag` 查询，没有判断开始/结束时间；未来处罚可能提前拦截，过期处罚也可能持续拦截。
4. **多处罚叠加会被覆盖**：生效新处罚前会停用同一对象/赛季的旧限制快照；撤销新处罚后仅停用当前快照，不会恢复旧处罚，导致有效处罚可能失效。
5. **禁赛消耗逻辑自相矛盾**：保存名单时会拒绝剩余禁赛大于零的球员进入名单，而确认名单时只对名单内球员调用消耗；被拒绝进入名单的禁赛球员无法由该正常流程消耗禁赛场次。
6. **取消资格影响不完整**：`allowParticipation` 已写入限制快照，但当前支持类没有对应校验方法，也未发现比赛执行/参赛确认入口使用该字段；赛事球队限制与报名校验的对象类型也未完全对齐。
7. **对象与范围校验不足**：服务未校验 `targetType` 与对象 ID、赛季、比赛之间的关联；前端也未支持账号、赛事球队、有效期、比赛和公告等关键字段，易产生无法生效或范围错误的数据。
8. **未知后台定义处罚无实际效果**：服务接受未知 `penaltyCode`，但会忽略其限制映射；如要支持“其他后台定义处罚”，需有规则配置和明确的影响映射。
9. **权限范围复核不足**：创建会校验赛事范围，但查询、详情、生效、撤销未在该服务中重新校验赛事范围，应进行越权测试。

## 13. 下一步建议

1. 先修正禁赛执行模型：明确“禁赛场次按实际缺席比赛消耗”的触发点，避免与名单保存拦截冲突，并使用原子条件更新扣减剩余场次。
2. 将限制从单条覆盖快照改为可叠加计算，或在生效/撤销时重算同一对象、赛季内所有有效处罚；同时将有效期纳入每次限制校验或增加可靠的到期任务。
3. 补齐处罚审核、驳回、到期完成、公告关联、对象归属校验和赛事范围复核，并将状态流转收敛为页面/API 均可执行的规则。
4. 为取消资格和球队停赛补齐报名、阵容、比赛执行、出场确认等入口的统一 `allowParticipation` 校验，形成明确的处罚影响矩阵。
5. 改造后台表为可检索选择赛季、比赛、球员、账号、长期球队、赛事球队和公告，并展示有效期、当前限制、禁赛消耗和审计记录。
6. 按“待测试项”建立集成测试与人工验收用例，重点覆盖有效期、叠加处罚、并发、撤销恢复和跨赛事越权。
