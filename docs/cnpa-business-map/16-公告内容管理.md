# 16-公告内容管理

> 本文件对应业务清单中的“公告内容管理”。需求原文将其列为“19. 公告内容”；此处按业务文档序号命名。结论来自对 `核心业务/核心实现.md`、管理端、官网端与 SQL 文件的静态核查，**不代表已完成真实接口联调或人工验收**。

## 1. 业务定位

公告是赛事平台面向公众发布通知、规则说明、赛事资讯和其他内容的统一载体。后台负责创建、编辑、发布、下线、置顶及规则替代；官网负责公开列表、详情、上一篇/下一篇和阅读数展示。

当前实现已从基础“内容发布”扩展到规则公告：规则类公告可关联赛事和赛季、标记版本，并通过规则替代关系维护某赛季当前生效的规则公告。

## 2. 最终业务规则

1. 后台可维护公告标题、摘要、纯文本正文、封面、分类、公开范围和重要标记；公告先保存为草稿。
2. 公告状态应为：`草稿`、`已发布`、`已下线`。已发布公告才可被前台访问；下线后不再公开；已发布内容应先下线再删除。
3. 发布、下线和置顶必须由后端权限控制，不能依赖前端按钮隐藏。置顶仅对已发布公告有效；排序应先置顶、再重要、最后按发布时间。
4. 公告可选关联赛事；规则类公告还应关联赛季与规则版本，并保证赛季与赛事归属一致。规则替代生效后，旧规则公告应失效或下线。
5. 定时发布应在设定时间自动完成发布；早于计划时间不得提前公开。
6. 前台列表、详情、上一篇/下一篇均只能返回处于公开窗口内的公告：未删除、已发布、发布时间不晚于当前时间、未下线或下线时间晚于当前时间，并应遵守公开范围。
7. 附件是可选能力：后台应按公告归属维护附件，前台详情应返回可下载的附件列表；附件不得被跨公告或未授权用户任意维护。
8. 发布、下线、置顶、规则替代、附件变更等关键动作应保留可检索的领域审计记录。

**建表一致性风险（P0）：** `sql/basketball.sql` 中的 `basket_announcement` 建表定义未包含代码 Mapper 正在读写的 `tournament_id`、`season_id`、`scheduled_publish_time`、`superseded_by`、`rule_version`；同时未在该 SQL 文件中找到 `basket_announcement_rule_link` 建表。若部署仅执行该基础 SQL，公告新增、查询或规则公告功能会因列/表缺失失败。上线前必须补齐可重复执行的迁移脚本并在空库验证。

## 5. 后端实现

### 管理端

- `BasketAnnouncementController` 暴露列表、详情、新增、编辑、发布、下线、置顶、取消置顶、规则替代、定时设置和删除接口；各写接口均配置细粒度 `@PreAuthorize` 权限及 `@Log`。
- `BasketAnnouncementServiceImpl` 新增时生成 `ANNyyyyMMddNNNN` 编号，初始状态为草稿；标题、分类和正文为必填校验点，正文经过纯文本清洗。
- 发布仅允许草稿或下线状态；下线仅允许已发布状态；删除仅允许草稿或下线状态。发布/下线的 Mapper 更新同时带旧状态条件，减少并发重复转换。
- 发布规则公告时会激活待生效的替代关系、撤销同赛季当前规则关系，并尝试下线被替代的旧公告。
- 发布、下线、置顶、取消置顶、规则替代与删除后调用 `BasketPublicCacheCleaner` 清理官网缓存。

### 官网端

- `BasketPublicAnnouncementController` 为匿名接口，提供公告分类、分页、当前赛季规则、详情和上一篇/下一篇。
- `BasketPublicAnnouncementServiceImpl` 的公开窗口条件为：未删除、状态已发布、`publish_time <= 当前时间`、`offline_time` 为空或晚于当前时间。
- 详情先校验公开状态，再执行 `view_count = ifnull(view_count, 0) + 1`，然后读取最新阅读数返回；计数增量在数据库层是原子操作，但未做同用户/同会话去重。
- 官网输出对象仅包含公告基础字段和封面 URL；详情返回正文纯文本，不包含附件、赛事 ID、赛季 ID、公开范围或规则版本。

## 6. 前端实现

### 管理端页面

- 页面：`basketball-admin-ui/src/views/cnpa/content/announcement/index.vue`。
- 支持按标题、分类、状态、赛事、赛季筛选；列表展示状态、置顶、重要、发布时间等信息。
- 新增/编辑表单覆盖分类、标题、摘要、封面上传、正文、公开范围、重要标记；规则公告可配置赛事、赛季、规则版本和定时发布时间。
- 操作入口覆盖发布、下线、置顶、取消置顶、删除、规则替代与定时发布设置，按钮受 `v-hasPermi` 控制。
- 页面未见公告附件的上传、排序、删除或下载管理入口；附件能力没有被纳入公告创建/编辑事务。

### 官网页面

- 路由：`/announcements` 和 `/announcements/:announcementId`。
- 列表页面支持分类、关键词、分页排序，展示封面、标题、摘要、发布时间、置顶/重要状态。
- 详情页面展示分类、置顶、标题、发布人、发布时间、纯文本正文及上一篇/下一篇；正文使用 `AnnouncementContentRenderer`，未按 HTML 注入。
- 官网页面未展示赛事/赛季关联、规则版本、公开范围，也未展示或下载公告附件。

## 7. 状态机

```text
草稿 DRAFT
  ├─ 编辑 → 草稿
  ├─ 设置未来定时发布时间 → 草稿（仅保存时间）
  ├─ 到达计划时间后手工发布 → 已发布
  └─ 删除 → 软删除

已发布 PUBLISHED
  ├─ 置顶 / 取消置顶 → 已发布
  ├─ 下线 → 已下线
  └─ 不允许编辑、定时设置或删除

已下线 OFFLINE
  ├─ 编辑 → 已下线
  ├─ 设置未来定时发布时间 → 已下线
  ├─ 再发布 → 已发布
  └─ 删除 → 软删除

规则替代：新规则公告（草稿/已下线）建立待生效替代关系
  └─ 新规则发布 → 新关系设为当前、旧关系失效、旧已发布规则尝试下线
```

**状态机缺口：** `schedulePublish` 只落库计划时间，代码库内未发现到点自动调用发布的定时任务；因此“定时发布”尚未形成从草稿/下线自动转为已发布的闭环。

## 9. 并发与幂等

1. **状态竞争：** 发布和下线使用“ID + 当前状态”条件更新，两个并发操作中只有一个应成功；失败方返回“发布失败/下线失败”。置顶更新仅以 ID 和未删除为条件，连续请求结果幂等，但不校验状态。
2. **公告编号：** 编号采用“当天前缀 + `countByNoPrefix + 1`”。并发新增可能计算出相同序号，虽然数库唯一索引会阻止重复，但当前没有重试或数据库序列机制，用户会得到插入失败。
3. **规则替代：** 规则替代流程使用事务，但“查询待生效关系—清当前—激活新关系—下线旧公告”未见版本号或唯一约束佐证；同一赛季并发发布多个规则公告时需验证最终仅有一条 `current_flag = 1`。
4. **定时发布：** 到点自动发布任务缺失，当前不存在任务重复执行、失败重试或幂等锁设计。
5. **阅读数：** 自增 SQL 可抵抗并发丢失更新，但刷新、爬虫和重复访问均计数；若该指标用于排行/运营，应增加去重或异步聚合策略。
6. **附件：** 附件写入与公告发布、删除、下线没有统一事务边界；孤儿附件、跨公告篡改和删除后残留均需补防护。

## 12. 已知问题和风险

### P0

1. **基础 SQL 与代码映射不一致。** 代码 Mapper 读写公告扩展字段和规则关联表，`sql/basketball.sql` 未同步定义；这是部署和运行时失败风险。
2. **公开范围未生效。** 官网 `publishedWrapper` 只校验删除、发布状态和时间窗口，没有 `public_scope = PUBLIC` 或按范围授权条件；匿名接口存在发布后越权公开风险。
3. **附件需求未闭环。** 附件表和生成式 CRUD 虽存在，但管理端公告页面、公告服务事务、官网详情响应均未接入附件。
4. **定时发布未闭环。** 仅保存时间且手工发布受时间限制，未发现自动发布调度任务、重试和监控实现。

### P1

1. 普通公告的赛事/赛季关联在后端编辑时可写入，但官网响应未携带关联信息，也没有按赛事维度的公开筛选；“按赛事关联”的用户价值尚未在前台落地。
2. `publicScope` 缺少枚举校验，当前可写入任意字符串；即使补上官网过滤，仍可能产生不可解释的范围值。
3. 管理端仅使用 `@Log`，未接入统一业务审计写入器；关键动作的对象快照、规则替代关联和附件变更难以保证统一追溯。
4. 公告编号的“计数加一”方式缺少并发重试，峰值创建时可能触发唯一键冲突。
5. 公开详情每次访问都增长阅读数，没有防刷或去重策略；公开接口还会返回作者名称，需确认运营与隐私口径。

### P2

1. 官网详情中的上一篇/下一篇跨全部公告分类和赛事范围导航，若后续要求在同赛事、同分类或同公开范围内导航，需要明确业务口径。
2. 规则替代同时维护公告 `supersededBy` 与关联表，双写数据需要补一致性约束和修复工具。
3. 下线、删除公告未见附件的级联处理或访问令牌失效策略，文件资源可能成为孤儿数据或继续可访问。

2. 为公告新增、发布、下线、置顶、规则替代、附件维护接入统一业务审计，并以公告 ID、赛事 ID、赛季 ID、操作者、动作和前后值建立查询链路。
3. 用数据库序列、雪花编号或唯一键冲突重试替换 `count + 1` 编号生成策略；为同赛季当前规则增加数据库唯一约束或悲观/乐观锁。

### P2

1. 为阅读数建立独立的反刷与异步聚合策略，并明确缓存命中是否计数。
2. 增加公告生命周期、公开范围、规则替代、附件归属、权限越权、并发发布和 SQL 迁移的自动化集成测试。
3. 梳理框架日志、统一业务审计和文件访问日志的保留周期及关联标识，方便运营排障和合规追溯。
