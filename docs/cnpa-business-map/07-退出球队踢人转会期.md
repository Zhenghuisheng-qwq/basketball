# 07-退出球队、踢人、转会期

> 范围：长期球队成员的主动离队、队长移除成员（“踢人”）、转会期规则，以及与单届赛事阵容转会/补员审核的边界。本文不把长期球队成员关系与 `basket_tournament_season_roster` 赛事阵容混为一谈。

## 1. 业务定位

退出、踢人和转会期共同解决“球员如何结束或变更球队归属”的问题，但系统中存在两个不同层级：

1. **长期球队成员关系**：`basket_team_member` 保存永久球队中的成员、队长、离队和被移除历史；它决定球员当前是否属于某支长期球队。
2. **赛事阵容关系**：`basket_tournament_season_roster` 保存某赛季、某支正式赛事球队的阵容快照；它决定球员本届赛事为哪支赛事球队出场。

最终业务要求是：普通成员离队、队长踢人均应在转会期和审核约束下执行；审核通过后球员成为自由球员，历史赛事快照不能被长期球队成员变化污染。当前实现则已具备一套**赛事阵容转会/自由球员补员/队长移交的审核流**，但长期球队仍保留直接离队、直接移除成员接口，二者尚未收敛为同一规则。

## 2. 最终业务规则

依据 `核心业务/核心实现.md`，最终规则如下：

1. 普通成员退出球队必须提交申请，不能直接结束成员关系。
2. 退出球队原则上仅在转会期允许；只有系统明确的特殊规则或例外才可在非转会期处理。
3. 退出申请需要后台审核，或按最终确认的队长/后台联合审核机制处理，并保留审核记录。
4. 审核通过后，成员结束与原长期球队的有效关系，成为自由球员；审核驳回后成员关系保持不变。
5. 同一成员的重复退出申请必须拦截，不能同时存在多条待处理申请。
6. 队长踢人不能直接删除成员，必须提交踢人申请并经过审核。
7. 踢人原因至少要覆盖：队友太菜、账号被封、态度不好、长期不活跃、违反规则、配合问题、其他；生产规则建议改为规范枚举加“其他说明”，不能只依赖自由文本。
8. 踢人申请必须审核；队长不能移除自己，也不能绕过队长移交流程。
9. 非转会期禁止踢人，除非已定义并落实特殊原因例外及其审批权限。
10. “转会管理期间全部成为自由球员”不应理解为系统自动清空所有球队成员；正确理解是：窗口开放后，成员可以申请退出或转会，审核通过后才成为自由球员。
11. 已报名、审核中、阵容锁定或已产生赛事快照的成员调整，必须遵守赛事层的报名、锁定和阵容变更规则，不能通过长期球队接口绕过。

## 4. 相关数据库表

| 表/对象 | 用 | 关键字段/状态 | 当前用途 | 结论 |
|---|---|---|---|---|
| `basket_team_member` | 长期球队成员关系 | `membership_status`、`is_current`、`active_member_slot`、`leave_time`、`leave_reason` | 直接离队写 `LEFT`；队长移除写 `REMOVED`；同时清空当前标记和槽位 | 长期成员变更的当前主表 |
| `basket_team` | 长期球队本体 | `current_member_count` 等 | 离队/移除后重新统计当前成员数 | 成员计数需与关系表保持一致 |
| `basket_player_profile` | 球员档案 | `current_team_id` | 离队/移除后，如当前球队为原球队则置空 | 表示长期球队当前归属，不是赛事阵容归属 |
| `basket_tournament_registration` | 球队报名申请 | `SUBMITTED`、`REVIEWING`、`APPROVED` 等 | 长期成员直接离队/移除前会检查该球队的进行中报名 | 当前仅是保护性拦截 |
| `basket_tournament_registration_player` | 报名阵容 | `team_member_id` | 若成员仍在进行中报名阵容，拒绝直接离队/移除 | 防止报名名单被直接破坏 |
| `basket_tournament_season` | 赛季及窗口配置 | `transfer_enabled`、`transfer_start_time`、`transfer_end_time`、`free_agent_*` | 赛事阵容转会/补员窗口判断 | 未被长期成员离队/踢人流程读取 |
| `basket_team_season_profile` | 正式赛事球队 | `season_id`、`participation_status`、`roster_lock_status` | 赛事变更时校验球队参赛状态和阵容锁定 | 与长期 `basket_team` 分层 |
| `basket_tournament_season_roster` | 正式赛事阵容快照 | `ACTIVE`、`TRANSFERRED_OUT`、`active_slot` | 审核通过的赛事转会使旧阵容失效并插入新阵容 | 历史比赛与长期成员变更隔离的关键 |
| `basket_tournament_roster_change_request` | 赛事阵容变更申请 | `TRANSFER`、`FREE_AGENT_ADD`、`CAPTAIN_TRANSFER`；`PENDING/APPROVED/REJECTED/WITHDRAWN` | 保存赛事转会、补员、队长移交申请 | 不是长期球队退出/踢人申请表 |
| `basket_tournament_roster_change_record` | 赛事阵容变更历史 | 变更前后、操作人、原因、生效时间 | Admin 审核通过时写入 | 已有赛事层留痕 |
| `basket_tournament_roster_operation_log` | 管理员特殊阵容操作 | 操作前后值、原因、管理员 | 迁移已定义 | 用于赛事阵容，不替代长期球队踢人审计 |

关键约束：

1. `basket_team_member.active_member_slot` 的唯一索引用于限制一名会员同时只存在一条有效长期球队成员关系；离队或被移除时必须清空该槽位。
2. 赛事阵容使用 `active_slot = {seasonId}:{playerId}` 的唯一约束，保证同一球员在同赛季只保留一条有效赛事阵容；其粒度与长期球队成员唯一约束不同。
3. `docs/cnpa-batch4-migration.sql` 已定义转会窗口和赛事阵容变更表；`docs/cnpa-admin-batch4-result.md` 记录该迁移于 **2026 年 7 月 25 日** 已执行。仍建议在目标环境实际核查表、字段和索引，不能只依赖文档结论。

## 5. 后端实现

### 5.1 长期球队直接离队与移除

| 场景 | Controller/接口 | Service 行为 | 权限与限制 |
|---|---|---|---|
| 成员主动离队 | `POST /basket/team/{teamId}/leave` | 将成员更新为 `LEFT`，`is_current=0`，清空活跃槽位，写离队时间/原因，清空球员当前球队，重算人数 | 只能操作本人；队长直接离队会被拒绝 |
| 队长移除成员 | `DELETE /basket/team/{teamId}/member/{teamMemberId}` | 将目标成员更新为 `REMOVED`，并执行相同的归属清理和人数重算 | 必须是该长期球队队长；不能移除自己或队长 |
| 成员展示字段更新 | `PUT /basket/team/{teamId}/member/{teamMemberId}` | 更新球衣号、阵容类型、备注等 | 不应用于替代赛事阵容变更 |

`TeamMemberBusinessServiceImpl` 的直接成员变更具有以下已确认行为：

1. 先通过 `captainPermissionService.requireTeamMember` 或 `requireTeamCaptain` 确认成员/队长身份和球队归属。
2. `assertNotInActiveRegistration` 查询该长期球队 `SUBMITTED`、`REVIEWING`、`APPROVED` 状态的报名；若目标成员仍在报名阵容中，则拒绝离队或移除。
3. `markMemberLeft` / `markMemberRemoved` 写入成员最终状态和固定文案“主动离队”或“被队长移除”。当前接口没有接收退出原因、踢人原因或特殊例外原因。
4. 通过 `TeamMemberJoinHelper.clearActiveMemberSlot`、`clearPlayerCurrentTeam` 和 `recalculateCurrentMemberCount` 维护成员唯一归属与球队人数。
5. 通过 `AccountSecurityLogHelper` 记录 `TEAM_LEAVE` 或 `TEAM_REMOVE` 安全日志；未见对应的长期球队退出申请、踢人申请、审核意见和站内通知实现。

### 5.2 赛事阵容转会、补员与队长移交

Web 端 `RosterChangeBusinessController` 已提供：

| 接口 | 申请类型 | 关键校验 |
|---|---|---|
| `POST /basket/player/roster-change/transfer` | `TRANSFER` | 当前用户已认证为球员、未受参赛限制、转会窗口开放、源/目标赛事球队有效且未锁定、目标阵容未满、申请人当前在源赛事阵容中、同类型无待审申请 |
| `POST /basket/player/roster-change/free-agent-add` | `FREE_AGENT_ADD` | 补员窗口开放、操作人是目标赛事球队队长、目标未锁定且未满、补员次数未超限、目标球员本赛季无有效阵容且未受限制 |
| `POST /basket/player/roster-change/captain-transfer` | `CAPTAIN_TRANSFER` | 申请人队长资质有效且是赛事队长、赛事球队未锁定、新队长在同队有效阵容中、不能移交给当前队长 |
| `POST /basket/player/roster-change/{requestId}/withdraw` | 撤回 | 仅申请人可撤回，且仅 `PENDING` 状态可撤回；更新带状态条件 |
| `GET /basket/player/roster-change/page` | 我的申请 | 按申请人和状态分页查询 |

Admin 端 `BasketRosterChangeAuditController` 提供列表、详情、通过、驳回接口；`BasketRosterChangeAuditServiceImpl` 在事务中处理：

1. 转会通过：校验纪律限制和阵容未锁定，将源 `season_roster` 更新为 `TRANSFERRED_OUT`，插入目标球队的新有效阵容，写 `roster_change_record`。
2. 自由球员补员通过：确认球员本赛季没有有效赛事阵容，插入目标球队新阵容，写变更记录。
3. 队长移交通过：清除赛事球队当前队长标记，设置新队长标记并更新赛事球队队长字段，写变更记录。
4. 审核通过或驳回后，使用 `updateStatusIfMatch` 将申请从 `PENDING` 更新为终态，并发送站内消息。

## 7. 状态机

### 7.1 长期球队成员当前状态

```text
                 邀请接受 / 申请通过 / 创建球队
                              │
                              ▼
                         ACTIVE（在队）
                         is_current = 1
                              │
          ┌──────────────────┴───────────────────┐
          │                                       │
     当前直接主动离队                         当前队长直接移除
          │                                       │
          ▼                                       ▼
       LEFT（已离队）                         REMOVED（被移除）
       is_current = 0                          is_current = 0
       清空 active_member_slot                 清空 active_member_slot
```

当前转换条件：队长不得通过离队接口离队；队长不得移除自己或其他队长；成员处于进行中赛事报名阵容时，直接离队/移除均被拒绝。**当前状态机没有 `PENDING_EXIT`、`PENDING_REMOVE`、`APPROVED` 或 `REJECTED` 等长期成员申请状态。**

### 7.2 赛事阵容变更申请状态

```text
提交 TRANSFER / FREE_AGENT_ADD / CAPTAIN_TRANSFER
                    │
                    ▼
             PENDING（待审核）
          ┌─────────┼─────────┐
          │         │         │
      申请人撤回  Admin 通过  Admin 驳回
          │         │         │
          ▼         ▼         ▼
     WITHDRAWN   APPROVED   REJECTED
                    │
                    ▼
   转会：旧 roster → TRANSFERRED_OUT，新 roster → ACTIVE
   补员：新 roster → ACTIVE
   队长移交：更新同队 roster 的 captain 标记
```

该状态机由 `RosterChangeStatusEnum` 定义，属于赛事阵容层。审核驳回不会变更原赛事阵容；撤回仅允许由申请人对 `PENDING` 申请执行。

### 7.3 最终目标状态机（长期球队）

长期球队应补齐独立的退出/踢人申请状态，例如：

```text
PENDING_EXIT / PENDING_REMOVE → APPROVED → LEFT / REMOVED
                              ├→ REJECTED → ACTIVE
                              └→ CANCELLED → ACTIVE
```

所有终态都应记录审核人、审核时间、原因、例外依据和通知结果；`APPROVED` 后才清空长期球队活跃成员槽位。

## 8. 权限规则

| 操作 | 当前权限控制 | 最终应有规则 | 当前差异 |
|---|---|---|---|
| 普通成员主动离队 | 当前登录用户只能对自己在指定球队的成员关系调用 `leave` | 提交退出申请；转会期/例外检查；审核后生效 | 当前直接生效，无窗口和审核 |
| 队长移除普通成员 | `requireTeamCaptain`；不能移除自己或 `CAPTAIN` 角色成员 | 队长提交踢人申请；仅转会期或批准例外；审核后生效 | 当前直接生效，无踢人申请和审核 |
| 队长离队 | 当前直接拒绝 | 应先完成队长移交或走受控解散/管理流程 | 与最终原则一致，但缺少完整后续流程说明 |
| 非本队队长移除成员 | 后端拒绝 | 必须拒绝 | 代码已覆盖 |
| 成员离队/移除进行中报名成员 | 后端检查进行中报名阵容并拒绝 | 还应覆盖赛事队伍锁定、赛程/比赛进行状态和特殊例外 | 现有检查范围有限 |
| 赛事转会申请 | 申请人必须是源赛事阵容球员 | 仅转会窗口、未锁定赛事队伍、纪律允许 | 当前已实现主要校验 |
| 赛事自由球员补员 | 目标赛事球队队长 | 补员窗口、名额、纪律和阵容状态 | 当前已实现主要校验 |
| 赛事阵容审核 | Admin 权限 `basket:rosterChangeAudit:list/query/audit` | 审核人、理由、时间、操作留痕均可追溯 | 当前已具备权限和审计字段，需联调验证 |

## 9. 并发与幂等

| 场景 | 当前控制 | 风险与要求 |
|---|---|---|
| 长期成员直接离队/移除重复请求 | 状态更新后第二次通常因成员已非有效关系失败 | 未见显式 CAS 条件更新；离队、计数重算、当前球队清理应做并发回归 |
| 长期成员同时离队与被队长移除 | 两条直接变更路径都可能读到 `ACTIVE` | 需验证最终只有一个终态、人数不重复扣减、日志不冲突；目标方案应由申请状态和条件更新统一仲裁 |
| 长期成员离队后加入另一队 | 清空 `active_member_slot` 后释放唯一关系 | 需验证与新队加入并发时唯一键异常能转换为稳定业务错误，不能出现双有效成员关系 |
| 赛事同类型重复申请 | `assertNoPendingChange` 查询 `PENDING` | 缺少数据库级 pending 唯一键；并发双提交可能都通过查询后插入 |
| 赛事申请撤回与审核并发 | 撤回使用 `request_status=PENDING` 条件更新；审核也使用 `updateStatusIfMatch` | 状态 CAS 能避免最终状态双写，但审核在状态 CAS 前先执行阵容变更，需重点压测事务隔离和失败回滚 |
| 两名管理员同时通过同一赛事申请 | 审核状态更新为条件更新 | `applyChange` 在 CAS 更新前执行，若没有行锁，第二个事务可能先修改阵容再因状态 CAS 失败；应复核数据库隔离、SQL 锁与事务回滚表现 |
| 多个转会/补员占用同一目标阵容名额 | 提交时先统计容量；赛事有效阵容有 `active_slot` 唯一键但不限制总人数 | 最后名额存在并发超额风险；审核通过时应再次在锁内核验容量 |
| 同赛季同球员多队赛事阵容 | `uk_season_roster_active_slot(active_slot)` | 数据库约束是有效兜底；需处理唯一键冲突并确保源阵容先失效、目标阵容后写入 |

## 12. 已知问题和风险

1. **P0：长期成员直接变更违反最终审核/转会期原则。** 当前 `leave` 和 `removeMember` 直接改变 `basket_team_member` 状态，未创建申请、未校验转会期、未做审核，也未实现特殊例外审批。
2. **P0：长期球队没有退出申请和踢人申请数据模型。** 未发现转会期配置表、退出申请表、踢人申请表，亦未见复用 `basket_tournament_roster_change_request` 的长期成员实现；不能仅靠已有赛事阵容变更表宣称需求已完成。
3. **P0：长期踢人原因不完整。** 当前固定写入“被队长移除”，无法记录核心需求中的踢人原因、补充说明、证据、审核意见或例外依据。
4. **P0：直接离队/移除并发一致性待验证。** 当前流程包含成员状态、当前球队、活跃槽位、球队人数和安全日志多处写入，但未见针对成员状态的显式 CAS 条件更新；同时离队/移除可能造成竞态。
5. **P1：报名保护不等于统一锁定保护。** 长期成员流程只检查进行中报名是否包含该成员，未见直接读取赛事球队 `roster_lock_status`、比赛阶段或比赛已开赛状态的统一规则；可能出现长期成员变更与赛事锁定边界不一致。
6. **P1：赛事阵容申请的防重主要依赖查询。** `assertNoPendingChange` 先查询再插入，数据库仅保证 `request_no` 唯一，未保证“同赛季、同球员、同类型仅一条待审”；并发重复提交仍有风险。
7. **P1：赛事审核的状态 CAS 位置需要压测。** Admin 审核先执行实际阵容变更，再做 `updateStatusIfMatch`；虽然处在事务内，但并发审核必须验证不会在 CAS 失败前造成重复变更或死锁问题。
8. **P1：容量只在提交申请时检查。** 目标阵容满员检查主要发生在申请提交期；多个待审申请在审核期间同时占用最后名额时，可能超出 `max_roster_count`，需要审核阶段再次加锁校验。
9. **P1：长期成员直接变更仅写安全日志。** 它不等于最终要求的审核日志和业务留痕；缺少可按申请、原因、审核人和生效时间查询的运营审计页。
10. **P2：自由球员概念需要统一。** 当前赛事“自由球员”指本赛季不存在有效赛事阵容的球员；最终长期球队规则中的“自由球员”指不再属于有效长期球队成员。两者不能直接等同。

## 13. 下一步建议

### P0

1. 新建或明确复用长期成员变更申请模型，至少区分 `LEAVE_TEAM`、`REMOVE_MEMBER`、`TRANSFER_TEAM`、`SPECIAL_EXCEPTION`，包含申请人、目标成员、原/目标长期球队、原因枚举、充说明、状态、审核人、审核时间、审核意见和生效时间。
2. 在长期成员变更申请提交与审核通过时统一校验：转会窗口、特殊例外、进行中报名、赛事阵容锁定、队长身份、一人一队、人数上限和处罚限制；移除当前直接离队/直接踢人作为默认路径。
3. 将长期成员生效动作收敛到一个事务服务：条件更新成员状态、清空 `active_member_slot`、更新 `current_team_id`、重算人数、写业务审计和通知；对状态使用 CAS 或行锁。
4. 审核通过长期成员变更后，明确与赛事层的衔接：已在赛事阵容的球员必须走赛事阵容变更或先按规则处理，不能只修改长期成员关系。

### P1

1. 在 `basket_tournament_roster_change_request` 增加待审唯一槽位或通过数据库锁/唯一约束保证同赛季同球员同类型只存在一条待审申请；将重复键异常转换为稳定业务提示。
2. 在 Admin 审核赛事转会/补员时，将“申请状态仍为待审、目标阵容未锁定、目标容量未满、球员仍满足资格”放到同一锁定事务内复验，再执行阵容写入。
3. 补齐长期球队退出、踢人和例外审批的 Admin 页面、Web 申请/撤回页面、站内消息和可查询历史；前端只展示权限入口，后端必须为最终裁决。
4. 统一文案和数据字典：长期成员的“离队/被移除/自由球员”与赛事阵容的“转出/补员/队长移交”分别建模、分别展示。

### P2

1. 设计转会期运营配置：按赛季、赛事或长期球队域明确生效范围、开始/结束时间、暂停状态、特殊例外类型、审批人和操作日志。
2. 为长期成员状态变更和赛事阵容变更增加端到端回归测试，覆盖并发、撤回、审核、通知、历史快照、处罚和异常回滚。
3. 在后续“赛事赛季阶段规则”“赛事报名与阵容快照”“审核日志与操作留痕”“并发幂等”文档中继续复用本文的分层结论，避免再次把长期成员关系误写为赛事阵容变更。
