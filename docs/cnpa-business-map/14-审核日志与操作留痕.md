# 14. 审核日志与操作留痕

## 1. 业务定位

本模块保证关键审核、授权、赛程、比赛数据、处罚和内容运营操作可被追溯：谁在何时对什么对象执行了什么动作、动作前后状态是什么、为何操作、涉及哪些字段，以及该操作是否成功。

日志不是单一表即可完成。系统目前同时存在统一业务审计、领域专用审核/状态日志、RuoYi `@Log` 操作日志和安全日志等多套机制；本篇梳理其边界，并标出尚未统一的留痕缺口。

## 2. 最终业务规则

下列操作必须留痕，至少包含操作人、操作时间、对象、动作、前后状态、原因/审核备注；涉及字段修改时还应记录前后值：

1. 球员认证审核通过/驳回，以及游戏 ID 首次绑定和后续修改。
2. 球队认证审核通过/驳回。
3. 队长授权的授予、撤回、失效。
4. 赛事报名审核通过/驳回。
5. 加入球队、退出球队、踢人和转会相关审核/生效操作。
6. 比赛数据提交、重提、审核通过、驳回；比分修改和比赛结果确认/重开。
7. 异常裁定、弃赛、处罚创建/生效/撤销。
8. 公告创建、发布、下架、置顶、撤销和删除。

审核和状态变更必须防重复：同一待审核对象被一个管理员处理后，其他管理员不得再次通过或驳回；审核记录、状态更新和后续副作用应在同一事务内成功或回滚。

## 3. 当前实现结论

### 代码确认

1. 已有统一审计中心 `basket_business_audit` / `basket_business_audit_field`，支持业务模块、对象类型/ID、动作、摘要、原因、操作人和字段前后值；后台提供列表和详情接口。
2. 统一审计写入器目前已被赛程生成/发布/编辑/直接录分、处罚、赛事管理员授权、赛事范围授权等部分链路使用。
3. 球员认证、球队认证、赛事报名、开放报名、队长授权、比赛状态、比赛数据提交审核、统计变更等已有专用审计或日志表，能保留各自领域的状态、审核人、备注和时间。
4. 比赛数据审核通过/驳回使用带当前状态条件的更新，更新失败会提示“可能已被其他管理员处理”；这为重复审核提供了基础并发保护。
5. 比赛结果页可查询比赛状态日志和统计变更记录；比赛数据审核页可查看提交版本及提交/审核日志。
6. 公告管理控制器使用 `@Log` 写框架操作日志，但本次未发现公告操作同步写入统一业务审计表的实现。
7. 统一业务审计页面/API 的字段命名与后端 DTO 不一致，当前页面筛选和列展示存在失效风险，不能视为已可用的追溯界面。

### 用户手测记录

本次仅做静态代码与 SQL 核对，未以多个后台账号并发审核，也未实际检查数据库日志、RuoYi 操作日志或页面查询结果；不应标记任何日志链路为人工验收通过。

## 5. 后端实现

1. `BasketBusinessAuditWriter` 负责统一审计写入：生成审计编号，记录操作成功结果、摘要、原因和当前登录操作人；若传入字段差异，则批量写入子表。
2. `BasketBusinessAuditController` 提供 `/basket/businessAudit/list` 和 `/basket/businessAudit/{id}`；`BasketBusinessAuditServiceImpl` 支持按模块、赛事、赛季、对象、动作、操作人和关键字查询，并返回字段差异详情。
3. `ScheduleAuditSupport` 将赛程草稿生成、发布/下架、删除、人工编辑、换队和比分录入写入统一审计；赛事/批次 ID 当前只拼接到摘要文本。
4. `BasketMatchDataAuditLogSupport` 将比赛数据提交、重提、通过和驳回写入 `basket_match_data_audit`；审核服务对提交记录和比赛行加锁，并用条件更新阻止重复审核。
5. `BasketMatchValidationService`、比分服务和统计服务通过 `basket_match_status_log` 写比赛生命周期记录；统计确认/重开还写 `basket_stat_change_record`。
6. 球员认证、球队认证、赛事报名和队长授权分别由各自服务写专用审核/授权日志；球员认证额外写平台身份历史和账户安全日志。
7. 多数后台控制器同时使用 `@Log`。这能写框架操作日志，但与领域审计表不是同一数据源，查询与保留策略需要统一定义。

## 6. 前端实现

1. 统一审计页为 `basketball-admin-ui/src/views/cnpa/discipline/audit-log/index.vue`，配套 API 为 `src/api/basket/businessAudit.ts`，具备列表查询和详情抽屉。
2. 比赛数据录入页 `cnpa/competition/match-data-entry/index.vue` 可通过 `basket:matchStat:audit` 查看比赛状态日志和统计变更。
3. 比赛数据审核页 `cnpa/competition/match-data-audit/index.vue` 展示提交版本及审核记录，并提供通过/驳回动作。
4. 球员认证、球队认证、报名审核、队长授权等页面分别展示各自领域的审核历史；这些记录尚未确认全部汇聚到统一审计页。
5. 当前统一审计页请求字段为 `businessModule`、`operationType`，表格读取 `targetType`、`targetId`、`operationTime`、`oldValue/newValue`；后端实际使用 `bizModule`、`actionType`、`objectType`、`objectId`、`createTime`、`beforeValue/afterValue`，前后端契约不匹配。

## 7. 状态机

审计记录本身应是追加式事实，不应随业务状态回滚而被业务更新覆盖；但它必须与对应业务事务一致。

### 审核对象通用状态

`待审核/审核中` → `通过` 或 `驳回`。

- 通过：写审核人、审核时间、备注、前后状态，并在同一事务中执行快照、资格、统计或通知等副作用。
- 驳回：写审核人、审核时间、必填驳回原因和前后状态；若支持重提，应以新版本或新申请继续留痕。
- 已处理：再次审核必须被条件更新/版本校验阻断。

### 比赛数据提交状态

`提交` → `审核中` → `通过` 或 `驳回` → `重提新版本`。

每个版本应保留独立的提交和审核记录；审核通过后才同步正式数据、生成当前正式结果并触发结算。

## 8. 权限规则

1. 统一审计列表与详情分别需要 `basket:businessAudit:list`、`basket:businessAudit:query`；仅拥有业务编辑权限不应自动获得全量审计查询权限。
2. 比赛数据审核列表、详情、通过、驳回使用 `basket:matchAudit:list/query/approve/reject`；比赛状态/统计审计使用 `basket:matchStat:audit`。
3. 各领域审核、处罚、公告、赛程和授权操作仍由其专属权限控制；写审计的职责在服务端，调用者不能通过请求参数伪造操作人。
4. 审计详情可能包含身份、账号、处罚原因或材料信息。`sensitive_flag` 仅标记字段，不代表已实现自动脱敏；查询层必须按角色和数据范围限制展示。
5. 平台账号、安全事件和认证资料需要较普通操作日志更严格的访问、导出和保留策略。

## 9. 并发与幂等

### 已实现保护

1. 比赛数据审核通过/驳回会锁定提交和比赛记录，并用“当前提交状态 + 审核状态”作为条件更新；受影响行不为 1 时拒绝重复审核。
2. 赛事报名、球员/球队认证等审核服务普遍以状态条件更新并写专用审核记录，具备基础重复处理拦截。
3. 统一审计字段明细和主记录由同一个写入器顺序写入；在外层业务事务中调用时可随业务回滚。

### 待验证或补强

1. `BasketBusinessAuditWriter` 自身未显式声明事务；若被非事务调用或子表批量写失败，可能出现主审计已写、字段明细缺失，需要确认所有调用点事务边界。
2. 统一审计编号采用随机 UUID 短串，依赖唯一索引兜底；理论冲突概率低但写入异常后的重试/重复记录策略未定义。
3. 统一审计写入器未填充 `tournament_id`、`season_id`、`biz_no`、`related_match_id`、对象版本或 `trace_id`，因此数据库索引与跨模块追踪能力没有被充分使用。
4. RuoYi `@Log`、统一业务审计、专用领域日志之间没有统一幂等键和关联 ID；同一操作可能多处记录或一处缺失，难以端到端比对。

## 12. 已知问题和风险

### P0

1. **统一审计页面与后端契约不匹配。** 页面/API 使用 `businessModule/operationType/targetType/targetId/operationTime/oldValue/newValue`，后端 DTO 使用 `bizModule/actionType/objectType/objectId/createTime/beforeValue/afterValue`。筛选条件会被忽略，表格关键列和字段差异可能为空或错误，审计中心当前不能作为可靠追溯工具。
2. **关键操作覆盖不完整且分散。** 统一审计仅确认接入部分服务；公告发布/下架、游戏 ID 修改、加入/退出/踢人/转会以及部分异常裁定未确认接入统一审计。专用表、框架日志和统一审计之间没有覆盖矩阵，无法证明需求列出的全部动作都可追溯。
3. **赛程审计缺少结构化赛事范围。** `ScheduleAuditSupport` 把 Event/批次 ID 拼入摘要，没有填入统一审计的赛季、比赛、业务号等结构化列；按赛事、赛季、比赛过滤会失真或无法使用。

### P1

1. 统一审计写入器固定 `action_result=SUCCESS`，未记录失败尝试、拒绝原因、异常栈或事务回滚信息；对安全排查和越权尝试追溯不足。
2. 字段审计虽有 `sensitive_flag`，但当前详情查询直接返回前后值，未见按敏感标识自动脱敏或权限隔离。
3. 领域日志的对象 ID 口径不统一：部分以长期球队/球员为主，部分以赛事快照或提交版本为主；跨赛事历史追踪可能需要额外关联。
4. `@Log` 和领域审计可能重复记录，但没有 `trace_id` 实际赋值，难以判定一次操作的完整审计链。

### P2

1. 统一审计查询缺少时间范围、动作结果、关联比赛/申请/处罚等常用过滤维度，前端也没有分页处理，数据量增长后可用性会下降。
2. 审计记录采用软删除字段，需明确谁可以删除、是否允许删除、删除本身如何留痕；合规场景通常应禁止业务侧删除审计事实。
3. 旧的 `basket_schedule_audit` 命名与当前统一审计实现并存，需梳理存量表和迁移策略，避免运营人员查错入口。

## 13. 下一步建议

### P0

1. 立即统一 `businessAudit.ts`、`audit-log/index.vue` 与后端 `BusinessAuditQuery/Vo` 的字段命名和类型，并增加前端接口契约测试；修复前不要把该页面作为验收完成项。
2. 建立“关键业务动作 → 写入表 → 查询入口 → 权限 → 测试用例”的覆盖矩阵，逐项补齐需求列出的十四类操作，优先公告、游戏 ID、队伍成员变更、比赛异常和处罚。
3. 改造统一审计写入接口，使调用方可传入赛事、赛季、业务号、关联申请/审核/比赛、对象版本和 `trace_id`；赛程审计不再依赖摘要字符串解析。

### P1

1. 为统一审计增加失败/拒绝结果、异常摘要及统一关联 ID，贯通 `@Log`、专用审核表、状态日志和通知/定时任务日志。
2. 对敏感字段实现服务端脱敏与数据范围授权；审计导出、查看和修改权限应分离。
3. 将审核状态更新、领域日志、统一审计和关键副作用纳入同一事务，并在所有高风险调用点验证子表写入失败会整体回滚。
4. 为业务审计列表增加时间范围、分页、动作结果、关联对象等索引和查询条件，避免规模增长后无法追溯。

### P2

1. 明确审计记录不可变与保留期策略：禁止普通业务软删审计，需归档时保留校验与访问链路。
2. 在比赛、报名、队长、处罚和公告详情页提供跳转到统一审计的深链接，降低运营人员跨多表排查成本。
