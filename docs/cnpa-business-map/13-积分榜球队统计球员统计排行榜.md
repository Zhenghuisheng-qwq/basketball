# 13. 积分榜、球队统计、球员统计与排行榜

## 1. 业务定位

本模块负责把已经确认的单场比赛结果沉淀为可公开、可查询、可重算的赛事数据：阶段/小组积分榜、球队赛季统计、球员赛季统计、球队排行榜和球员排行榜。

它不是原始数据录入模块。唯一可信的输入应是已结束且数据已确认的比赛及其正式结果、单场球队统计、单场球员统计；未审核、已驳回、已重开或未确认的数据不得进入汇总和官网展示。

## 2. 最终业务规则

1. 只有比赛数据审核通过、比赛结果正式确认后，才同步比赛比分、分节比分、球队单场数据、球员单场数据、积分榜、赛季统计和排行榜。
2. 积分榜按 Event/运营赛季、阶段和小组隔离；积分、胜负、得失分、净胜分、胜率、连胜/连败及同分排序必须按赛事积分规则计算。
3. 球队和球员赛季统计必须只累计已确认单场统计，至少支持按赛事/赛季、阶段、球队、球员查询；平台归属应随 Event/比赛快照保持隔离。
4. 排行榜应从同一份已确认赛季统计构建，并保存快照日期、名次、上期名次和统计值；球队、球员的排行类型必须配置/枚举化。
5. 重复审核、重复确认、重试结算不得重复累计。结果重开、官方修正、弃赛裁定后，应重建受影响范围并失效官网缓存。
6. 官网只能展示公开赛季下的正式数据；比赛结果应要求 `FINISHED + CONFIRMED`，原始待审提交数据不能作为前台统计来源。
7. 历史赛季/赛事展示应使用 EventTeam/EventPlayer 或结果快照，不能因为长期球队改名、换 Logo、球员资料变化而污染历史。

## 3. 当前实现结论

### 代码确认

1. `BasketDataSettlementServiceImpl` 是统一重算入口，可按赛季、阶段、小组或单场比赛重建；其汇总范围是目标赛季的已结束且 `data_status=CONFIRMED` 比赛。
2. 结算依次重建积分榜、球队赛季统计、球员赛季统计和赛季排行榜；成功后写统计变更记录并清理 `basket:public:*` 缓存。
3. 正式结果确认、队长提交审核通过、结果重开、异常裁定和官方数据修正会通过 `BasketMatchStatSyncServiceImpl` 的幂等同步记录触发 `rebuildMatch`。
4. 积分榜由 `BasketStandingServiceImpl` 根据确认比赛、赛事积分规则和同分规则计算；支持赛季、阶段和小组范围重建。
5. 球队/球员赛季统计从已确认的 `basket_match_team_stat`、`basket_match_player_stat` 聚合构建，统计表自身也标记为 `CONFIRMED`。
6. `BasketRankingServiceImpl` 从赛季统计生成球队和球员排行榜，并按当天零点保存排行榜快照；当前重建使用赛季级 `stage_id=0` 范围。
7. 官网已有公开积分榜、赛季球队/球员统计、数据中心排行榜和赛季汇总接口，前端已有赛事积分榜和数据中心页面调用。
8. 当前统计/积分榜/官网展示主要通过长期 `team_id`、`player_id` 关联名称和 Logo；未见在汇总表中保存 EventTeam/EventPlayer 名称快照，因此历史资料污染风险仍存在。

### 用户手测记录

本次未连接数据库、未执行结算重建接口、未验证积分规则、未检查真实官网页面数据；以下“已通过项”仅表示代码路径已存在，不代表用户手测、接口联调或数据迁移完成。

## 4. 相关数据库表

| 表/对象 | 用途 | 当前结算口径 |
| --- | --- | --- |
| `basket_match` | 比赛结果主表 | 仅已结束且数据已确认的记录是统计汇总的基础。 |
| `basket_match_official_result` | 当前有效正式结果 | 确认、审核通过、修正或裁定后生成/替换；用于正式结果版本和同步幂等关联。 |
| `basket_match_team_stat` | 球队单场统计 | 以 `data_status=CONFIRMED` 的记录汇总球队赛季统计。 |
| `basket_match_player_stat` | 球员单场统计 | 以 `data_status=CONFIRMED` 的记录汇总球员赛季统计。 |
| `basket_stage_standing` | 阶段/小组积分榜 | 保存赛季、阶段、小组、球队、排名、积分、胜负、得失分、连胜/连败及快照时间。 |
| `basket_team_season_stat` | 球队赛季统计 | 保存赛季/阶段维度的球队场次、胜负、得失分和技术统计汇总。 |
| `basket_player_season_stat` | 球员赛季统计 | 保存赛季/阶段、球队、球员的场次、得分、篮板、助攻、命中率、效率等汇总。 |
| `basket_team_rank` | 球队排行榜快照 | 以赛季、阶段、排行类型、球队和 `snapshot_date` 保存名次、上期名次与统计值。 |
| `basket_player_rank` | 球员排行榜快照 | 以赛季、阶段、排行类型、球员/球队和 `snapshot_date` 保存名次、上期名次与统计值。 |
| `basket_stat_sync_record` | 结算触发幂等记录 | 唯一键围绕 `matchId + officialResultId + syncType`，防止同一正式结果重复触发同步。 |
| `basket_stat_change_record` | 重算审计 | 记录结算触发类型、汇总数量和操作人。 |
| `basket_data_settlement_batch` | 需求中的结算批次对象 | 在当前代码中未见对应实体、Mapper 或写入链路；不能视为已实现。 |

基线表普遍只保存长期 `team_id`、`player_id`，没有 EventTeam/EventPlayer 的展示快照列；与“历史数据使用快照”的目标不完全一致。

## 5. 后端实现

1. `BasketDataSettlementServiceImpl` 提供赛季、阶段、小组、单场四种重建范围。重建前执行赛季数据校验并获取按赛季维度的 Redis 分布式锁；成功后写审计并清理公开缓存。
2. 自动触发来自确认/重开等正式结果变更。`BasketMatchStatSyncServiceImpl` 先写入唯一幂等键，只有首次成功写入时才调用结算；重复触发直接跳过。
3. `BasketStandingServiceImpl` 从已确认比赛构建球队聚合，计算场次、胜负、得失分、净胜分、积分、胜率、连胜/连败；同分比较通过赛事积分规则中的同分项处理，包括相互战绩等规则。
4. `BasketTeamSeasonStatServiceImpl`、`BasketPlayerSeasonStatServiceImpl` 从已确认单场统计聚合赛季/阶段数据，重建时先清除目标范围旧汇总再批量写入新汇总。
5. `BasketRankingServiceImpl` 从赛季球队/球员统计生成全部枚举排行类型的排行记录。球队排行包含胜率、场均得分/失分、篮板、助攻、抢断、盖帽与命中率等；球员排行包含场均得分、篮板、助攻、抢断、盖帽、命中率和效率等。
6. `BasketDataSettlementController`、`BasketStandingController`、`BasketRankingController` 提供后台查看、校验和重建接口；赛季、阶段、小组、比赛范围均可由有权限管理员人工重算。
7. 官网 `BasketPublicStandingController`、`BasketPublicSeasonStatController`、`BasketPublicDataCenterController` 提供积分榜、球队/球员赛季统计、排行榜和赛季汇总；公开比赛详情的球队/球员单场统计也过滤为已确认数据。

## 6. 前端实现

1. 后台页面包括：`cnpa/statistics/standings`、`team-season`、`player-season`、`ranking`、`settlement` 和 `season-result`，配套 API 位于 `basketball-admin-ui/src/api/basket/standing.ts`、`ranking.ts` 等。
2. 后台支持查看积分榜、球队/球员统计、球队/球员排行榜，并提供赛季/阶段/小组/单场等范围的重建入口；具体按钮权限由后端 `BasketSettlementPerms` 控制。
3. 官网积分榜组件为 `basketball-web-ui/src/views/events/components/RegularStandings.vue`，调用公开积分榜接口。
4. 官网数据中心页面为 `basketball-web-ui/src/views/data/index.vue` 及其组件，使用公开赛季列表、球队排行榜、球员排行榜和赛季汇总 API；球队/球员详情页也读取公开赛季统计和排行榜。
5. 页面及接口存在不代表已完成真实数据验收。应特别验证：无数据、重算中、重算失败、规则缺失、榜单快照为空及球队/球员改名后的展示。

## 7. 状态机

### 单场结果到结算

`待审/已提交` → `已确认（CONFIRMED）` → `生成当前正式结果` → `写入同步幂等记录` → `重建汇总` → `清理公开缓存`。

当结果被重开、裁定或官方修正时，应生成新的正式结果版本或更新正式状态，再触发同一赛季范围的重建。未确认比赛永远不应参与积分榜和赛季统计。

### 重算任务

`待校验` → `获得赛季锁` → `重建积分榜（规则可用时）` → `重建球队统计` → `重建球员统计` → `生成排行榜快照` → `审计/清缓存` → `完成或回滚`。

- 手工重算要求赛季校验通过、积分规则完整。
- 自动触发时，若仅缺积分规则，当前代码允许跳过积分榜但仍重建球队统计、球员统计和排行榜；这会形成“统计更新、积分榜空缺”的部分可用状态。

## 8. 权限规则

1. 后台积分榜、球队/球员赛季统计、排行榜的查询分别由 `BasketSettlementPerms` 中的列表权限保护。
2. 赛季/阶段/小组/单场重建属于高风险操作，需要数据结算或专项重建权限；控制器同时记录操作日志。
3. 结算前的比赛数据确认、结果重开、官方修正、弃赛裁定应由比赛审核/裁定权限控制，不能把结算接口作为绕过审核的入口。
4. 官网公开接口使用免登录访问，但必须先校验赛季公开状态；结果页和单场统计只读取已确认数据。
5. 直接数据表查询、缓存刷新和人工重建都不应授予普通队长或普通运营角色。

## 9. 并发与幂等

### 已实现保护

1. 结算按 `seasonId` 获取 Redis 分布式锁，避免同一赛季的多次重建并行执行；锁含 30 分钟 TTL，并在 finally 中按令牌释放。
2. `basket_stat_sync_record` 使用基于比赛、正式结果和同步类型的幂等键；插入唯一键冲突时不重复调用结算，避免同一正式结果重复累计。
3. 重建是覆盖式计算：积分榜、赛季统计和同日排行快照会先删除/软删除目标范围旧数据再写新数据，因此重复“重算”本身不会按增量重复累加。
4. 结算、汇总表写入、审计和缓存清理在服务事务中组织；官方结果确认和提交审核通过也通过事务调用重建。

### 待验证或补强

1. Redis 锁 TTL 固定 30 分钟。若大赛季重建超过 TTL，可能出现第二个进程再次取得锁；需要评估续租、任务超时和锁失效后的数据一致性。
2. 覆盖式重建与官网读取并发时，需要验证事务隔离和缓存清除的时序，避免用户短时间读到空榜、旧榜或统计与排行榜不同步。
3. `basket_stat_sync_record` 只保证“触发记录”幂等；若记录成功后结算失败，如何重试、标记失败和补偿需专项验证。
4. 官方数据修正、结果重开、弃赛裁定触发的重建范围需要验证是否足够覆盖赛季、阶段、小组及排行榜，不得只重算单场后留下关联榜单旧数据。

## 11. 待测试项

### 必测

1. 一场审核通过的比赛：总比分、分节比分、球队单场统计、球员单场统计、阶段积分榜、赛季统计和排行榜全部正确更新。
2. 未审核、已驳回、已重开、已取消比赛：不得进入积分榜、球队/球员统计、排行榜或官网结果页。
3. 同分球队：验证积分、相互战绩、相互得失分、净胜分等赛事规则配置的排序结果。
4. 弃赛、官方修正、结果重开：胜负、积分、赛季统计、正式结果版本、排行榜快照和官网展示均应重新一致。
5. 重复审核、重复确认、接口重试和重复重建：不得重复累计；`basket_stat_sync_record`、汇总行数和排行榜名次保持正确。
6. 赛季、阶段、小组隔离：其他 Event、其他阶段、其他小组数据不得混入；单场重建后整季相关榜单不应遗留旧值。
7. 官网：公开赛季可以展示真实数据，非公开赛季拒绝访问；无确认数据时不展示待审/模拟数据。

### 待联调/待测试

1. 平台维度：分别准备 PC、PS、Xbox 的 Event/比赛，确认平台隔离依赖赛季/比赛数据而非前端混合查询，并验证跨平台同名球队/球员不会合并。
2. 历史快照：球队改名/换 Logo、球员改显示名/转会后，历史积分榜、统计、排行榜、详情页是否仍展示赛事当时快照。
3. 锁与恢复：模拟 Redis 锁冲突、锁过期、结算中断和缓存清理失败，验证重试及用户可见数据。
4. 规则缺失：自动触发仅跳过积分榜时，后台和官网是否能明确提示“统计已更新、积分规则未配置”，避免误认为榜单已完整。
5. 重建页面的权限、操作日志、耗时、错误展示、空数据展示和大数据量分页性能。

## 12. 已知问题和风险

### P0

1. **历史快照链路不完整。** 积分榜、赛季统计和公开服务普遍用 `team_id`、`player_id` 回连长期球队/球员表获取名称和 Logo；长期资料变化会污染历史赛季展示，不符合 EventTeam/EventPlayer 快照原则。
2. **自动结算允许缺积分规则的部分成功。** 当前自动触发时若仅缺积分规则，会跳过积分榜但继续生成球队统计、球员统计和排行榜；若前台没有明确状态提示，会出现“排行榜存在但积分榜缺失”的业务不一致。
3. **结算批次未落地。** 需求列出了 `basket_data_settlement_batch`，但当前未见相应实体、Mapper 或写入记录；无法完整追溯每次重建的输入版本、范围、耗时、成功/失败状态和输出快照。

### P1

1. **排行榜仅按赛季级范围重建。** `BasketRankingServiceImpl` 固定以 `stage_id=0` 生成排行；接口查询虽接受阶段条件，但阶段级/小组级排行榜是否有数据需验证，不能默认已实现。
2. **积分榜重算是覆盖式删除/写入。** `basket_stage_standing` 在目标范围内被删除后重建，`snapshot_time` 不等于可回溯历史榜单；若需要“某日积分榜”或仲裁前后对比，应新增结算批次/快照版本。
3. **平台不是统计查询显式过滤条件。** 当前后台统计查询对象没有 `platformCode`；隔离主要依赖 Event/赛季和比赛归属。若一个赛季未来允许多平台混合，需要补齐平台维度字段、索引与查询条件。
4. **公开数据回读当前长期资料。** 除历史污染外，球队解散、文件删除或球员隐藏时可能造成历史榜单名称/Logo 缺失；需要快照兜底。

### P2

1. 统计重算未见专项单元/集成测试文件，尤其缺同分规则、弃赛、修正、并发重算和大赛季性能回归。
2. 榜单快照日期统一归一到当天零点；同一天多次结果修正会覆盖当日排行，无法直接展示日内变更历史。
3. 公开接口使用汇总表，不会返回原始审核版本和计算依据；运营排障需要额外的“从正式结果到汇总行”的可追溯诊断接口。

## 13. 下一步建议

### P0

1. 为积分榜、赛季统计和排行榜引入 EventTeam/EventPlayer 名称、Logo、所属球队等快照字段，或统一通过可版本化的赛事快照读取，禁止历史公开页直接依赖长期资料。
2. 收敛“规则缺失仍部分结算”的产品策略：要么阻止全部对外生效，要么在结算批次、后台和官网明确标记不完整状态并隐藏相关排行榜。
3. 落地 `basket_data_settlement_batch`：记录触发来源、输入正式结果版本、范围、锁令牌、开始/结束时间、状态、错误、输出行数与快照日期，并支持失败重试/补偿。

### P1
