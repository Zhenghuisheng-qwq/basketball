# 10. 小组赛/循环赛赛程生成

## 1. 业务定位

本模块负责在报名审核完成后，把某个运营赛季（下文称 Event）中的正式参赛球队转换为可执行的比赛计划。目标是先生成可复核的草稿赛程，再由有权限的管理员发布；比赛记录需要保留赛事、阶段、平台、EventTeam 以及球队名称/Logo 快照，避免长期球队资料变更污染历史赛程。

本文覆盖常规单循环与小组赛应有的排程边界，也如实记录当前代码已实现的范围：当前主策略是按 Event 下全部有效 EventTeam 生成单循环，尚未按小组过滤生成。

## 2. 最终业务规则

1. 报名审核通过并完成阵容锁定后，管理员可为当前 Event 或当前小组生成赛程；不得固定按 24 支球队计算。
2. 采用单循环时，`n` 支球队应生成 `n × (n - 1) / 2` 场真实比赛。偶数队每轮两两对战；奇数队加入虚拟 `BYE`，每轮仅一支真实球队轮空，不生成“没有对手”的比赛记录。
3. 同一真实球队在同一轮、同一比赛日均最多一场；主客队不得相同；同一 Event 的球队不得混入其他 Event 的赛程。
4. 默认比赛日为周二、周四、周六，默认时间段为 21:00、22:00；但排程必须以规则表配置为准，不能在 Java 代码中写死。时间段容量和分配方式也应配置化。
5. 系统先生成草稿批次及草稿比赛，管理员确认发布后才允许前台展示；已发布批次不得直接覆盖生成，草稿可以删除后重建。
6. 每场比赛至少绑定 `eventId/seasonId`、`stageId`、`platformCode`、主客 EventTeam 快照及主客长期 `teamId` 回溯字段；展示优先读取快照名称和 Logo。
7. 用户所述“奇数时 22 点循环队伍多一支”应理解为轮空或可配置的时间槽分配，不能把无对手占位生成成比赛。

## 3. 当前实现结论

### 代码确认

1. `BasketScheduleGenerateServiceImpl` 从 `basket_team_season_profile` 加载当前 Event 下已审核、状态为 `ACTIVE` 的 EventTeam 快照，按实际数量预览并生成，不存在固定 24 队算法。
2. `RoundRobinRoundBuilder` 使用 Berger/Circle Method。奇数球队会附加内部 `BYE` 标记并跳过该配对，因此不会落库无对手比赛；每轮同一 EventTeam 至多出现一次。
3. `ScheduleTimeAllocator` 从规则上下文读取星期、时间段、单槽容量和分配模式，为“一轮对应一个比赛日”的所有比赛赋时；容量不足会阻止生成。
4. 生成会创建 `basket_schedule_generate_batch` 草稿批次，并把每场 `basket_match` 初始为草稿/不公开。发布和下架会按批次同步比赛的 `publish_status`、`public_status`。
5. 比赛已写入 `home_event_team_id`、`away_event_team_id` 和名称/Logo 快照，已经不是只依赖长期 `teamId`。
6. 当前生成入口只按 `eventId` 读取全部有效 EventTeam；`stageId` 仅用于绑定比赛阶段，未见按 `basket_tournament_group` 或分组成员过滤。因此“按当前小组生成循环赛”尚未实现。
7. 生成校验只要求 EventTeam 已审核且 `ACTIVE`，没有单独核验 EventTeam/阵容的锁定状态；自动任务只按报名截止、无待审核及已存在赛程等条件触发，和“管理员允许并锁定阵容后”这一前置条件不完全一致。

### 用户手测记录

本次仅完成静态代码、SQL 与页面链路核对，未连接实际数据库、未通过浏览器操作生成或发布赛程；下列功能均不能记为已手测通过。

## 4. 相关数据库表

| 表/对象 | 当前用途 | 关键约束或说明 |
| --- | --- | --- |
| `basket_schedule_rule` | 排程规则主表 | 规则编码、版本、启用状态、单时间槽容量、分配模式。 |
| `basket_schedule_rule_weekday` | 比赛日配置 | 使用 ISO 星期值；V2 种子为周二、周四、周六。 |
| `basket_schedule_rule_time_slot` | 时间段配置 | V2 种子为 21:00、22:00；生成器从表中读取。 |
| `basket_schedule_generate_batch` | 生成批次 | 记录 Event、规则版本、EventTeam 数、场次数、草稿/发布状态。 |
| `basket_match` | 实际比赛赛程 | 绑定批次、Event、阶段、平台、规则、EventTeam、长期 teamId 与展示快照。 |
| `basket_match_team` | 比赛主客队辅助记录 | 当前持久化仅写 `team_id` 与主客标识，未见 EventTeam 外键字段。 |
| `basket_team_season_profile` | EventTeam | 当前候选球队来源，需属于目标 Event、已审核且 `ACTIVE`。 |
| `basket_tournament_stage` | 赛事阶段 | 生成时校验所选 `stageId` 归属目标 Event。 |
| `basket_tournament_group`、`basket_tournament_group_team` | 小组及成员 | 需求要求的小组排程范围应来源于此；当前生成服务未使用。 |
| `basket_tournament_round` | 赛事轮次 | 当前循环算法只写 `round_no`，未创建或关联 `round_id`。 |

`docs/sql/cnpa-schedule-v1-migration.sql` 建立规则、批次及比赛扩展字段；`docs/sql/cnpa-schedule-v2-migration.sql` 补充 `slot_capacity`、`allocation_mode` 并投放当前正式 V2 规则。V1 历史种子的时间槽包含 09:00、10:00、20:00、21:00，不等同于本需求指定的 21:00、22:00，不能把 V1 种子误认为已满足最终时段规则。

## 5. 后端实现

1. 管理接口位于 `BasketScheduleManageController`：提供 Event 上下文、预览、生成草稿、发布、下架、删除草稿及赛程列表/人工维护接口；分别使用 `basket:schedule:query/generate/publish/remove/list/add/edit/score` 权限。
2. `BasketScheduleGenerateServiceImpl.preview` 返回 EventTeam 数、预计场数、规则信息和平台；`generateDraftSchedule` 会锁定赛季行、阻止覆盖已发布赛程、根据需要删除旧草稿，再持久化批次和比赛。
3. `ScheduleEventTeamSupport.loadActiveSnapshots` 以 EventTeam 为候选范围，并构造名称/Logo 快照；`RoundRobinRoundBuilder` 同时在计划中保存 EventTeam ID、长期 teamId 及展示快照。
4. `RegularRoundRobinV1Strategy`、`RegularRoundRobinV2Strategy` 共用 `RegularRoundRobinScheduleGenerator`。规则策略工厂按规则编码和版本选择实现；定时任务默认寻找启用的 `REGULAR_ROUND_ROBIN/V2` 规则。
5. `validateGeneratedPlans` 校验主客 EventTeam 不相同、同批次配对不重复、同一时刻不冲突、同一轮不重复参赛，并通过 Mapper 检查已存在的 EventTeam 对阵与时间冲突。
6. 发布仅将选定批次状态更新为已发布，并批量公开该批次比赛；下架则把同批次设为未发布且不公开。删除草稿前会拒绝存在已发布赛程的 Event。

## 6. 前端实现

1. 管理页为 `basketball-admin-ui/src/views/cnpa/competition/schedule-manage/index.vue`，配套 API 为 `src/api/basket/scheduleManage.ts`。
2. 页面可选择赛事/运营赛季、阶段和规则，读取 Event 上下文，显示 EventTeam 数量、规则的比赛日和时间段，并提供生成前预览。
3. 页面提供生成草稿、发布、下架、删除草稿、赛程列表、手工新增/编辑比赛及比分录入入口；生成结果会回填批次信息。
4. 管理页可维护单场主客 EventTeam、阶段、轮次、时间、比赛状态和发布状态。该能力适合运营修正，但需要服务端持续保证 EventTeam 归属、时间冲突和已发布数据保护。
5. `basketball-web` 已存在公开比赛控制器，但本次未完成实际请求验证；草稿是否在所有官网赛程接口中都被 `public_status=1` / `publish_status=1` 严格过滤，需联调确认。

## 7. 状态机

### 赛程批次

`无批次` → `草稿（DRAFT）` → `已发布（PUBLISHED）` → `已下架（UNPUBLISHED）`。

- 草稿：生成后可在后台审核、编辑或删除，不应在前台展示。
- 已发布：对外公开；当前服务禁止在存在已发布批次时重新覆盖生成，也禁止用“删除草稿”删除。
- 已下架：比赛批次及比赛公开标识被关闭。是否允许重新发布、已发生比赛能否下架，需要按运营规则进一步明确。

### 单场比赛

生成时为“已排期 + 数据草稿 + 未发布/不公开”；发布后转为“已发布/公开”。比赛执行状态、比分审核和统计影响属于后续比赛执行链路，本篇不将其视为已验证的排程完成条件。

## 8. 权限规则

1. 查询 Event 上下文、规则和赛程列表需要 `basket:schedule:query` 或 `basket:schedule:list`。
2. 预览无需写库，应使用查询权限；生成草稿需要 `basket:schedule:generate`。
3. 发布与下架需要 `basket:schedule:publish`；删除草稿需要 `basket:schedule:remove`。
4. 人工新增、编辑及录分分别使用 `basket:schedule:add`、`basket:schedule:edit`、`basket:schedule:score`。
5. 服务端除权限外还校验 Event 存在、阶段归属和 EventTeam 归属/参赛资格；但锁定状态与小组归属目前不是生成前置校验，不能仅依赖页面隐藏按钮。

## 9. 并发与幂等

### 已实现保护

1. 自动/手动生成会对运营赛季执行 `selectByIdForUpdate`，并检查现有批次、现有比赛和已发布批次，降低同一 Event 并发生成重复赛程的风险。
2. 生成前校验 EventTeam 对阵是否已经存在，并校验同一 EventTeam 的同一开赛时间冲突；批次内也检查同轮/同时间重复参赛。
3. 强制重生成功前会软删除旧草稿比赛与草稿批次，且生成在事务中执行。

### 仍需验证或补强

1. 发布/下架更新没有版本号或条件更新（CAS）语义；两个管理员并发操作同一批次时需要验证最终状态、审计和前台可见性是否一致。
2. `countEventTeamPair` 的范围与“阶段/小组/规则版本”口径需联调确认。若只按 EventTeam 对过滤，未来双循环、不同阶段或重赛可能被误判为重复。
3. 数据库应补齐能与业务口径一致的唯一约束或锁策略，至少保证同一 Event/阶段/小组/轮次下不会落入重复配对或同队同日冲突数据。
4. 当前时间冲突校验以完全相同的开赛时间为核心；“同一比赛日最多一场”与同一天不同时间槽的限制是否完全被数据库查询覆盖，需要专项测试。

## 10. 已通过项

以下均为**代码确认通过**，不是用户手测结论：

1. 按实际 EventTeam 数量计算单循环场次，至少两队才允许生成。
2. 奇数球队通过 `BYE` 轮空，不生成无对手比赛；偶数/奇数均可使用 Circle Method 生成轮次。
3. 每轮球队最多出现一次，主客 EventTeam 相同会被拦截。
4. 比赛日、时间段、容量、分配模式均进入规则上下文，V2 默认种子为周二/周四/周六及 21:00/22:00。
5. 比赛落库绑定 Event、阶段、平台、主客 EventTeam 与球队名称/Logo 快照；历史展示具备不依赖长期球队名称的基础。
6. 草稿批次、发布、下架、删除草稿和操作审计链路已经具备；后台 `schedule-manage` 页面已有对应入口。

## 12. 已知问题和风险

### P0

1. **小组范围缺失。** 当前候选集为整个 Event 的有效 EventTeam，`stageId` 不改变候选集，未读取小组及小组成员表；若直接用于小组赛，会把不同小组球队排到一起。
2. **阵容锁定不是生成硬前置。** 需求要求锁定成功后生成，当前仅检查报名审核与参赛状态；自动任务在报名截止后也可能生成草稿，需要避免把未完成锁定的阵容固化为赛程。
3. **淘汰赛未落在当前策略范围。** 现有规则是单循环，不能把“待测淘汰赛生成”误记为已实现能力。

### P1

1. **V1 配置与最终默认时段不一致。** V1 迁移种子并非仅 21:00、22:00；当前自动任务使用 V2。运营侧需明确 V1 的历史定位、启用状态和可选范围，避免管理员误选。
2. **轮次实体未完全绑定。** 循环算法只写 `round_no`，未创建/关联 `basket_tournament_round.round_id`；若后续依赖轮次表管理分组、晋级或展示，需要补齐。
3. **`basket_match_team` 只保存长期 `team_id`。** 主表已保存 EventTeam 快照，但辅助表未见 EventTeam 标识；后续若比赛名单、统计或资格校验从该表回溯，可能重新引入跨赛事/历史污染风险。
4. **下架与已执行比赛的边界未定义。** 已有比分、审核结果或排行榜影响后是否允许下架，当前文档和生成服务未见明确业务限制。

### P2

1. 当前分配器允许同一时间槽容纳多场比赛，容量默认为 12；若业务实际只有一块场地，必须通过场地维度或把容量配置为 1 限制，否则会排出同时间并行多场。
2. 页面允许人工编辑/新建赛程，需持续验证服务端对已发布比赛、EventTeam 快照和时间冲突的保护，不能以界面可操作性替代后端约束。
