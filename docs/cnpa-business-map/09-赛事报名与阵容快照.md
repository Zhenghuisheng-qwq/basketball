# 09-赛事报名与阵容快照

> 范围：球队报名、报名阵容编辑、报名审核、平台与队长授权校验、报名撤回/驳回重提、EventTeam/EventPlayer 快照和阵容锁定。单届赛事转会/补员见 `07-退出球队踢人转会期.md`，赛事基础状态见 `08-赛事赛季阶段规则.md`。

## 1. 业务定位

赛事报名是长期球队进入某个具体赛事运营赛季的入口，阵容快照是把“报名时的球队和球员信息”固化为本届赛事对象的边界层。

系统中对应两类对象：

1. **报名申请**：`basket_tournament_registration` 与 `basket_tournament_registration_player`，保存球队申请参加某赛事赛季时的联系人、平台、报名阵容和审核过程。
2. **正式参赛快照**：`basket_team_season_profile` 与 `basket_tournament_season_roster`，分别对应本届赛事球队（EventTeam）和本届赛事球员阵容（EventPlayer）。审核通过后由后台事务生成，后续比赛、统计和历史展示应优先读取这些快照。

核心链路为：

```text
已认证长期球队
  → 具备目标赛事/赛季有效队长授权
  → 在报名窗口内创建报名草稿
  → 选择 5–8 名当前球队成员并完成平台资格校验
  → 队长提交报名
  → Admin 重新校验并审核
  → 生成 EventTeam / EventPlayer 快照
  → 阵容锁定
  → 进入阶段、分组、赛程和比赛数据链路
```

## 2. 最终业务规则

依据 `核心业务/核心实现.md`，最终规则如下：

1. 没有有效长期球队不能提交球队赛事报名。
2. 已加入球队但不是队长的普通成员可以查看赛事信息，但不能代表球队提交报名。
3. 队长可以申请加入目标赛事，但必须具备该赛事/赛季有效队长授权；授权哪个赛事，只能报名哪个赛事。
4. 队长报名时必须校验球队完整性、球队认证状态、成员关系、阵容人数和赛事平台资格。
5. 报名阵容人数至少 5 人、最多 8 人；不要求 PG/SG/SF/PF/C 五个位置全部齐全。
6. 报名阵容中必须有且只有一名场上队长，球队队长必须在报名阵容中并标记为场上队长；5V5 赛制首发人数必须为 5 人。
7. 报名审核中允许修改报名资料和阵容；审核通过后不能直接修改。
8. 赛事球队或阵容锁定后，如需调整，必须进入受控的阵容变更审核流程，不能直接改写已锁定快照。
9. 报名驳回后可以重新编辑和提交，但必须仍在报名窗口内，并重新经过完整校验。
10. 报名审核通过后生成 EventTeam 快照和 EventPlayer 快照；快照记录本届赛事所需的球队名称、球员昵称、头像、平台、游戏 ID、位置和阵容角色等信息。
11. 阵容锁定后，长期球队改名、换队长、成员离队或球员资料变化不能污染已经生成的赛事历史数据。
12. 已报名的平台组应从可报名列表移除，但历史报名记录和审核记录仍必须可查询。
13. 同一球队、同一赛事赛季、同一参赛平台不能重复报名；重复点击、并发提交和重复审核必须稳定拦截。
14. Open 个人报名是独立于球队报名的流程；当前代码和第四批结果已存在 Open 报名/审核及 `event_team_id = NULL` 的赛季阵容来源，但它不应与球队报名的 EventTeam 生成混为一谈，是否作为正式产品入口需单独确认。

## 3. 当前实现结论

| 功能点 | 已实现 | 部分实现 | 未实现/差异 | 依据 | 结论 |
|---|---|---|---|---|---|
| 队长查看可报名赛事 | ✓ |  |  | `pageAvailableSeasons` | 按球队、队长授权、赛事状态、报名窗口、平台和名额过滤 |
| 非队长查看赛事信息 | ✓ |  | 提交权限需保持后端拒绝 | `pageMemberAvailableSeasons`、报名权限校验 | 普通成员可查看/提醒队长，但不能代表球队报名 |
| 创建报名草稿 | ✓ |  |  | `createDraft` | 要求当前球队成员关系、有效队长授权、目标赛事开放和未重复报名 |
| 报名资料编辑 | ✓ |  | 最终规则要求审核中可改，当前 `REVIEWING` 不可改 | `assertRegistrationEditable` | 当前仅 `DRAFT/REJECTED` 可编辑 |
| 报名阵容编辑 | ✓ |  | 同上 | `saveRoster` | 当前审核中和已通过均被编辑状态拦截 |
| 报名提交 | ✓ |  |  | `submit` | `DRAFT/REJECTED → REVIEWING`，提交前重新验证阵容与处罚 |

| 驳回后重新报名 | ✓ |  | 需验证原审核记录是否完整展示 | `REJECTED.canEdit/canSubmit` | 驳回后可再次编辑并提交 |
| 队长授权校验 | ✓ |  |  | `requireValidQualificationForEvent`、`selectActiveGrantForEvent` | 提交和审核均校验授权与球队/赛季匹配 |
| 球队认证校验 | ✓ |  |  | `assertTeamRegistrationEligible`、Admin `validateBeforeApprove` | 未审核通过的长期球队不能报名/通过 |
| 平台开放和游戏账号校验 | ✓ |  |  | `EventPlatformSupport`、平台账号 Service | 报名平台必须开放；每名阵容球员必须有对应平台有效账号 |
| 阵容人数/队长/首发校验 | ✓ |  |  | `validateSubmitRoster`、Admin `validateBeforeApprove` | Web 提交和 Admin 审均有复核 |
| Admin 报名审核 | ✓ |  | 待真实联调 | `BasketRegistrationAuditController/ServiceImpl` | 支持列表、详情、通过、驳回和审核记录 |
| 审核通过生成 EventTeam/EventPlayer | ✓ |  |  | `BasketParticipationGenerationServiceImpl` | 事务内生成快照并锁定阵容 |
| 审核日志 | ✓ |  |  | `basket_tournament_registration_audit` | 记录通过、驳回、生成快照、自动锁定等动作 |
| 阵容锁定 | ✓ |  | 解锁能力存在，需限制运营使用 | EventTeam Admin Service | 审核通过自动锁定，也提供 Admin 锁定/解锁/修复接口 |
| 锁定后提交修改申请 |  | ✓ | 当前报名详情返回 `canRequestRosterChange=false` | Web 报名 Service、RosterChange Service | 赛事阵容另有转会/补员流，但未与报名详情的“申请修改”入口统一 |
| 已报名平台从可报名列表移除 | ✓ |  | 需联调多状态记录 | `loadRegisteredPlatformCodes` | 已有有效报名时不再出现在可报名列表 |
| Open 个人报名 | ✓/独立流程 |  | 产品开关与正式展示边界待确认 | `OpenRegistrationBusinessController`、batch4 | 可生成无 `event_team_id` 的赛季阵容，不等同球队报名 |

**结论：** 球队报名、审核、平台/队长/阵容校验和快照生成已经有较完整实现；最明显的规则差异是“最终要求审核中允许修改”，而当前 Web Service 的 `canEdit()` 只允许草稿和驳回状态。另一个边界是审核通过后确实自动锁定，但 Admin 仍存在解锁接口，且报名详情没有统一的阵容变更申请入口，需在后续迭代中收敛。

## 4. 相关数据库表

| 表/对象 | 作用 | 关键字段 | 当前结论 |
|---|---|---|---|
| `basket_tournament_registration` | 球队报名主记录 | `season_id`、`team_id`、`platform_code`、队长、状态、提交/审核/撤回时间 | 记录一支长期球队对一个赛事赛季的平台报名 |
| `basket_tournament_registration_player` | 报名阵容 | `registration_id`、`team_member_id`、`player_id`、首发、场上队长、校验状态 | 编辑时逻辑删除旧阵容，再插入当前草稿阵容 |
| `basket_tournament_registration_audit` | 报名审核历史 | 前后状态、动作、审核人、审核说明、审核时间 | 通过、驳回、生成快照、自动锁定均可留痕 |
| `basket_team` | 长期球队 | 球队名称、Logo、审核状态、长期队长等 | 报名只引用长期球队，不直接把长期资料当历史快照 |
| `basket_team_member` | 长期球队成员 | `team_id`、`player_id`、有效成员状态 | 报名阵容只能选择当前有效成员 |
| `basket_tournament` | 具体赛事 | 平台、发布状态、报名/比赛时间 | 赛事平台和发布状态参与报名校验 |
| `basket_tournament_season` | 赛事运营赛季 | 报窗口、赛季状态、报名开关、最大队伍数、5–8 人限制 | 报名的直接赛季上下文 |
| `basket_tournament_season_platform` | 赛季开放平台 | `season_id`、`platform_code`、`platform_status` | `requireOpenPlatform` 校验报名平台 |
| `basket_captain_qualification` | 赛事/赛季队长授权 | 授权人、球队、`season_id`、状态、有效期 | 报名创建、提交、审核和快照生成均需要匹配授权 |
| `basket_player_profile` | 球员档案 | 认证状态、昵称、位置等 | Admin 审核确认球员认证有效 |
| `basket_player_platform_account` | 球员平台游戏账号 | 平台、展示/规范 ID、账号状态 | 按赛事平台确认账号 `ACTIVE` |
| `basket_team_season_profile` | EventTeam 实际表 | 赛事球队编号、报名来源、球队名称/Logo/简介/平台/队长快照、参赛状态、锁定状态 | 报名审核通过后生成正式赛事球队快照 |
| `basket_tournament_season_roster` | EventPlayer 实际表 | 球员/会员、报名来源、昵称/头像/平台/游戏 ID/位置快照、角色、状态、锁定、`active_slot` | 报名审核通过后生成正式赛事球员快照 |
| `basket_tournament_open_registration` | Open 个人报名 | 个人报名赛季、球员、状态等 | 独立于球队报名，正式阵容可没有 EventTeam |

关键数据库约束：

1. `uk_registration_season_team_platform (season_id, team_id, platform_code, is_delete)` 防止同一球队、同一赛季、同一平台重复报名。
2. `uk_registration_no` 防止报名编号重复。
3. `uk_event_team_registration (registration_id, is_delete)` 防止同一审核通过报名重复生成 EventTeam。
4. `uk_season_roster_active_slot (active_slot)`，其中 `active_slot = {seasonId}:{playerId}`，防止同一球员在同一赛季同时存在多条有效正式阵容。
5. 报名球员表和正式阵容表都保存 `team_id`/`event_team_id` 以及来源报名 ID，使报名草稿、正式快照和后续变更可以追溯。

## 5. 后端实现

### 5.1 Web 端报名流程

`TeamRegistrationBusinessController` 提供以下业务接口：

| 接口 | 作用 | 主要权限/校验 |
|---|---|---|
| `GET /basket/team/{teamId}/registration/available-season/page` | 查询队长可报名赛事 | 当前用户须是球队队长或有目标赛季有效授权 |
| `POST /basket/team/{teamId}/registration/draft` | 创建报名草稿 | 有效球队成员、队长授权、球队审核通过、赛事开放、平台开放、未重复报名 |
| `GET /basket/team/registration/{registrationId}` | 报名详情 | 只能由该报名对应的队长查看管理 |
| `PUT /basket/team/registration/{registrationId}` | 更新联系人和备注 | 当前状态可编辑且未锁定 |
| `PUT /basket/team/registration/{registrationId}/roster` | 保存报名阵容 | 当前状态可编辑、成员属于球队、阵容 5–8 人、不重复 |
| `POST /basket/team/registration/{registrationId}/submit` | 提交报名 | 重新校验报名窗口、球队、阵容、处罚和平台资格 |
| `POST /basket/team/registration/{registrationId}/withdraw` | 撤回报名 | 仅 `SUBMITTED/REVIEWING` 且未超过报名截止时间 |
| `DELETE /basket/team/registration/{registrationId}/draft` | 删除草稿 | 仅 `DRAFT` |
| `GET /basket/team/registration/{registrationId}/audit-record/page` | 查看审核记录 | 仅报名队长 |
| `GET /basket/season/{seasonId}/platforms` | 查询赛季开放平台 | 只读 |
| `GET /basket/team/registration/{registrationId}/roster/candidates` | 查询可选成员 | 仅报名队长；按当前赛事平台过滤有效账号 |

创建草稿时的后端顺序为：

1. 确认当前用户仍有有效球队成员关系。
2. 确认本人是球队队长，或具有绑定该球队和目标赛季的有效队长授权。
3. 确认目标运营赛季和赛事存在、赛事已发布、报名时间有效、球队报名开关开启且赛季未结束/关闭/取消。
4. 通过 `EventPlatformSupport.requireOpenPlatform` 确认请求平台是该赛季开放平台。
5. 查询阻断状态的既有报名；`DRAFT/SUBMITTED/REVIEWING/APPROVED/REJECTED` 都会阻止再次创建，撤回/取消等终态才可能重新申请。
6. 写入 `DRAFT` 主记录，报名阵容在后续保存接口中写入。

### 5.2 报名阵容校验

保存阵容时，Service 会：

1. 先通过 `assertRegistrationEditable` 判断报名未锁定且当前状态允许编辑。
2. 校验人数，默认最小 5 人、最大 8 人；赛季配置会被限制在平台常量边界内。
3. 校验传入 `teamMemberId` 不重复，并确认每名成员属于报名球队、仍为当前有效成员。
4. 逻辑删除该报名下旧的有效报名球员行，再按当前顺序插入新的报名球员行。
5. 保存 `player_id`、`member_id`、`team_member_id`、阵容角色、球衣号、首发和场上队长标记，初始校验状态为 `PENDING`。

提交报名时会再次校验：

1. 状态只能为 `DRAFT` 或 `REJECTED`。
2. 目标赛事仍在报名时间内、赛事已发布、球队报名已开放。
3. 阵容人数在 5–8 人范围内。
4. 阵容中必须且只能有一名场上队长，且长期球队队长必须在阵容中并标记为场上队长。
5. 首发人数必须为 5 人。
6. 阵容成员没有重复，仍属于当前球队且为有效成员。
7. 阵容球员没有当前赛季已经生效的正式赛事阵容。
8. 阵容成员不处于当前赛季有效处罚期。
9. 通过后将报名状态以条件更新方式改为 `REVIEWING`，并发送“报名审核中”站内消息。

### 5.3 Admin 审核

Admin `BasketRegistrationAuditController` 提供：

```text
GET  /basket/registrationAudit/list
GET  /basket/registrationAudit/{id}
POST /basket/registrationAudit/{id}/approve
POST /basket/registrationAudit/{id}/reject
GET  /basket/registrationAudit/{id}/audit-record/list
```

审核通过前会重新校验：

1. 报名球队存在且已通过球队认证。
2. 报名阵容非空，人数符合赛季和 5–8 人边界。
3. 报名队长授权仍为 `ACTIVE`，且会员、球队、赛季均与报名一致。
4. 阵容球员不重复、确实属于长期球队、球员认证通过。
5. 每名球员有目标赛事平台的有效游戏账号或兼容的已确认平台资料。
6. 球员没有同赛季其他球队的有效正式阵容。
7. 球队、球员或账号没有当前赛季生效的处罚/限制。
8. 赛季报名队伍数没有超过 `max_team_count`；审核时对赛季行使用 `selectByIdForUpdate`。

通过流程使用报名状态 CAS：

```text
REVIEWING / SUBMITTED
          │ Admin approve
          ▼
      APPROVED
          │ 同一事务
          ├─写报名审核记录 APPROVE
          ├─生成 EventTeam
          ├─生成 EventPlayer/SeasonRoster
          ├─写 GENERATE_EVENT_TEAM / GENERATE_EVENT_PLAYER
          ├─写 AUTO_LOCK_ROSTER
          └─发送审核通过通知
```

驳回流程要求填写驳回原因，以条件更新将 `REVIEWING/SUBMITTED → REJECTED`，写审核记录并通知报名队长。重复审核通过或驳回会因状态不再匹配而失败。

## 6. 前端实现

| 前端区域 | 文件/页面 | 当前能力 | 结论 |
|---|---|---|---|
| Web 报名 API | `basketball-web-ui/src/api/teamRegistration.ts` | 可报名赛事、草稿、详情、资料、阵容、提交、撤回、删除、审核记录、平台、候选成员 | 已对接真实 Web 接口 |
| Web 报名页面 | `views/account/events/TeamRegistrationFlow.vue` 等 | 队长选择赛事、填写信息、选择成员、设置首发/场上队长并提交 | 需以接口返回的状态和权限为准 |
| Web 我的赛事 | `TeamRegistrationBusinessController` 的 `my-events` 接口 | 查询公开赛事和用户/球队赛事记录 | 普通成员可查看，不获得报名写权限 |
| Admin 报名审核 | `basketball-admin-ui/src/views/cnpa/participation/team-registration/index.vue` | 查询、查看详情、通过、驳回、查看报名阵容/审核信息 | 使用 `basket:registrationAudit:*` 权限 |
| Admin 正式赛事球队 | `official-teams/index.vue`、`eventTeam.ts` | 查看 EventTeam、查看 EventPlayer、锁定/解锁/修复阵容、调整参赛状态 | 是快照运维入口，不是长期球队编辑入口 |
| Open 个人报名 | `OpenRegistrationBusinessController` 及 Open 页面 | 独立提交/审核个人报名 | `event_team_id` 可为空，不能当作球队报名结果 |

前端必须遵循以下边界：

1. 非队长可以看到赛事详情或球队赛事记录，但不能仅靠隐藏按钮获得报名权限；后端必须拒绝直接调用报名写接口。
2. 报名详情的 `canEdit`、`canSubmit`、`canWithdraw`、`rosterLocked` 只能作为展示提示，最终仍以后端状态条件更新为准。
3. 已通过报名的快照页面必须展示 EventTeam/EventPlayer 的快照字段，不应直接读取长期球队当前名称、头像和球员当前游戏 ID 替代历史数据。
4. Admin 的“解锁阵容”是高风险运维操作，应仅对有明确权限和审计要求的管理员开放，不能成为常规修改报名的入口。

## 7. 状态机

### 7.1 报名主状态

```text
创建草稿
   │
   ▼
DRAFT（草稿） ── submit ─→ REVIEWING（审核中） ── approve ─→ APPROVED（已通过）
   │                         │   │                         │
   │ delete                  │   └─ reject ─→ REJECTED     └─ 自动生成并锁定快照
   │                         │
   └─────────────────────────└─ withdraw ─→ WITHDRAWN（已撤回）

REJECTED（已驳回） ── edit/submit ─→ REVIEWING
```

代码枚举还定义了 `SUBMITTED`、`CANCELLED`：

1. Web 提交当前直接将 `DRAFT/REJECTED → REVIEWING`；`SUBMITTED` 主要兼容历史状态，并在用户展示侧按“审核中”处理。
2. `SUBMITTED/REVIEWING` 可撤回；`DRAFT` 可删除；`DRAFT/REJECTED` 可编辑和再次提交；`APPROVED` 被视为锁定，不可直接编辑。
3. 当前没有长期保留的“审核中可编辑”路径，这与最终规则存在差异，需明确是改变代码还是调整需求。

### 7.2 报名球员校验状态

```text
PENDING（待校验） ── Web/Admin 复核通过 ─→ PASS（通过）
         └──────────────────────────────→ FAIL（不通过）
```

Admin `revalidate` 会根据球员认证、平台账号、纪律限制等更新每名报名球员的校验状态；只要存在非 `PASS`，报名不能审核通过。

### 7.3 EventTeam 与 EventPlayer 状态

```text
报名 APPROVED
      │
      ├─ BasketTeamSeasonProfile / EventTeam：ACTIVE + LOCKED
      └─ SeasonRoster / EventPlayer：ACTIVE + LOCKED
```

之后赛事阵容变更可使旧 `SeasonRoster` 进入 `TRANSFERRED_OUT` 等终态并插入新有效行；这属于赛事阵容变更流程，不应直接修改初始报名记录的历史内容。

## 8. 权限规则

| 操作 | 当前权限与归属校验 | 终要求 | 当前风险 |
|---|---|---|---|
| 查看可报名赛事 | 当前用户须是球队成员；队长或有有效赛事授权时返回可报名列表 | 普通成员可查看赛事信息，队长/授权人才能报名 | 空列表原因需保持可理解 |
| 创建草稿 | 本队队长或绑定本队的有效队长授权 | 只能代表授权球队、授权赛事报名 | 需并发验证授权过期时不能创建 |
| 编辑报名/阵容 | 只能报名队长；状态可编辑且未锁定 | 审核中按最终规则应允许编辑 | 当前 REVIEWING 被拒绝 |
| 提交报名 | 只能报名队长；需目标赛事授权、窗口和全部校验 | 后端拒绝未授权/已结束/非本队请求 | 应覆盖过期队长权限 |
| 撤回报名 | 只能报名队长；仅提交/审核中且未截止 | 审核通过后不能随意撤回 | 当前已按状态和窗口限制 |
| Admin 审核 | `basket:registrationAudit:list/query/audit` | 仅赛事运营管理员可审核 | 需实际菜单库验证权限落库 |
| 生成/锁定 EventTeam | 审核服务事务；Admin 另有 `basket:eventTeam:edit` 锁定/解锁/修复 | 审核通过自动锁定；解锁只能特殊运维 | 解锁入口可能绕过常规变更审核 |
| 查看审核记录 | 报名队长可查本人球队报名；Admin 可查审核详情和全部记录 | 记录不可被普通用户修改 | Web/Admin 两套读入口需保持一致 |
| Open 个人报名 | 独立个人流程 | 只有明确开放的赛季允许 | 需与球队报名展示和快照统计隔离 |

## 9. 并发与幂等

| 场景 | 当前控制 | 风险与要求 |
|---|---|---|
| 重复点击创建草稿 | Service 先查阻断状态；数据库有 `(season,team,platform,is_delete)` 唯一键 | 查询与插入之间仍需依赖数据库唯一键，异常应转换为稳定业务提示 |
| 同队同赛季并发报名 | Service `assertNoExistingRegistration` + 唯一键 | 验证只有一条有效报名，不能产生两条草稿或审核记录 |
| 重复保存报名阵容 | 事务内逻辑删除旧球员并重插 | 并发保存可能互相覆盖，需确认是否应加报名行锁或版本号 |
| 提交与编辑并发 | 编辑状态判断、提交状态条件更新 | 需验证提交成功后并发编辑不会写入已锁定/审核中数据 |
| 提交与撤回并发 | 提交和撤回均带状态条件更新 | 最终只能是一个稳定终态，不能同时发送相互矛盾的通知 |
| 两个 Admin 同时审核 | `updateStatusIfMatch` 只允许一个状态更新成功；赛季审核使用 `selectByIdForUpdate` | 需验证快照生成、审核记录和通知只执行一次 |
| 审核通过与快照生成 | 在事务内 CAS 更新、生成 EventTeam/EventPlayer、写锁定日志 | 任一环节失败必须整体回滚，不能留下 APPROVED 但无快照或快照未锁定 |
| 同赛季同球员重复正式阵容 | Service count + `active_slot` 唯一键 | 并发审核不同球队报名时需验证唯一键和事务回滚 |
| 审核通过时赛季最后名额 | 赛季行锁后统计已通过数量 | 需确认统计口径包含哪些终态，以及报名撤回/驳回是否释放名额 |
| 队长授权过期与报名并发 | 创建、提交、审核均有授权校验 | 需确保审核阶段不会使用已过期授权；快照必须记录授权来源 |
| EventTeam 解锁与阵容变更并发 | Admin 解锁更新锁定字段；变更 Service 读取锁定状态 | 需防止解锁窗口让普通报名写接口或转会流程绕过审核 |

## 12. 已知问题和风险

1. **P0：最终规则与当前编辑状态不一致。** 需求要求“报名审核中允许修改”，但 `TournamentRegistrationStatusEnum.canEdit()` 只允许 `DRAFT` 和 `REJECTED`，`assertRegistrationEditable` 会拒绝 `REVIEWING` 编辑。需要产品确认以代码还是需求为准。
2. **P0：审核通过后存在 Admin 解锁接口。** `BasketEventTeamAdminController` 提供 `unlock-roster`；若解锁后缺少严格权限、原因、审批和再次锁定规则，可能绕过“锁定后修改必须审核”的最终规则。
3. **P0：报名详情未接入统一阵容变更申请。** `applyRegistrationPermissionFields` 固定 `canRequestRosterChange=false`；现有 `RosterChangeBusinessService` 面向正式赛事阵容的转会/补员/队长移交，尚未成为球队报名页面的统一“修改申请”入口。
4. **P0：审核通过前后业务对象容易混用。** `basket_tournament_registration_player` 是报名草稿/审核阵容，`basket_tournament_season_roster` 才是正式赛事球员快照；后续接口不得直接把报名行当作比赛阵容。
5. **P1：审核通过后生成快照是“审核状态更新后再生成”。** 代码处于同一事务并有回滚保护，但需要实际验证异常时不会留下 `APPROVED` 无 EventTeam、EventTeam 无完整 EventPlayer 或锁定状态不一致的数据。
6. **P1：重复报名防重同时依赖 Service 查询和数据库唯一键。** 数据库唯一键包含 `is_delete`，逻辑删除/撤回终态的重新报名语义需要在各查询和唯一键行为上统一验证。
7. **P1：同赛季球员有效阵容防重是“查询 + active_slot 唯一键”。** 两个审核事务并发时，必须确认唯一键冲突会触发完整事务回滚，不能留下部分审核日志或通知。
8. **P1：平台账号兼容逻辑仍有历史回退。** Admin 审核允许读取有效平台账号，也兼容球员档案上的历史 `gameAccount/gameTerminal`；需要明确生产是否允许旧字段作为正式报名资格。
9. **P1：赛事平台变更与已报名记录的关系需冻结。** 若运营赛季平台在已报名后修改，已报名的 `platform_code` 和 EventPlayer 平台快照应保持历史一致，同时新报名可见性不能产生混乱。
10. **P1：报名队伍上限与报名状态口径需要统一。** 审核通过时按赛季锁行并统计已通过数量，但撤回、驳回、取消和历脏数据如何计数需要固定规则。
11. **P2：Open 个人报名的产品边界未完全统一。** 当前已存在独立实现和表，但其 EventTeam 为空，公开赛事、分组、比赛和统计是否允许与球队报名混合，需要在后续链路中明确。
12. **P2：快照读取尚未覆盖全部前台页面。** 第四批结果已指出部分官网赛程、比赛名单、历史荣誉页面仍可能读取长期档案；若未统一读取 EventTeam/EventPlayer，历史仍可能被长期资料污染。
