# 08-赛事、赛季、阶段、规则

> 范围：赛事基础配置、顶层赛季与赛事运营赛季、平台隔离、报名窗口、赛事/赛季/阶段状态、规则版本和后台管理。报名提交、阵容快照、分组赛程、比赛执行分别见后续文档。

## 1. 业务定位

赛事域是平台运营的配置骨架，负责定义“在哪个赛季、以什么平台、在什么时间、按什么阶段和规则举办比赛”。它向球队报名、阵容快照、分组赛程、比赛录入、积分统计和公开展示提供共同的上下文。

当前代码并非单一“赛事 → 赛季”模型，而是存在两层赛季：

```text
basket_competition_season（顶层赛季，例如 2026 CNPA 赛季）
        │ 1:N
        ▼
basket_tournament（具体赛事，绑定唯一比赛平台和赛事时间）
        │ 1:1/1:N
        ▼
basket_tournament_season（赛事运营赛季，承载报名、阵容、转会和阶段）
        ├── basket_tournament_season_platform（开放平台）
        ├── basket_tournament_stage（阶段）→ round/group/group_team
        ├── basket_tournament_rule（规则版本）
        └── basket_tournament_award_config（奖项配置）
```

后台创建具体赛事时，会自动创建一条对应的运营赛季并同步赛事平台。因此本文保留这套现有模型，不把 `basket_competition_season`、`basket_tournament` 和 `basket_tournament_season` 强行合并或替换。

## 2. 最终业务规则

依据 `核心业务/核心实现.md`，最终规则如下：

1. 后台可以创建、编辑、发布和管理赛事。
2. 后台可以创建赛季，并在赛季下配置赛事运行信息。
3. 后台可以创建赛事阶段，并按阶段组织后续分组、轮次和赛程。
4. 后台可以创建赛事规则，规则应具备版本、生效时间、状态和公开展示能力。
5. 创建赛事必须区分平台；平台标准值为 `PC`、`PS`、`XBOX`。
6. 不同平台应对应不同赛事及其规则，不能让不兼容的平台报名、阵容或比赛数据混用。
7. 同一长期球队可以同时参加多个赛事，但每次报名都要满足目标赛事/赛季的平台、报名窗口、队长授权和报名规则；“一人一长期球队”不等于“一队只能参加一个赛事”。
8. 赛事、赛季、阶段、分组、轮次和规则的关系应以现有代码为准，文档需清楚标识两层赛季模型。
9. 后台需能控制公开状态、报名时间、赛季状态、当前阶段和规则版本；状态变更不得绕过数据依赖。

核心需求文档记录的用户手测结果为：后台创建赛季、赛事、赛事阶段、赛事规则通过；创建赛事时平台区分通过；队长具备对应授权时球队可同时参加多个赛事通过。本文保留为“用户手测记录”，未在本次文档编写中重新执行页面联调。

## 3. 当前实现结论

| 功能点 | 已实现 | 部分实现 | 未实现/待确认 | 依据 | 结论 |
|---|---|---|---|---|---|
| 顶层赛季 CRUD | ✓ |  | 状态无专用流转接口 | `BasketCompetitionSeasonController/ServiceImpl` | 可建、改、删顶层赛季；归档后禁止修改 |
| 具体赛事 CRUD | ✓ |  |  | `BasketTournamentController/ServiceImpl` | 创建时要求所属顶层赛季、时间和单一平台 |
| 创建赛事自动生成运营赛季 | ✓ |  | 需确认历史数据是否都已补齐 | `createOperationalSeason` | 赛事创建后自动插入 `basket_tournament_season` |
| 赛事平台同步 | ✓ |  | 无独立平台开关管理接口 | `syncEventPlatform`、`season_platform` | 赛事平台写入运营赛季开放平台；创建时禁止 `ALL` |
| 运营赛季 CRUD 与状态流转 | ✓ |  | `publish` 当前为空实现 | `BasketSeasonController/ServiceImpl` | 支持报名开关、开赛、结束；状态变更使用条件更新 |
| 赛事发布/下架/关闭 | ✓ |  | 关闭未见级联关闭运营赛季/阶段 | `BasketTournamentServiceImpl` | `DRAFT/DISABLED → ACTIVE`，可下架或关闭 |
| 阶段 CRUD 和状态流转 | ✓ |  | 未见自动维护赛季 `current_stage_id` | `BasketTournamentStageServiceImpl` | 草稿阶段可编辑/激活/删除；激活后可结束或取消 |
| 阶段时间与赛季边界校验 | ✓ |  | 创建/编辑期不强制赛季边界，激活时才检查 | `validateStageTimes` | 激活前会校验阶段时间落在运营赛季内 |
| 规则 CRUD | ✓ |  | 未见版本发布、冻结、回滚和规则生效仲裁 | `BasketTournamentRuleServiceImpl` | 可按运营赛季维护规则记录 |
| 规则唯一性 | ✓/数据库 |  | 应验证实际迁移/基线库 | `uk_rule_season_type_version` | 同运营赛季、同规则类型、同版本不能重复 |
| 公开状态字段 | ✓/字段 |  | 发布状态与公开读取联动需联调 | tournament/season/stage 的 `public_status` | 后台可配置字段，但各读侧过滤规则需继续核查 |
| 后台页面和按钮权限 | ✓ |  | 需实际菜单库验证 | Admin UI `cnpa/event/*`、`@PreAuthorize` | 赛事、赛季、阶段、规则均有页面和权限点 |

**结论：** 赛事、运营赛季、阶段、规则的后台基础管理已存在，核心创建/状态接口和页面也已具备；当前最大的理解风险是“两层赛季”与“创建赛事自动创建运营赛季”。此外，`current_stage_id`、规则版本启用、平台关闭、赛事关闭级联以及公开状态读侧约束未见完整统一实现，不能写成已完全闭环。

## 4. 相关数据库表

| 表/对象 | 层级与用途 | 关键字段/约束 | 当前结论 |
|---|---|---|---|
| `basket_competition_season` | 顶层赛季 | `season_no`、`season_year`、`season_name`、起止时间、状态、公开状态 | 由 `cnpa-competition-season-migration.sql` 引入；一个顶层赛季可关联多个赛事 |
| `basket_tournament` | 具体赛事主表 | `competition_season_id`、`game_terminal`、报名/比赛时间、`tournament_status`、`public_status` | 赛事必须绑定顶层赛季与单一平台；创建时默认为草稿 |
| `basket_tournament_season` | 赛事运营赛季 | `tournament_id`、报名/赛季时间、阵容人数、报名/转会/补员开关、`season_status`、`current_stage_id` | 报名、阵容、阶段和转会等后续业务的直接所属对象 |
| `basket_tournament_season_platform` | 运营赛季开放平台 | `season_id`、`platform_code`、`platform_status`；`uk_season_platform` | 创建/修改赛事时按赛事平台 upsert 为开放；未见单独关闭平台后台接口 |
| `basket_tournament_stage` | 赛事阶段 | `season_id`、阶段类型/赛制、时间、顺序、状态、晋级规则、公开状态；阶段编号唯一 | 支持草稿、进行中、已结束、已取消 |
| `basket_tournament_round` | 阶段内轮次 | `season_id`、`stage_id`、轮次顺序、局数、状态 | 服务于后续赛程生成与比赛组织 |
| `basket_tournament_group` | 段内分组 | `season_id`、`stage_id`、分组编号/名称、状态 | 服务于小组/循环赛组织 |
| `basket_tournament_group_team` | 分组与参赛队关系 | `group_id`、`team_id` 等 | 基线表仍以长期 `team_id` 建模；正式赛事球队快照关联边界需在赛程文档复核 |
| `basket_tournament_rule` | 赛季规则版本 | `season_id`、`rule_type`、`version_no`、`effective_time`、`rule_status` | 已有版本字段和唯一约束，但业务层未见发布/冻结流转 |
| `basket_tournament_award_config` | 奖项规则配置 | `season_id`、奖项编码、评选规则、状态 | 表存在，独立运营和荣誉关联留待后续文档 |
| `basket_team_season_profile` | 正式赛事球队快照 | `season_id`、参赛状态、阵容锁定、平台快照 | 由报名审核产生，不能替代长期 `basket_team` |

关键数据关系与约束：

1. `basket_competition_season` 是顶层年度/赛季容器；`basket_tournament.competition_season_id` 关联它。
2. `basket_tournament_season.tournament_id` 关联具体赛事。当前创建赛事会自动建立一条“主运营赛季”，所以 Admin UI 的赛事规则页面会读取赛事的 `operationalSeasonId`。
3. `uk_season_platform(season_id, platform_code, is_delete)` 防止同一运营赛季同一平台重复开放。
4. `uk_stage_season_no(season_id, stage_no)` 保证阶段编号唯一；Service 另检查同赛季阶段名称不能重复。
5. `uk_rule_season_type_version(season_id, rule_type, version_no)` 保证规则版本唯一，但不会自动保证同时只有一份“现行规则”。

## 5. 后端实现

### 5.1 顶层赛季、赛事与运营赛季

| 能力 | Controller/接口 | Service 关键行为 |
|---|---|---|
| 顶层赛季列表/详情/新增/修改/删除 | `/basket/competition-season/*` | 校验起止时间、同年份同名唯一；已有赛事不能删除；归档状态不允许修改 |
| 赛事列表/详情/新增/修改/发布/下架/关闭/删除 | `/basket/tournament/*` | 创建必须选择顶层赛季，校验报名/比赛时间与单一平台；草稿创建，发布/下架/关闭使用状态条件更新 |
| 运营赛季列表/详情/新增/修改 | `/basket/tournament/{tournamentId}/season/*`、`/basket/season/{seasonId}` | 校验报名时间、赛季时间和 5–8 人阵容边界，默认 `PREPARE` |
| 报名窗口与赛季运行状态 | `/basket/season/{seasonId}/open-registration`、`close-registration`、`start`、`finish` | `PREPARE/REGISTRATION_CLOSED → REGISTRATION_OPEN → REGISTRATION_CLOSED/IN_PROGRESS → FINISHED`；结束时使对应赛季队长资质过期 |

具体实现结论：

1. `BasketTournamentServiceImpl.create` 要求 `competitionSeasonId`、报名起止、比赛起止和 `gameTerminal`；平台会统一规范化，并拒绝创建 `ALL` 平台事，仅支持 `PC/PS/XBOX`。
2. 创建具体赛事后，`createOperationalSeason` 自动写入一条 `basket_tournament_season`：名称和时间从赛事复制，默认最大 16 队、最小 5 人、最大 8 人、允许球队报名、不允许 Open 报名、状态为 `PREPARE`。
3. 创建或更新赛事后，`syncEventPlatform` 通过 `BasketTournamentSeasonPlatformMapper.upsertOpenPlatform` 将赛事单一平台同步到运营赛季平台表。
4. 发布赛事采用 `DRAFT/DISABLED → ACTIVE` 的条件更新，并同步主运营赛季的报名和比赛时间；若当前时间位于报名窗口，会将该运营赛季同步为 `REGISTRATION_OPEN`。
5. 运营赛季 `openRegistration`、`closeRegistration`、`start`、`finish` 使用 `updateStatusIfMatch`，能阻止对不符合来源状态的重复状态跳转。
6. `BasketSeasonServiceImpl.publish` 当前仅校验赛季存在，没有写状态或公开字段，属于空实现风险。
7. 顶层赛季状态枚举存在 `PREPARE/ACTIVE/FINISHED/ARCHIVED`，但当前 Controller/Service 未见专用发布、开始、结束、归档动作接口；创建/修改请求可直接带状态，需收紧治理。

### 5.2 阶段、轮次、分组与规则

| 能力 | Controller/接口 | 当前行为 |
|---|---|---|
| 阶段列表/详情/新增/修改/激活/结束/取消/删除 | `/basket/stage/*` | 新增为 `DRAFT`；仅草稿可编辑/删除，激活后可结束或取消 |
| 轮次管理 | `BasketTournamentRoundController` 及相关 Service | 轮次实体按运营赛季、阶段和顺序组织，供赛程生成使用 |
| 分组管理 | `BasketTournamentGroupController`、`GroupTeam` | 分组及分组参赛队关系存在，后续按阶段组织赛程 |
| 规则列表/新增/编辑/删除 | `/basket/season/{seasonId}/rule/*`、`/basket/tournamentRule/{ruleId}` | 按运营赛季维护规则标题、类型、内容、版本、生效时间、状态、排序 |

阶段 Service 的关键约束：

1. 创建阶段要求运营赛季存在、同赛季阶段名称不重复，自动生成阶段编号，默认 `DRAFT` 和公开状态 `1`。
2. 阶段开始/结束时间在创建、编辑时会检查先后关系；激活时还会检查时间必须落在运营赛季时间范围内。
3. 阶段删除仅允许草稿状态且阶段下没有比赛；状态变更使用条件更新。
4. 当前未见激活阶段时写回 `basket_tournament_season.current_stage_id`，也未见自动结束上一个活跃阶段的逻辑。

规则 Service 的关键现状：

1. 新增规则会直接按请求写入 `rule_type`、`rule_title`、`rule_content`、`version_no`、`effective_time`、`rule_status` 和排序字段。
2. 编辑和删除仅校验规则记录存在，未见“赛季已开始/规则已生效后禁止修改”“只允许一个现行版本”“版本切换自下线旧版”等业务规则。
3. 规则表的版本唯一键是数据库保护；Service 没有主动将唯一键异常转换为明确业务提示。

后台按钮权限与后端 `@PreAuthorize` 已对应：

1. 赛事：`basket:tournament:list/query/add/edit/publish/close/remove`。
2. 运营赛季及顶层赛季：`basket:season:list/query/add/edit/publish/openRegistration/closeRegistration/start/finish/remove`；顶层赛季复用了这组权限。

当前需注意：前端按钮隐藏不是权限边界；所有写入仍应由 Admin 后端权限和 Service 状态校验裁决。公开状态字段也不能仅靠 UI 开关认定官网已正确过滤，需对公开读侧单独联调。

## 7. 状态机

### 7.1 顶层赛季状态

```text
PREPARE（筹备中） → ACTIVE（进行中） → FINISHED（已结束） → ARCHIVED（已归档）
```

该枚举已存在。当前实现仅明确“归档后不允许修改”，未见独立的状态转换接口和 CAS 约束；因此上图是状态字典，不应当作已完整实现的状态机。

### 7.2 赛事状态

```text
               publish
DRAFT（草稿） ─────────→ ACTIVE（已发布） ── close ─→ ENDED（已结束）
   │                       │
   │ delete                └── unpublish ─→ DISABLED（已禁用）
   │                                               │
   └──────────────────────────────────── publish ─┘
```

当前后端约束：

1. 发布仅允许 `DRAFT` 或 `DISABLED → ACTIVE`。
2. 下架仅允许 `ACTIVE → DISABLED`。
3. 关闭允许 `DRAFT/ACTIVE → ENDED`。
4. 删除仅允许 `DRAFT`，且赛事下不存在报名数据。

### 7.3 运营赛季状态

```text
PREPARE（筹备中）
   ├── open-registration → REGISTRATION_OPEN（报名中）
   └── start → 不允许

REGISTRATION_OPEN（报名中）
   ├── close-registration → REGISTRATION_CLOSED（报名截止）
   └── start → IN_PROGRESS（进行中）

REGISTRATION_CLOSED（报名截止）
   ├── open-registration → REGISTRATION_OPEN
   └── start → IN_PROGRESS

IN_PROGRESS（进行中） ── finish → FINISHED（已结束）
```

`CLOSED`、`CANCELLED` 枚举值已定义，但当前 `BasketSeasonServiceImpl` 未见对应 Controller 动作。`publish` 接口当前也未改变运营赛季状态。

### 7.4 阶段状态

```text
DRAFT（草稿） ── activate → ACTIVE（进行中） ── finish → FINISHED（已结束）
     │                    │
     ├── delete           └── cancel → CANCELLED（已取消）
     └── cancel → CANCELLED
```

仅草稿阶段可编辑；仅草稿且无比赛记录的阶段可删除。当前不保证同一运营赛季同一时刻只有一个 `ACTIVE` 阶段，也不自动同步 `current_stage_id`。

### 7.5 规则状态

规则表有 `rule_status`、`version_no`、`effective_time`，但当前未见规则状态枚举和发布状态机。现状是 CRUD 数据记录，不是可审计的“草稿 → 生效 → 废止”规则版本流程。

## 8. 权限规则

| 操作 | 当前权限/校验 | 必须保持的边界 | 风险 |
|---|---|---|---|
| 创建顶层赛季 | `basket:season:add` | 仅赛事运营管理员可创建年度容器 | 顶层赛季复用运营赛季权限，职责较粗 |
| 创建赛事 | `basket:tournament:add`；必须选择顶层赛季和单一平台 | 普通用户、队长不能创建赛事 | 后端已校验平台，但需检查所有入口一致 |
| 编辑/发布/关闭赛事 | `edit/publish/close` | 已有报名/赛事数据时不得破坏所属层级和历史时间线 | 部分字段在发布后是否冻结需继续确认 |
| 维护运营赛季与报名窗口 | `basket:season:*` | 只有后台能开放/关闭报名、开赛、结束 | `publish` 空实现易造成权限看似存在但无业务效果 |
| 创建/激活/结束阶段 | `basket:stage:*` | 只能在对应运营赛季内操作，阶段时间必须合法 | 未见“只允当前赛季管理员”范围校验 |
| 维护规则 | `basket:tournamentRule:*` | 规则的编辑、版本、生效应被运营权限保护 | 未见生效后冻结或双人复核 |
| 球队参加多个赛事 | 队长在各赛事报名时通过对应授权和报名校验 | 长期球队成员关系不应限制多赛事参赛 | 需在报名文档验证授权粒度和跨平台条件 |
| Web/官网读取 | 无赛事配置写入口 | 仅展示公开、可见且符合状态的数据 | `public_status` 的读侧过滤需联调 |

## 9. 并发与幂等

| 场景 | 当前控制 | 风险与要求 |
|---|---|---|
| 同名赛事并发创建 | Service 查询同顶层赛季同名；数据库基线有赛事名称唯一键但维度可能不同 | 应确认实际迁移后的唯一索引覆盖 `competition_season_id + name`，并将重复键转稳定业务错误 |
| 赛事发布/下架/关闭并发 | `updateStatusIfMatch` 条件更新 | 可避免最终状态重复跳转；需验证同步运营赛季只执行一次 |
| 运营赛季报名开关/开赛/结束并发 | `updateStatusIfMatch` | 状态 CAS 已有，需压测管理端重复点击与相邻状态竞争 |
| 结束赛季与队长授权 | `finish` 事务中调用授权过期 | 需验证状态失败时授权不会被提前过期，重试不产生重复历史 |
| 阶段激活/结束/取消并发 | `updateStatusIfMatch` | 可保证单阶段自身状态一致，但不能防止两个草稿阶段同时激活 |
| 多阶段同时激活 | 未见“赛季内唯一 ACTIVE 阶段”数据库或 Service 约束 | 高风险：`current_stage_id` 也未自动维护，应增加锁或唯一业务约束 |
| 阶段删除与赛程生成并发 | 删除时检查比赛数 | 若检查与写入之间无锁，可能出现阶段被删后仍创建比赛；赛程生成需在同一事务/锁策略中复验 |
| 同版本规则并发新增 | 表唯一键 `uk_rule_season_type_version` | Service 未显式防重；需捕获重复键并返回明确错误 |
| 赛事更新与平台同步并发 | 每次更新对主运营赛季 upsert 开放平台 | 将平台从 A 改为 B 时，旧平台是否应关闭未定义，可能留下多平台开放记录 |

## 12. 已知问题和风险

1. **P0：双赛季模型容易被误用。** `basket_competition_season` 是顶层赛季，`basket_tournament_season` 是赛事运营赛季；若页面或后续代码混用两者，会导致规则、报名、阶段和统计关联错误。
2. **P0：`current_stage_id` 未见自动维护。** 阶段激活/结束/取消 Service 仅更新阶段状态，未见更新运营赛季当前阶段，也未见限制同一运营赛季只能有一个活跃阶段。
3. **P0：赛事平台更新可能遗留旧开放平台。** `syncEventPlatform` 只 upsert 当前平台为开放，未见在赛事平台修改时关闭旧平台；可能让单平台赛事在运营赛季层变成多平台可报名。
4. **P1：运营赛季 `publish` 是空实现。** Controller 和权限存在，但 Service 只校验赛季存在，不更新状态或公开状态，容易产生“操作成功但业务未变化”。
5. **P1：顶层赛季缺少受控状态流转。** 虽有状态字典并限制归档后修改，但未见开始、结束、归档等独立接口或条件更新，状态可能在编辑请求中被直接改写。
6. **P1：规则版本治理不足。** 有版本字段和唯一键，但未见草稿/生效/废止状态机、唯一现行版本、历史冻结、回滚或规则变更审计；赛季进行中编辑规则可能影响公平性。
7. **P1：阶段时间边界校验时机偏晚。** 创建和编辑阶段时仅校验开始早于结束，直到激活才核验是否在赛季时间范围内；错误数据可长期停留在草稿。
8. **P1：赛事关闭未见级联策略。** 关闭赛事后，运营赛季、阶段、报名、转会窗口和公开读侧如何收敛未在当前 Service 中统一处理。
9. **P1：基础表与迁移版本需实际核查。** `sql/basketball.sql` 是基线定义，顶层赛季、赛事时间和转会字段来自后续迁移；目标环境必须确认迁移已执行且索引一致。
10. **P2：公开状态读侧未在本文验证。** 字段存在不代表官网、个人中心、报名候选列表都正确按赛事/赛季/阶段状态过滤，需要在前台展示文档和联调中验证。

## 13. 下一步建议

### P0

1. 在模型、接口、页面和文档中固定命名：`competition season`（顶层赛季）、`tournament`（具体赛事）、`tournament season`（运营赛季），禁止把三个 ID 互相替代。
2. 实现“激活阶段”事务：锁定运营赛季，结束或拒绝其他活跃阶段，条件更新当前阶段 `current_stage_id`，并在赛季非进行中或阶段时间非法时拒绝。
3. 明确单平台赛事的平台变更策略：禁止已报名后修改平台，或在事务内关闭旧 `season_platform`、打开新平台，并重新校验已报名数据；不能仅 upsert 新平台。
4. 为赛事、运营赛季、阶段和规则分别补齐状态变更审计，记录操作人、时间、前后状态、原因和关联影响。

### P1

1. 将 `BasketSeasonServiceImpl.publish` 改为真实、可验证的状态/公开行为，或删除该无效入口，避免权限和 UI 产生误导。
2. 为顶层赛季增加受控状态流转与 CAS：筹备、进行中、结束、归档；归档前校验下属赛事及统计结算状态。
3. 为规则引入版本治理：草稿、发布、生效、废止、唯一现行版本、赛季开始后冻结/需二次审批、变更审计和官网读取版本选择。
4. 将阶段时间必须落在运营赛季内的校验提前到创建和编辑期，并校验阶段顺序、时间重叠和后续比赛依赖。

### P2

1. 增加端到端用例覆盖：创建顶层赛季→创建赛事→自动运营赛季/平台→发布→开放报名→配置阶段/规则→开始/结束；验证各状态、权限、公开读侧和历史数据一致。
2. 在 `09-赛事报名与阵容快照.md` 中继续核对队长授权、平台开放状态和报名窗口如何共同裁决报名；在 `10-小组赛循环赛赛程生成.md` 中核对阶段/分组/轮次与赛事球队快照的绑定。
3. 对实际目标库执行只读结构核查，确认 `competition_season`、赛事时间字段、运营赛季平台表、转会字段及关键唯一索引均已按迁移落库。
