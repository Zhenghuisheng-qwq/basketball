# CNPA 赛事发布模型改造 — 技术影响评估

> 分支：`basketball-20260803`  
> 评估日期：2026-08-03  
> 性质：只读代码盘点 + 影响评估（本轮未改业务代码）  
> 依据模块：`basketball-admin` / `basketball-web` / `basketball-admin-ui` / `basketball-web-ui` + `docs/sql`

---

## 1. 当前赛事主流程梳理

### 1.1 真实层级（与口头描述有差异）

当前代码不是「直接创建一个赛事赛季」这么简单，而是 **三层容器**：

| 层级 | 表 | 业务含义 | 典型 ID |
|------|----|----------|---------|
| L1 顶层赛季 | `basket_competition_season` | 年度/届别容器，如「2026赛季」 | `competitionSeasonId` |
| L2 赛事 | `basket_tournament` | 具体联赛/杯赛实体，含单值 `game_terminal` | `tournamentId` |
| L3 运营赛季 | `basket_tournament_season` | **报名 / 赛程 / 比赛 / 统计的实际操作单元** | `seasonId` / **`eventId`** |

**业务别名映射（重要）：**

- **EventTeam** ≠ 独立表，实际是 `basket_team_season_profile`
- **EventPlayer** ≠ 独立表，实际是 `basket_tournament_season_roster`

### 1.2 后台如何创建赛事 / 赛季

1. 先建顶层赛季  
   - Controller：`BasketCompetitionSeasonController` → `POST /basket/competition-season`  
   - Service：`BasketCompetitionSeasonServiceImpl`  
   - 表：`basket_competition_season`
2. 再建赛事（自动创建运营赛季）  
   - Controller：`BasketTournamentController` → `POST /basket/tournament`  
   - Service：`BasketTournamentServiceImpl.create()`  
   - 插入 `basket_tournament`  
   - 调用 `createOperationalSeason()` 插入 `basket_tournament_season`（默认 `maxTeamCount=16`，`allowOpenRegistration=0`，阵容 5–8）  
   - 调用 `syncEventPlatform()` 写入 **单个** `basket_tournament_season_platform`（来自 `tournament.game_terminal`）
3. 运营赛季也可独立维护  
   - Controller：`BasketSeasonController` → `POST /basket/tournament/{tournamentId}/season`  
   - Service：`BasketSeasonServiceImpl`

后台页面：`basketball-admin-ui/src/views/cnpa/event/list/index.vue`（赛事）、`cnpa/event/season/index.vue`（顶层赛季）

### 1.3 前台如何展示赛事

- 路由：`/tournament`（`EventsPage.vue`），query：`competition`=tournamentId，`seasonId`=运营赛季，`tab`
- API：`BasketPublicTournamentController`  
  - `GET /basket/public/tournament/page`  
  - `GET /basket/public/tournament/{tournamentId}`  
  - `GET /basket/public/tournament/{tournamentId}/season`  
  - `GET /basket/public/season/{seasonId}/overview|placement|schedule/page|standing`
- 前端模块：`basketball-web-ui/src/api/publicTournament.ts`、`views/events/*`

### 1.4 用户如何报名（球队报名主链路）

```
队长授权(seasonId) → 选运营赛季 + platformCode → createDraft
→ 保存阵容 → submit → 后台审核
```

- Controller：`TeamRegistrationBusinessController`  
- Service：`TeamRegistrationBusinessServiceImpl`  
- 表：`basket_tournament_registration` + `basket_tournament_registration_player`  
- 前置：`requireValidQualificationForEvent(..., seasonId)`、赛季开放、平台开放、阵容 5–8  
- 名额：审核通过后才计数；前台可报名列表用 **APPROVED 数 vs season.maxTeamCount**；审核中不占名额（与业务口径一致）  
- 前台：`TeamRegistrationFlow.vue`、`MyEventsView.vue`、`api/teamRegistration.ts`

### 1.5 报名审核后如何生成 EventTeam / EventPlayer

- Controller：`BasketRegistrationAuditController` → `POST /basket/registrationAudit/{id}/approve`  
- Service：`BasketRegistrationAuditServiceImpl.approve()`  
  - `countApprovedBySeasonId(seasonId)` vs `maxTeamCount`（**按赛季总量，非按平台**）  
  - `BasketParticipationGenerationServiceImpl.generateFromTeamRegistration()`  
    - EventTeam → `basket_team_season_profile`（`event_team_no`、`season_id`、`registration_id`、`game_terminal`=platform）  
    - EventPlayer → `basket_tournament_season_roster`（锁定，含平台游戏 ID 快照）  
  - `ensureRosterLockedForApprovedRegistration()`

### 1.6 当前赛程如何生成 / 发布

- Controller：`BasketScheduleManageController`（路径大量用 `eventId`，语义=运营赛季 ID）  
- Service：`BasketScheduleGenerateServiceImpl`  
- 策略：仅 `REGULAR_ROUND_ROBIN` V1/V2（单循环，Berger；奇数队 BYE）  
- 取队：`selectEligibleForScheduleBySeasonId` — **按 season 全量 EventTeam，不按 platform 过滤**  
- 平台码：`ScheduleEventTeamSupport.resolvePlatformCode(eventId)` 从 **`tournament.game_terminal`** 取，写入每场 `basket_match.platform_code`  
- 表：`basket_schedule_generate_batch`（`event_id`）、`basket_match`（`season_id`）  
- 自动 Job：`ScheduleAutoGenerateJob` 仅生成草稿不发布  
- 后台页：`cnpa/competition/schedule-manage/index.vue`

### 1.7 比赛数据提交与审核

- 前台提交：`BasketPlayerMatchDataController` → `PlayerMatchDataServiceImpl` → `basket_match_data_submission`（维度：match + 提交方球队/eventTeam）  
- 后台审核：`BasketMatchDataAuditController` → `BasketMatchDataSubmissionAuditServiceImpl.approve()`  
  - `applyApprovedSubmissionToOfficialData()` → 比分/球队统计/球员统计/官方结果  
  - `BasketDataSettlementServiceImpl.rebuildMatch()` → `basket_stage_standing` / `basket_team_season_stat` / `basket_player_season_stat` / `basket_team_rank` / `basket_player_rank`  
- 结算重建入口按 **seasonId**，未见 division/platform 隔离键

### 1.8 个人中心如何读「我的赛事 / 我的赛程」

| 能力 | 接口 | 前端 |
|------|------|------|
| 我的赛事上下文/列表 | `/basket/account/my-events/*` | `MyEventsView.vue` |
| 我的报名 | 球队 registration page / Open page | Tab `applications` |
| 已参加 | `/basket/player/event-team/list` + account tournament page | Tab `joined` |
| 我的赛程 | `/basket/player/my-schedules`（可筛 seasonId、platformCode） | Tab `schedule` |
| 比赛数据 | `/basket/player/match-data/*` + eventTeam matches | 新旧两套路并存 |

### 1.9 后台管理入口（菜单组件）

| 功能 | 组件路径 |
|------|----------|
| 顶层赛季 | `cnpa/event/season` |
| 赛事列表/发布 | `cnpa/event/list` |
| 球队报名审核 | `cnpa/participation/team-registration` |
| Open 报名审核 | `cnpa/participation/open-registration`（已有，默认关闭） |
| 正式参赛球队/球员 | `official-teams` / `event-roster` |
| 赛程生成发布 | `competition/schedule-manage` |
| 比赛管理 | `competition/schedule`（菜单别名 match-manage） |
| 比赛数据审核 | `competition/match-data-audit` |

## 2. 当前 eventId / seasonId / tournamentId 关系（重点）

### 2.1 真实语义

| 名称 | 实际指向 | 说明 |
|------|----------|------|
| `competitionSeasonId` | `basket_competition_season.id` | 顶层年度容器 |
| `tournamentId` | `basket_tournament.id` | 赛事主表 |
| `seasonId`（业务主路径） | **`basket_tournament_season.id`** | 报名/比赛/授权/统计默认都指它 |
| `eventId`（赛程模块） | **= seasonId = 运营赛季 ID** | `ScheduleGenerateReq` 注释与 `ScheduleEventTeamSupport` 明确等同 |
| `operationalSeasonId`（VO） | 同上运营赛季 | 创建赛事时自动生成 |
| `eventTeamId` | `basket_team_season_profile.id` | 正式参赛球队快照 |
| `tournamentSeasonId` | **代码中几乎不存在此命名** | 概念上=seasonId |

### 2.2 混用 / 混乱点（必须标记）

1. **赛程 API 用 `eventId`，比赛表用 `season_id`，同值不同名**  
   - `BasketScheduleManageController` `/event/{eventId}`  
   - `BasketMatch.seasonId`  
   - `BasketScheduleGenerateServiceImpl` 同时 `setEventId(eventId); setSeasonId(eventId);`
2. **队长授权方法名写 Event，参数写 seasonId**  
   - `requireValidQualificationForEvent(..., Long seasonId)`  
   - 注释：`eventId(seasonId)` → `basket_captain_qualification.season_id`
3. **前台路由 param `:tournamentId` 经常装的是 seasonId**  
   - `/account/my-events/:tournamentId/team-registration`  
   - `/account/my-tournaments/:tournamentId/team/*`  
   - 公开页 query `competition` 才是真正的 tournamentId
4. **两套「赛季」并存**  
   - 筛选器 `competitionSeasonId` vs 报名 `seasonId`  
   - 运营人员与前端极易说错
5. **platform vs gameTerminal 双轨**  
   - 赛事层：`game_terminal`（单值必填）  
   - 报名/比赛层：`platform_code`  
   - EventTeam 把 platform 写入 `game_terminal` 字段  
   - 赛程平台解析仍回退 `tournament.game_terminal`，与 `season_platform` / registration.platform_code 未完全统一
6. **admin 领域对象 `BasketTournamentRegistration` Java 字段缺 `platformCode`，但表与 Mapper/XML 已有**  
   - web 模型有 `platformCode`；admin 实体不同步，增加维护风险
7. **`tournamentType` 不是 Series**  
   - 后台选项：`REGULAR_SEASON` / `PLAYOFFS` / `ALL_STAR`  
   - 创建默认还可落到 `LEAGUE`（后端兜底）——与老板说的 League/Arena/Cup/Open **不是同一概念**

### 2.3 是否会导致查询错误？

| 风险场景 | 现状 |
|----------|------|
| 把 tournamentId 当 seasonId 查报名/赛程 | 前台路由命名已埋雷；部分跳转用 `/events/${tournamentId}` 但无对应路由 |
| 多平台同 season 排赛 | 会把全部平台 EventTeam 混进同一批循环赛（P0 级潜在事故） |
| 名额按 season 总量 | 多平台时无法做到「每平台 10 队」 |
| 排行榜按 season 重建 | 无 platform/division 隔离键，多平台会串榜 |

### 2.4 是否必须统一命名？

**必须。** 建议在改造中收口为：

- `seriesId` / `seriesCode`（赛事系列）  
- `seasonId` → 仅指 `tournament_season`（发布的具体赛季）  
- `divisionId` → 平台赛区  
- `tournamentId`：若保留表，明确为「赛季壳」或逐步弃用为兼容别名  
- `eventId`：建议废弃或严格定义为「对外展示用运营单元」并文档化；赛程 API 不要再与 seasonId 双写  
- `eventTeamId` / `eventPlayerId`（roster id）保持业务术语，表名可渐进改或不改

## 3. 当前表结构与新模型映射

### 新模型目标

```
tournament_series
  → tournament_season
    → tournament_division
      → tournament_registration
        → event_team / event_player
          → match / match_submission
```

### 映射与建议

| 新模型 | 当前可复用 | 建议 |
|--------|------------|------|
| `tournament_series` | **无**；`tournamentType` 语义不符 | **新增** series 配置（见第 4 节） |
| `tournament_season` | `basket_tournament_season` 最接近；但当前挂在 `tournament` 下，且上面还有 `competition_season` | **复用并升格**：把「发布对象」明确为 season；评估是否弱化/合并 `basket_tournament` 与 `basket_competition_season` |
| `tournament_division` | `basket_tournament_season_platform` 仅有 platform 开放状态，**无独立名额/赛程/榜维度主键** | **建议新增 division 表**（或把 season_platform 升级为 division，并补 `max_team_count`、状态、展示名等） |
| `tournament_registration` | `basket_tournament_registration`（已有 `platform_code`、球队报名） | **复用**；补 `division_id`、预留 `registration_mode` |
| `event_team` | `basket_team_season_profile` | **复用**；加 `division_id`（保留 season_id） |
| `event_player` | `basket_tournament_season_roster` | **复用**；加 `division_id` |
| `match` | `basket_match`（已有 `season_id`、`platform_code`、home/away event_team） | **复用**；加 `division_id`（platform_code 可冗余） |
| `match_submission` | `basket_match_data_submission` | **复用**；通过 match/eventTeam 间接绑 division，必要时冗余 `division_id` |

### 哪些表建议加 `division_id`（P0）

- `basket_tournament_registration`  
- `basket_captain_qualification`（或 season+platform 唯一约束升级）  
- `basket_team_season_profile`  
- `basket_tournament_season_roster`  
- `basket_schedule_generate_batch`  
- `basket_match`  
- `basket_stage_standing` / `basket_team_season_stat` / `basket_player_season_stat` / `basket_team_rank` / `basket_player_rank`  
- 阶段/分组若按赛区独立：`basket_tournament_stage` / `group` / `round`

### 可暂时不改（短期）

- 长期球队 `basket_team`（已趋向 GENERAL，不绑平台）  
- 球员认证 / 平台账号表  
- 比赛数据提交子表（period/stat/material）— 通过 submission→match 关联  
- 争议/异常表 — 第二阶段再补 division 过滤

### 需要新增字段（season 层）

- `series_id` / `series_code`  
- `display_title`（展示标题，如 CNPA League 2026 S1）  
- `format_type`：`REGULAR_PLAYOFF` / `GROUP_KNOCKOUT` / `KNOCKOUT`（与现有 `formatCode=5V5` 区分）  
- `registration_mode` 或 `allow_team_registration` + 未来 PERSONAL 开关（已有 allow_* 可扩展）  
- division 层：`max_team_count`、`platform_code`、报名/比赛时间是否可覆盖 season

### 关于 `basket_tournament` / `basket_competition_season`

这是与新模型的 **结构性冲突点**：

- 新口径：固定 Series → 发布 Season → 多 Division  
- 旧结构：CompetitionSeason(年) → Tournament(单平台赛事) → OperationalSeason  

**建议**：  
- 短期兼容：把现有 `tournament` 视为「某 series 下某次发布的壳」，或一对一映射到 season；  
- 中期：以前台/报名/赛程统一以 **seasonId + divisionId** 为真源，tournament 仅作兼容外键。

## 4. 新增 Series 是否需要独立表

### 评估

| 方案 | 优点 | 缺点 |
|------|------|------|
| 纯枚举 `LEAGUE/ARENA/CUP/OPEN` | 简单、固定四种、改动小 | Banner/图标/默认赛制/文案需另找配置位；运营难改 |
| 独立表 `basket_tournament_series` | 可配默认赛制、文案、图标、Banner、排序、启用状态 | 多一张表与后台维护页 |
| 枚举 + 配置表（推荐） | 代码强约束四种 code；运营可改展示资源与默认值 | 实现略多一点 |

### 推荐

**枚举强约束 + 轻量配置表（或字典扩展）**：

- 代码枚举固定：`LEAGUE` / `ARENA` / `CUP` / `OPEN`  
- 表或运营配置存：`display_name`、`banner`、`icon`、`default_format_type`、`default_description`、`enabled`、`sort`  
- 前台栏目固定读配置；后台发布第一步选 series  
- **不建议**把现有 `tournamentType`（常规赛/季后赛/全明星）直接改成 Series — 那是赛段/子类型语义，冲突

是否需要运营后台维护：**需要基础配置页**（改 Banner/文案），但不需要「随时新增第五种系列」的完整 CRUD 自由度。

## 5. Division 平台赛区接入评估

### 5.1 现状能否承接「一季多平台」？

**不能安全承接。** 已有碎片能力：

| 能力 | 现状 |
|------|------|
| 多平台开放表 | `basket_tournament_season_platform` 存在 |
| 创建赛事 | 只从单值 `game_terminal` sync **一个** platform |
| 报名 | registration 有 `platform_code`，唯一键 `season+team+platform` |
| 名额 | **season.maxTeamCount 总量**，无 per-platform |
| 赛程 | 全 season EventTeam 一起排；platform 取自 tournament |
| 排行榜/统计 | 按 season 重建，无 platform/division 维度 |
| 前台展示 | Hero 显示 tournament.gameTerminal；报名可选 season platforms |

### 5.2 是否需要 `tournament_division`

**强烈建议新增（或升级 season_platform → division）。**  
仅 `platform_code` 字符串不够：名额、赛程批次、榜、阶段都需要稳定外键 `division_id`。

建议字段示意：`id, season_id, platform_code, division_name, max_team_count, registration_* , status, display_order`

### 5.3 必须绑定 divisionId 的业务

| 业务 | 必须？ | 说明 |
|------|--------|------|
| 报名 | 是 | 独立名额与审核 |
| 队长授权 | 是（或 season+platform 等价） | 口径：无永久资格，绑具体赛区 |
| 名额统计 | 是 | 审核通过才占该 division 名额 |
| EventTeam / EventPlayer | 是 | 快照归属赛区 |
| 赛程 / Match | 是 | 禁止跨平台混排 |
| MatchSubmission | 间接必须 | 经 match/eventTeam |
| 排行榜 / 数据统计 | 是 | 独立运营 |
| 前台详情平台切换 | 是 | 切换即换 division 上下文 |
| 个人中心我的赛事/赛程 | 是 | 展示与筛选按 division |

### 5.4 改造风险

- **P0**：若不先引入 division，只开多平台，会立刻出现混排赛程、串榜、名额错误。  
- 赛程生成、自动 Job、结算 rebuild、公开 standing API 都要改过滤键。  
- 前台公开页目前以 tournament + season 为上下文，需增加 division 切换态（query 建议 `divisionId` 或 `platform`）。  
- 旧数据需为每个 season 的已有 platform 回填一条 division。

## 6. 报名方式兼容评估

### 6.1 现状

- 球队报名：主链路完整（draft→roster→submit→audit→snapshot）  
- Open 个人报名：已有独立表 `basket_tournament_open_registration`、前后台页面与审核；赛季默认 `allowOpenRegistration=0`  
- **没有**统一的 `registration_mode = TEAM | PERSONAL` 枚举层

### 6.2 建议（本阶段不实现个人报名）

1. **球队报名继续用** `basket_tournament_registration`，不要推倒。  
2. **registration_mode 放在 season（或 division）配置层**，不放在单条报名记录作为唯一真相；记录上可冗余 mode。  
   - 推荐：season 声明支持哪些 mode；division 可覆盖（若各平台策略不同）。  
3. **PERSONAL 本阶段**：  
   - 新接口若收到 PERSONAL → 明确返回「个人报名暂未开放」  
   - 现有 Open 链路：保持关闭；**不要半开**；评估后续是演进 Open 表还是新建 personal_registration，再统一生成 EventTeam/EventPlayer  
4. **未来个人报名**无论组队方式如何，审核通过后仍必须落到 EventTeam + EventPlayer（可系统队/后台组队，但那是后续轮次）。  
5. **当前阶段校验改动（预留级）**：  
   - season 发布校验：仅 TEAM 开放  
   - 拦截 PERSONAL / 禁止误开 allowOpenRegistration（或运营开关与产品口径对齐）  
   - 不实现组队、系统分配、个人转球队完整流

### 6.3 统一报名表 vs 分表

| 方案 | 建议 |
|------|------|
| 强制一张统一 registration | 短期成本高，Open 已分表 |
| **球队表保留 + 个人表后续** | **推荐**；上层用统一「报名视图/领域服务」生成快照 |
| 现在合并 Open 与 Team | **不建议**本阶段做 |

## 7. 赛制类型兼容评估

### 现状

- 可生成规则几乎写死：`REGULAR_ROUND_ROBIN`（常规赛单循环）  
- **未写死 24 支**；按实际锁定 EventTeam 数 `n*(n-1)/2`  
- 默认名额上限创建时 16  
- 有 stage/group/round 表结构，但自动生成主路径不走小组赛/淘汰树  
- `tournament.formatCode` 实际是 `5V5` 类，**不是** REGULAR_PLAYOFF / GROUP_KNOCKOUT  
- 后台 `tournamentType` 是常规赛/季后赛/全明星，与新「赛制类型」再次撞名

### 建议

| 赛制 | 本阶段 |
|------|--------|
| `REGULAR_PLAYOFF` | **优先基础版**：先做常规赛循环（已有）；季后赛晋级树 **预留字段/阶段类型，不实现完整晋级** |
| `KNOCKOUT` | 可第二优先级评估；需独立生成器，当前无 |
| `GROUP_KNOCKOUT` | **建议先预留不开放**（分组+晋级复杂度高） |

平台赛区独立生成：当前不支持，必须随 division 改造一起做。

## 11. 数据迁移风险

### 需要 migration（本轮只评估，不写 SQL）

1. **Series 回填**  
   - 无可靠字段时默认 `LEAGUE`，或按 `tournamentType`/`tournamentName` 人工映射表  
2. **Division 回填**  
   - 每个 `tournament_season` + 已有 `season_platform` / `game_terminal` → 1 条 division  
   - `max_team_count` 从 season.maxTeamCount 拷贝到该唯一 division  
3. **下游补 `division_id`**  
   - registration / eventTeam / roster / match / batch / standing / rank / stat / captain_qualification  
   - 匹配键：优先 `platform_code`，其次 tournament.game_terminal  
4. **competition_season / tournament 壳保留**  
   - 避免断外键；逐步只读兼容  
5. **风险**  
   - 历史脏数据 platform 为空或 GENERAL  
   - 同 season 若已存在多 platform 报名但赛程已按全量生成 → **数据语义已错**，需人工核对是否已有多平台生产数据  
   - Open 报名历史与新 PERSONAL 口径对齐问题

## 12. 建议分几轮实现

基于真实复杂度（三层旧模型 + 已有多平台半成品 + 赛程/结算强耦合 + 前后台双端），**建议 8 轮**，不建议压成 5 轮（Division 与赛程/榜容易夹生）；10 轮偏碎，除非人力并行拆前端。

| 轮次 | 内容 | 产出 |
|------|------|------|
| **第 1 轮** | ID 语义收口文档 + 代码别名收敛（eventId/seasonId/tournamentId 对照表、接口注释、前端路由命名治理方案） | 无行为变更或极小兼容别名 |
| **第 2 轮** | Series + Season 模型（配置/枚举、season 挂 series、displayTitle、format_type 预留）；弱化 tournamentType 误用 | 后台能选系列发布「赛季」 |
| **第 3 轮** | Division 表/升级 + 迁移回填 + 下游外键 | 数据层具备赛区隔离能力 |
| **第 4 轮** | 后台步骤式发布 + 赛区配置页 | 运营可用新发布流（仍可只开球队报名） |
| **第 5 轮** | 球队报名/审核/快照/队长授权/名额按 division | **不破坏现有球队主链路** |
| **第 6 轮** | 赛程生成/Match/自动 Job/阶段按 division；结算与榜按 division | 消灭混排混算 |
| **第 7 轮** | 前台详情平台切换 + 个人中心 + 公开赛程/榜 API | 用户侧闭环 |
| **第 8 轮** | 全链路联调、旧数据验收、PERSONAL 拦截验收、单测/回归 | 可发布 |

并行可选：第 2–4 轮后端模型与后台 UI 可部分并行；第 6–7 强依赖第 3/5。

**个人报名完整实现、小组赛晋级、季后赛树、BO3/BO5：明确排除出以上 8 轮。**

| 风险项 | 等级 | 说明 |
|--------|------|------|

## 14. 本轮结论

| 问题 | 结论 |
|------|------|
| 改造规模 | **大改**（领域模型升维 + 多端 + 迁移 + 赛程/结算隔离） |
| 是否建议现在做 | **建议做**，但必须分轮；不要在同一迭代「多平台 + 个人报名 + 复杂赛制」一起上 |
| 是否先只做球队报名 | **是**，坚决只做 TEAM |
| 是否先引入 divisionId | **是，且应早于「真正多平台运营」**；否则现有半成品多平台会变成事故 |
| 个人报名 | **只预留**（mode/开关/错误文案）；Open 保持关闭，不半实现 |
| 最推荐路径 | 收口 ID 语义 → Series/Season → Division+迁移 → 后台发布 → 报名快照 → 赛程结算 → 前台个人中心 → 联调 |
| 第一轮开发从哪开始 | **ID 语义收口 + Series/Season 字段设计评审（含与 competition_season/tournament 共存策略）**，同时出 division 迁移方案；不要先改前台皮肤 |

### 与新需求的核心冲突清单（务必对齐产品）

1. 旧：`competition_season → tournament(单平台) → operational_season`；新：`series → season → division`。  
2. 旧：`tournamentType`=常规赛/季后赛/全明星；新：Series=League/Arena/Cup/Open — **不能复用同一字段**。  
3. 旧：名额/赛程/榜以 season 为边界；新：以 division 为边界。  
4. 旧：已有 Open 个人报名半套实现；新：PERSONAL 暂不开放且要统一预留 — 需产品决定 Open 的生死。  
5. 旧：赛程只支持单循环；新：三种赛制 — 本阶段只能上基础循环 + 预留。
