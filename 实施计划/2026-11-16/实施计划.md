# CNPA Cup 赛程与球队历史页修复记录

日期：2026-11-16

来源是运营在 CNPA Cup 2026 S1、PS/Xbox 9V5（`divisionId=214`，赛事球队 Homi，`eventTeamId=330`）上的三轮反馈，以及随后的代码审查。代码还在本地工作区，没有提交，也没有发到正在跑的服务上。

这条记录只覆盖这次碰到的三件事：杯赛标准模板落位被写成高排名对低排名、结构页在已有名单时仍报参赛队不足、官网历史球队的赛事和阶段筛选是错的。不改报名、审核、积分公式，也不改线上数据。

## 1. 问题核对

对照截图和当时的源码。下面只记已经对过代码的结论。

| 现场现象 | 代码里的原因 | 处理 |
| --- | --- | --- |
| 应用杯赛标准模板报英文 `Cup eliminationPlacement is not allowed` | 杯赛只允许 `GROUP_CROSS`、`MANUAL`。规则面板加载时把快照里的 `GROUP_CROSS` 收成 `HIGH_VS_LOW`，模板表单再把这个值交回去 | 保留这两种落位。表单里不在允许列表中的值，提交前收回默认的小组交叉站位。错误文案改成中文 |
| 运营要 30 队、8 组、每组前 2 名，同组两队决赛前不相遇，高名次对交叉组低名次 | 旧的交叉落位把同一组的第 1 名和第 2 名排成相邻两场。8 组时这两场在同一半区，下一轮就会相遇 | 先排完全部第 1 名的交叉场，再排第 2 名的交叉场。无轮空时同组只在决赛相遇 |
| 结构页五次提示「阶段参赛队伍不足 2 支（stageTeams=0, pairingSlots=0）」，表上参赛队却是 30，官网也能看到名单 | 30 来自正式名单或阶段上已写入的 `participant_count`，不是 `basket_division_stage_team`。预览直接拿空的阶段参赛队做校验。淘汰赛工作台在没有阶段参赛队时，又把整份正式名单的人数填进去 | 第一阶段预览前，从已锁定的正式名单补齐阶段参赛队，并且单独提交。淘汰赛没有阶段参赛队时人数记 0。未确认的人工落位或小组交叉，先报抽签未确认 |
| 模板已经应用成功，交叉站位显示人工落位，小组赛仍报队伍不足 | 应用模板只把阶段设为就绪，不插入阶段参赛队。小组赛生成前还要求分组批次已锁定。当时点的是预览，校验发生在插入之前，所以一直看到 0 | 预览先写入第一阶段参赛队。分组没锁定时改为说明已有多少支球队、请先分组并锁定 |
| 历史球队比赛页、数据页的赛事筛选只有系列名，选了也不按这支球队参加过的赛事过滤 | 比赛页的选项来自每场比赛上的轮次文案。数据页的选项只有当前 `seasonName`，而且不参与重新请求 | 用长期球队的已公开参赛记录做选项，带上赛区名和这场赛事的 `eventTeamId`。切换赛事后按该赛区重拉比赛和统计 |
| 赛事后面的阶段永远是常规赛、季后赛 | 两个页面把阶段写死成 `regular` / `playoffs` | 选中某一场赛事后，阶段列表改为该赛区当前赛制快照里的阶段名。选「全部赛事」时只留「全部阶段」 |

后来的截图里，杯赛模板已经用「人工落位」应用成功。这次没有把已经落下去的 `MANUAL` 改回 `GROUP_CROSS`。要自动交叉，需要在模板里重新选择「小组交叉站位」再应用。

## 2. 冻结决定

1. 杯赛淘汰落位继续只允许小组交叉站位和人工落位。`HIGH_VS_LOW` 不在服务端映射成 `GROUP_CROSS`。
2. 自定义淘汰赛的下拉里补上这两种落位，避免规则面板再次把已保存的 `GROUP_CROSS`、`MANUAL` 收成高排名对低排名。
3. 预览第一阶段可以写入阶段参赛队。这次写入单独提交。后面的分组或抽签校验失败，不把刚写入的参赛队回滚掉。
4. 点「生成赛程」仍是一整笔事务。分组没锁定时，生成会把同一次事务里的参赛队插入一起回滚。要把名单留下，先点预览。
5. 淘汰赛在没有本阶段参赛队时，不拿整份正式名单的人数冒充淘汰赛人数。
6. 同组两队决赛前不相遇，只保证没有轮空的小组交叉。有轮空且无法同时满足交叉和轮空时，仍拒绝并要求改人工落位。30 队、8 组、每组晋级 2 人得到 16 人，没有轮空，落在这条保证里。
7. 官网赛事列表只放已公开赛季里、未删除赛区上的参赛记录。状态为 `INACTIVE` 的不放。当前打开的这场如果没出现在历史里，仍补进下拉，避免这一页自己消失。
8. 公开的球队技术统计和球员技术统计按赛区累计，没有阶段参数。数据页的阶段下拉跟赛事走，选中某个阶段不另算一套场均。
9. 线上库不做 `INSERT`、`UPDATE`、`DELETE` 和 DDL。这次没有新 SQL。

## 3. 现有链路，修复时接着用

| 环节 | 现有落点 | 这次怎么对待 |
| --- | --- | --- |
| 杯赛标准模板 | `CupStandardTemplateBuilder`，模板码 `CUP_STANDARD_V1` | 只改拒绝文案和前端提交值。默认落位仍是 `GROUP_CROSS` |
| 规则面板 | `DivisionFormatRulesPanel.vue` 的 `normalizeStagesForUi` | 继续在加载时规范化落位，但不再改掉小组交叉和人工落位 |
| 阶段参赛队 | `DivisionStageExecutionApplicationServiceImpl.initializeStageTeams` | 第一阶段仍从 `selectFormalEventTeams` 复制。预览通过 Spring 代理调用，使事务真正生效，并锁赛区行 |
| 结构页人数 | `toExecutionListVo` 优先用阶段上的 `participantCount` | 阶段行里已经写了 30 时，列表仍显示 30，直到预览把真实人数写回去。对阵工作台的空淘汰赛不再显示这份 30 |
| 小组赛生成 | `GroupStageStageScheduleStrategy` | 仍要求分组批次存在且为 `LOCKED`。组数不一致、每组晋级人数缺失这些校验不动 |
| 交叉落位 | `GroupCrossPlacementStrategy` | 只调整第一轮场次顺序。奇数小组、每组晋级超过 2 人，仍要求人工落位 |
| 淘汰赛签表 | `EliminationBracketMaterializer` | 不改。它仍把相邻签位配成一场，胜者再和相邻场次的胜者打。场次顺序因此决定半区 |
| 历史球队页 | 路由 `/tournament/team/:teamId`，这里的 id 是赛事球队 | 参赛历史用详情里的 `sourceTeamId` 去调 `GET /basket/public/team/{teamId}/season-history`。这个接口要的是长期球队 |
| 公开阶段 | `GET /basket/v4/public/stage/list?divisionId=` | 读当前赛制快照下未删除的阶段，名称用 `stageName` |
| 公开比赛 | `GET /basket/v4/public` 的比赛列表 | 只含已发布比赛。赛程没生成或没发布时，筛选正确也会是空列表 |
| 公开统计 | `stats/team-stat`、`stats/player-stat` | 仍只按赛区。数据页切换赛事时改用该赛事的 `divisionId` 和 `eventTeamId` |

## 4. 三轮各自收什么

| 轮次 | 现场 | 收口 |
| --- | --- | --- |
| 第 1 轮 | 模板英文报错；结构页报 0 支球队；同组会在决赛前相遇 | 落位值不再被收成 `HIGH_VS_LOW`。交叉场次改成上下半区。预览和淘汰赛的报错改成能对上真实原因 |
| 第 2 轮 | 模板已按人工落位应用，结构页仍报队伍不足，参赛队列是 30 | 预览补齐第一阶段参赛队。没锁定分组时说明已有多少支。淘汰赛空名单不再显示 30 |
| 第 3 轮 | 历史球队筛不出参加过的赛事，阶段永远是常规赛和季后赛 | 赛事下拉改为参加过的已公开赛事。阶段下拉改为该赛事的真实阶段 |
| 审查 | 把三轮放到一起看 | 预览写入改为单独事务并锁赛区。切换球队时不再拿上一支球队的历史。某一场赛事的比赛接口失败时，不清空其他赛事已经取到的比赛 |

第 2 轮没有把已应用的人工落位改回小组交叉。第 3 轮没有为数据页新做按阶段汇总的统计接口。
