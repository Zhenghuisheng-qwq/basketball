# CNPA 数据中心 V2 实施计划

基准文档：《CNPA_V2_数据中心规则与发布机制_开发需求说明书》V1.0（2026-10-29）。

代码基线：分支 `20261016`，HEAD `1f0aa4c4`（2026-11-02）。审计时工作区干净。本计划只覆盖数据中心的规则、资格和发布，不重做赛事域。

## 1. 冻结决策

这些决定在四轮里不再改口。

1. 文档里的 `eventId` 使用 `basket_division.id`。`Season` 只挂在 `Series` 上，同一季可以有多个平台和模式，不能当统计主键。
2. 统计范围使用真实阶段 `basket_division_stage.id`。一个 Division 可以有多段同类型阶段，配置键是 `divisionId + stageId`，不是阶段枚举。
3. 每个 Division 另有一个虚拟范围 `OVERALL`。它把选定阶段的 `basket_match.id` 并起来，每场只计一次。不新增 `PLAYOFF` 枚举。文档里的季后赛对应已有阶段类型 `KNOCKOUT` / `SEMI_FINAL` / `FINAL` 中实际存在的阶段。
4. 一局是 `basket_match.id`。系列赛是 `basket_match_series.id`。同一系列赛里的第几局用 `series_id + series_game_no`。轮次用 `round_no`，不建轮次表。
5. 技术统计榜和 `basket_standing` 积分榜分开。四轮都不改积分、晋级、同分规则和资格确认。
6. `basket_team_stat`、`basket_player_stat` 继续做现有 Division 累计统计，不改成规则快照。新榜写入独立快照表。公开数据中心在第 3 轮才改读快照。
7. 双败正式执行、赛中转会时间窗、跨赛事总榜、名人堂自动重发，都不在这四轮。

## 2. 现有链路，实施时必须接着用

| 环节 | 现有落点 | 四轮里怎么对待 |
| --- | --- | --- |
| 单场提交与版本 | `BasketV4PlayerMatchSubmissionServiceImpl`，唯一键 `(match_id, submit_event_team_id, version_no, is_delete)` | 不改提交模型 |
| 系列赛提交 | `BasketV4PlayerSeriesSubmissionServiceImpl`、`BasketV4SeriesSubmissionAuditServiceImpl` | 不改；重算时按局里的 `match.id` 取数 |
| 审核通过后的正式统计 | `OfficialMatchResultSettlementService.settleFromSubmission` → `basket_match_team_stat` / `basket_match_player_stat` | 第 3 轮在 `rebuildDownstream` 之后追加本 Division 的榜单重算 |
| 退回已通过提交 | `StageExecutionExceptionApplicationServiceImpl.reopenApprovedSubmission` | 同上，沿用现有回滚，再触发重算 |
| 阶段积分榜 | `TieBreakStandingService.rebuildStageStanding` | 不改 |
| Division 累计技术统计 | `BasketV4StatsSettlementServiceImpl.rebuildTeamStat` / `rebuildPlayerStat` | 第 1～2 轮不改。公开榜切走之后，这张表仍给定详情和旧接口 |
| 弃赛 | `StageExecutionExceptionApplicationServiceImpl.forfeitMatch` | 资格引擎把 `FORFEITED` 排除出技术局。现有累计表第 1～2 轮仍可能把弃赛算进场次，这是已知旧口径 |
| 轮空 | `BracketSlot`，来源类型 `BYE` | 不生成 Match，不计局、不计轮次 |
| 官网数据中心 | `basketball-web-ui/src/views/data/index.vue`，接口 `GET /basket/v4/public/stats/team-stat`、`/player-stat` | 第 3 轮才改读新接口 |
| 首页三王 | `BasketPublicHomeServiceImpl.buildDataFocus`，`GET /basket/public/home/data-focus` | 第 3 轮改读同一份已发布快照 |
| 后台积分榜页 | `basketball-admin-ui/src/views/cnpa/event-v4/stats/index.vue` | 保留积分榜页。数据排行配置单独做工作台入口，不塞进积分榜表格 |

当前公开榜的问题，作为第 3 轮之前允许存在的现状：

- 累计统计按整个 `divisionId` 加总，小组和淘汰混在一张表。
- `BasketV4MatchTeamStatMapper.selectByDivisionId` 把 `FINISHED` 和 `FORFEITED` 都算进 `match_count`。
- 数据中心把全量结果拉到前端再排序、再按 10 条切片。
- 没有上榜门槛，也没有“榜未发布”。

## 3. 四轮关系

```text
第 1 轮  规则草稿能保存          官网不变
   ↓
第 2 轮  后台试算和排除原因      官网仍读旧榜
   ↓
第 3 轮  发布快照，数据中心和首页改读快照    P0 可验收
   ↓
第 4 轮  命中率门槛、差异、归档、失败日志    P1，不挡 P0
```

每一轮结束都要能单独上线。后一轮不通过时，前一轮的草稿或旧公开榜继续可用。

建议新增表，全部放在 `docs/sql/`，按轮次加迁移，不改历史生产数据。

| 表 | 出现轮次 | 职责 |
| --- | --- | --- |
| `basket_leaderboard_policy` | 第 1 轮 | 某 Division + scope 的一份规则。草稿可改，已发布行不可原地改 |
| `basket_leaderboard_policy_audit` | 第 1 轮 | 保存、校验、发布、归档的操作日志 |
| `basket_leaderboard_run` | 第 2 轮建表，第 3 轮用于正式重算 | 一次试算或正式重算的作业、数据修订号、错误 |
| `basket_leaderboard_snapshot` | 第 3 轮 | 可原子切换的正式榜指针 |
| `basket_leaderboard_entry` | 第 2 轮可先存试算，第 3 轮只对已发布快照公开 | 球队或球员的资格、指标、排除原因 |

`scope_key` 约定：阶段用 `STAGE:{stageId}`，全赛事用 `OVERALL`。同一 `division_id + scope_key` 同时最多一行 `lifecycle = ACTIVE`。修订中的新版本是另一行 `DRAFT`，不在同一行写两个状态。

## 第 1 轮：规则能保存

### 目标

管理员可以按一个 Division 的真实阶段保存数据排行规则草稿，并按赛制填上推荐初值。保存和修改草稿不影响官网、不影响 `basket_team_stat`、不影响积分榜。

### 本轮要做

1. 迁移 `docs/sql/cnpa-leaderboard-policy-r1.sql`。
   - `basket_leaderboard_policy`：`division_id`、`scope_key`、`stage_id`（OVERALL 为空）、`version_no`、`lifecycle`（先只用 `DRAFT` / `READY`）、`template_code`、`ranking_audience`、`config_json`、`based_on_policy_id`、`expected_lock`（乐观锁）、操作人与时间。
   - `basket_leaderboard_policy_audit`：操作人、动作、旧值、新值、理由、时间。
   - 唯一约束：同一 Division + scope + version 只有一行未删除记录。DRAFT 同一 scope 同时只有一份。
2. 后台接口，挂在现有 V4 管理端，建议前缀 `/basket/v4/division/{divisionId}/leaderboard`。
   - `GET .../scopes`：只返回这个 Division 真实存在的阶段，外加一个可选的 `OVERALL`。不返回别的赛事的阶段类型。
   - `POST .../policies/drafts`：按阶段新建草稿。已有草稿则拒绝再开一份。
   - `PUT .../policies/drafts/{draftId}`：保存。请求带当前 `expected_lock`，冲突返回明确错误。
   - `POST .../policies/drafts/{draftId}/validate`：数字非负、比例在 0～1、必填项齐全、循环赛不要求淘汰轮次。通过后可标为 `READY`，仍可退回 `DRAFT`。
   - `POST .../policies/drafts/{draftId}/load-template`：只改这份草稿。
3. 模板只提供初值，按 `BasketDivisionStage.competitionFormat` 选择，不按 Series 写死。
   - `ROUND_ROBIN`：球队最低有效局、赛程履行率；球员最低局和出场比例。`minimumTeamPlayedRounds` 固定为 0，界面不展示。
   - `GROUP_STAGE`：同上，默认最低局可按需求说明书的 Cup 小组建议。
   - `SINGLE_ELIMINATION`：展示实际轮次、最低局、系列赛数。`bestOf > 1` 时系列赛数门槛可用；BO1 时系列赛数默认 0。
   - `DOUBLE_ELIMINATION`：允许把字段存进草稿，界面标明“双败未开放执行，此模板不能发布到正式榜”。第 1 轮不允许把它标成 `READY`。
4. 权限加在 `BasketEventV4Perms`：查看、编辑草稿、校验。发布权限本轮只留常量，不开放发布按钮。后端每个写接口鉴权，不靠前端藏按钮。
5. 管理端页面放在赛事工作台，不新建孤立菜单。
   - 在 `DivisionWorkspaceNav.vue` 增加「数据排行」。
   - 新页面 `basketball-admin-ui/src/views/cnpa/event-v4/leaderboard/index.vue`。
   - 复用 `DivisionContextHeader` 显示赛季、系列、平台、模式、赛制。
   - 页面分区：阶段选择、模板、球队规则、球员规则、保存草稿、校验。指标出手门槛留到第 4 轮，本轮配置区可以先不展示。
6. 赛事发布向导 `publish/index.vue` 不阻塞。排行规则未保存时，赛程和赛事发布仍按原逻辑进行。向导里只加一句说明：排行榜稍后单独配置。

### 本轮明确不做

- 不试算，不写快照，不改 `BasketV4PublicStatsController`。
- 不改 `rebuildTeamStat` / `rebuildPlayerStat` / `rebuildStageStanding`。
- 不改官网 `data/index.vue` 和首页数据焦点。
- 不把规则塞进 `FormatSnapshot`。赛制快照锁定的是比赛规则，排行门槛可以后改，两者版本独立。

### 验收

- 同一个 Division 的两个阶段各有一份草稿，改其中一份不影响另一份。
- 把 League 常规赛草稿的最低局改成 3，Arena 单败草稿仍是自己的值。
- 循环赛保存时不能要求“至少 2 个淘汰轮次”。
- 两个管理员同时保存同一草稿，后保存的一方收到版本冲突，前一份不被覆盖。
- 保存草稿前后，`GET /basket/v4/public/stats/team-stat?divisionId=` 的结果一致。
- 无编辑权限的账号调用保存接口被拒绝。
- 审计表能看到操作人、Division、scope、新旧 JSON。

### 完成边界

本轮上线后，运营可以提前把规则存好，但官网榜和现在一样。没有 `READY` 以外的发布动作。

## 第 2 轮：后台能试算

### 目标

用已审核的单场正式统计，按草稿规则算出谁能上榜、谁因为哪条规则不能上榜。试算结果只在后台可见。

### 计算口径

输入只读这些现有表，不读 `basket_team_stat` 的累计场次。累计表把弃赛算进去了，不能当资格分母。

| 量 | 算法 |
| --- | --- |
| 有效技术局 | `basket_match.publish_status = PUBLISHED` 且 `match_status = FINISHED`，并且存在未删除的 `basket_match_team_stat`。`FORFEITED`、`CANCELLED`、未审核、轮空都不算 |
| 球队有效局 | 该 `event_team_id` 参与的上述比赛的 `match.id` 去重 |
| 球员有效出场 | 同一场存在未删除的 `basket_match_player_stat`。只在大名单上、没有单场行，不算出场 |
| 实际轮次 | 上述有效局的 `round_no` 去重。只在淘汰阶段的规则里启用。循环赛和小组赛这条条件视为关闭 |
| 系列赛数 | 有效局上非空的 `series_id` 去重。同一 BO 系列的多局只算 1 个系列赛。没有 `series_id` 的 BO1 场次不记入系列赛数 |
| 赛程履行率 | 分母是截至试算时点、该队应打的已发布赛程，去掉轮空、取消、未到履行时点的场次。分子是已 `FINISHED` 或已 `FORFEITED` 的应履行场次。对手弃赛记本队履约，但不增加技术局。分母为 0 时，这条规则不判失败，也不当成 100% 凑数 |
| 球员出场比例 | `ceil(窗口内该队有效局 × minimumPlayerTeamRate)`，再和 `minimumPlayerGames` 取较大值。分母为 0 则球员不达标。本轮没有转会时间窗，分母用该 `event_player_id` 所属 `event_team_id` 在本 scope 的有效局 |
| 所属球队达标 | `requireEligibleTeam = true` 时，球员所在赛事球队必须先通过球队规则 |

排序用未四舍五入的原始值。试算可以返回前 10 和全量资格，但还不是官网分页契约。

`OVERALL` 的比赛集合是操作员在草稿里勾选的阶段。默认勾选该 Division 全部未删除阶段。同一个 `match.id` 只进入一次。

### 本轮要做

1. 迁移 `docs/sql/cnpa-leaderboard-preview-r2.sql`，增加 `basket_leaderboard_run`、`basket_leaderboard_entry`。试算 run 的 `purpose = PREVIEW`，不设置公开指针。
2. 新增资格服务，放在 `basketball-admin` 的 V4 support 下，例如 `LeaderboardEligibilityService`。它只读 Match、MatchSeries、单场统计和草稿 JSON。禁止调用 `rebuildTeamStat` 或 `rebuildStageStanding`。
3. 接口：
   - `POST .../policies/drafts/{draftId}/preview`：同步试算。16～32 队应在数秒内返回；超时就记一条失败 run，不改草稿状态。
   - `GET .../eligibility?policyId=`：全部 / 已达标 / 未达标。每行带 `validGames`、`playedRounds`、`playedSeries`、`dueFixtureRate`、`eligibilityStatus`、`failedConditions`。
4. 排除原因使用稳定编码，后台显示中文：
   - `TEAM_GAMES_TOO_FEW`
   - `TEAM_ROUNDS_TOO_FEW`
   - `TEAM_SERIES_TOO_FEW`
   - `TEAM_DUE_FIXTURE_RATE_LOW`
   - `TEAM_NOT_ELIGIBLE`
   - `PLAYER_GAMES_TOO_FEW`
   - `PLAYER_ROUNDS_TOO_FEW`
   - `PLAYER_SERIES_TOO_FEW`
   - `NO_VALID_TEAM_GAMES`
5. 管理端在第 1 轮页面下半部加预览：达标人数、未达标人数、前 10、排除原因。提供“只看未达标”。
6. 统计榜单页 `stats/index.vue` 保持积分榜。可以加一个独立入口跳到数据排行预览，不把资格行混进积分榜列。
7. Arena S1 只读核对脚本放在 `scripts/`，只 `SELECT`。用真实 `round_no` 和审核局数重算，不按队名写死名单。生产库禁止 `INSERT` / `UPDATE` / `DELETE`。

### 本轮明确不做

- 不发布，不切换官网。
- 不因为试算去改 `selectByDivisionId` 的弃赛口径。旧累计表的场次问题留到公开榜切走之后再决定要不要另开清理，不塞进本轮。
- 不做命中率出手门槛。预览里的命中率列可以沿用现有“累计命中 / 累计出手”，但低出手不删行。
- 不实现转会窗口。`BasketEventPlayer` 没有生效起止时间。

### 验收

对照需求说明书里现在就能构造的用例：

| 编号 | 期望 |
| --- | --- |
| T01 | 只打完 2 局且未满 2 个不同淘汰轮次的队，预览为未达标，单场详情仍在 |
| T02 | 两个不同 `round_no`、共 4 个有效局，其他条件满足则达标 |
| T03 | 8 个有效局都在同一个 `round_no`，轮次门槛为 2 时未达标 |
| T04 | 球队局数够、球员只有 3 局，球员未达标 |
| T05 | 球员 4 局但只有 1 个淘汰轮次，个人轮次门槛为 2 时未达标 |
| T06 | 球员 4 局、球队 10 局、比例低于 50%，球员未达标 |
| T07 | 积分榜最后一名，有效局够，技术榜预览仍达标 |
| T09 | 同一球员两个 Division，预览互不影响 |
| T14 | 同一场重复提交、退回后重传，有效局仍是 1 |
| T15 | 轮空和弃赛可以出现在赛程或积分结果里，技术局数不增加 |
| T19 | 本轮尚未做出手门槛，预览不得因为三分出手少把球员从得分榜删掉 |

另外：

- 预览失败时草稿还在，官网 `/team-stat` 不变。
- 小组阶段有变动时，只重算该阶段和同一 Division 的 `OVERALL` 预览，不读其他 Division。
- 试算 run 记录 `division_id`、`scope_key`、规则版本、开始结束时间和错误信息。

### 完成边界

运营可以在发布前看名单和原因。官网仍然是旧榜。第 2 轮的预览结果和第 3 轮第一次正式发布必须用同一套资格函数，避免两套算法。

## 第 3 轮：排行榜独立发布

### 目标

规则可以发布成不可变版本。官网数据中心和首页得分王、助攻王、篮板王只读最近一次成功快照。赛事公开不再依赖排行榜已发布。

这是 P0 上线轮，也是唯一改公开读路径的一轮。

### 发布规则

1. 只有 `READY` 草稿可以发布。发布人要有本赛事的发布权限。
2. 发布在一个事务里完成：按草稿再算一遍，写入新的 `snapshot` 和 `entry`，成功后再把该 scope 的公开指针切到新快照，并把该行标成 `ACTIVE`。旧 `ACTIVE` 改为被替代，行本身不改 `config_json`。
3. 计算失败则回滚这次发布。若已有旧 `ACTIVE`，公开端继续读旧快照。
4. 发布请求带 `expectedActiveVersion`。两个管理员同时发布不同草稿时，只有一个成功。
5. 已发布规则不能原地编辑。修订是基于 `ACTIVE` 再插入一行 `DRAFT`。草稿变化期间官网仍读旧版本。
6. 同一 Division 的不同阶段可以分开发布。`OVERALL` 单独发布。
7. 无人达标是合法发布结果，空态编码 `NO_ELIGIBLE_SUBJECTS`，不自动改成展示全部球队。
8. 审核通过、撤回、纠错、判负、撤销判负之后，只给受影响的 `divisionId` 入队重算。一场比赛只属于一个 `stageId`；若该 Division 的 `OVERALL` 已发布，连同 `OVERALL` 一起重算。其他 Division 不重算。
9. 重算幂等键：`divisionId + scopeKey + policyVersion + sourceRevision`。同一键重复触发不累加。同一 scope 排队，旧修订号的结果不能覆盖较新的快照。
10. 重算失败时公开指针不动，run 记录错误。后台能看到“当前快照时间”和失败原因。

`sourceRevision` 用该 scope 内正式单场统计的最大 `update_time` 加匹配场次数量组成，能区分“又审核了一场”和“重复点击”。不要求全局事务序号。

### 本轮要做

1. 迁移 `docs/sql/cnpa-leaderboard-publish-r3.sql`。
   - `basket_leaderboard_snapshot`：`run_id`、`division_id`、`scope_key`、`policy_id`、`source_revision`、`published_at`、`is_public`。
   - 同一 scope 同时只有一个 `is_public = 1`。
   - `lifecycle` 补上 `ACTIVE`。`ARCHIVED` 留到第 4 轮再用。
2. 公开接口新增，不改旧接口的路径和返回，避免详情页和未升级客户端突然空榜。
   - `GET /basket/v4/public/leaderboard`
   - 参数：`divisionId`、`scope`（`stageId` 或 `OVERALL`）、`tab=team|player`、`mode=average|total`、`sortBy`、`page`、`pageSize`（上限 10，本轮固定按 10 使用）。
   - 返回：`status`、`policyVersion`、`snapshotId`、`lastCalculatedAt`、`totalEligible`、`rows`、`emptyReason`。
   - `status` 没有 `ACTIVE` 快照时为未发布，`rows` 为空，`emptyReason = NOT_PUBLISHED`。
   - 有快照但合格数为 0 时，`emptyReason = NO_ELIGIBLE_SUBJECTS`。
   - 最新 run 失败且仍有旧快照时，`emptyReason` 为空，另给 `stale = true` 和 `lastCalculatedAt`。
3. 排序在服务端完成：先资格，再当前指标，再按 10 条分页。`totalEligible` 是过滤后的人数，不是原始参赛队数。名次按全量合格名单连续计算，第二页接着第一页，不把原始前 10 滤完再留空。
4. 场均和总计使用同一批合格对象。场均分母是该 scope 的有效出场局，不是系列赛数。命中率是累计命中除以累计出手；出手为 0 时该列为空，不显示 0%。
5. 官网 `data/index.vue`：
   - 选择器继续用赛季 → Division（平台、模式、状态）。选中值写入地址栏 `divisionId`。
   - 增加该 Division 已存在阶段的 scope 选择。没有的阶段不显示。
   - 地址栏保留 `divisionId`、`scope`、`tab`、`mode`、`sortBy`、`page`。
   - 去掉“先拉全表再前端排序分页”。搜索若本轮仍要保留，改为服务端关键字，或明确只过滤当前已返回页并在计划里不做全表搜索。本轮建议搜索交给服务端，避免又把未达标队伍滤进内存。
   - 空态文案按未开赛、未发布、无人达标、更新延迟分开。视觉结构、统计列、球队/个人、场均/总计、每页 10 条保持现状。
6. 首页 `BasketPublicHomeServiceImpl.buildDataFocus` 改为读取该默认 Division 已发布快照的得分、助攻、篮板第一名。没有已发布快照时，三王为空，不回退到无门槛的 `listPlayerStat`。焦点战队逻辑本轮不动。
7. 重算挂接点只加在 `OfficialMatchResultSettlementService.rebuildDownstream` 成功之后，以及判负、撤销判负、退回提交已经会调用的同一条下游。不在结算事务里做全量跨赛重算。结算事务提交后触发本 Division 的异步或同步重算；若同步，失败不能把已经审核通过的比赛事务回滚掉，只记失败 run 并保留旧快照。
8. 管理端发布按钮放在第 1 轮页面的操作区：校验通过 → 试算 → 确认发布。确认框写明版本号和 scope。已发布版本只显示“创建修订”。
9. 权限：发布、重算与编辑草稿分开。`BasketEventV4Perms` 增加发布和重算权限码，并在菜单或按钮上使用。

### 本轮明确不做

- 不删除旧的 `/basket/v4/public/stats/team-stat` 和 `/player-stat`。比赛详情、球队详情若仍读累计表，保持原样。
- 不改积分榜页面的数据和算法。
- 不做归档、纠错审批和命中率出手删除。
- 不把 `isDataCenterFeatured` 做成新的全站配置中心。第 3 轮默认 Division 仍沿用首页现有的当前赛季选择；全站唯一推荐赛事若要运营手选，放到第 4 轮，避免和第 3 轮的读路径绑死。

## 第 4 轮：运营收口

### 目标

补上运营解释和历史收口：命中率出手门槛、修订差异、归档、纠错和失败日志。不做跨赛事榜，不自动重算名人堂。

### 本轮要做

1. 命中率门槛写进已有 `config_json.metricGates`，指标为 `FG_PCT`、`THREE_PCT`、`FT_PCT`，球队和个人分开配置累计最低出手。
   - 只有 `sortBy` 是该命中率时才应用门槛。
   - 按得分、篮板等排序时，低出手的行保留，命中率列仍显示“—”。
   - 对应验收 T19：三分 1 投 1 中、出场已够、门槛为每局至少 2 次出手时，不进入三分命中率榜，仍可进入得分榜。
2. 创建修订时，预览区比较新草稿和当前 `ACTIVE`：门槛差异、达标人数增减、新进榜和掉榜的 `eventTeamId` / `eventPlayerId`。比较结果不写公开指针。
3. 归档。
   - 接口 `POST .../archive`，权限与发布分开。
   - 记录归档时的 `policy_id`、`snapshot_id`、统计时点。
   - 归档后的公开读仍是这份快照，状态显示为最终榜。
   - 新建下一季、下一个 Division 不得更新已归档行。对应 T18。
4. 纠错。
   - 归档后不允许直接改规则或改历史提交来“修榜”。
   - 纠错走现有退回重传或比赛结果修正。完成后由授权管理员对这个已归档 scope 重新发布一版快照，旧快照保留。
   - 审计记旧快照、新快照、理由、操作人。不提供“强制上榜”按钮。
5. 运行日志页用 `basket_leaderboard_run`：成功、失败、`sourceRevision`、耗时、错误摘要。放在数据排行页面的二级区域，不新建系统。
6. 全站默认推荐赛事：若产品仍要“导航进入数据中心时打开指定 Division”，本轮在 Division 上增加一个互斥标记，同一时刻只有一个 `is_data_center_featured = 1`。从赛事页进入仍优先用该页带入的 `divisionId`。这一项可以单独开关；不做也不影响已发布榜。
7. 名人堂生成服务不订阅榜单重算事件。荣誉仍只走现有 `BasketHonorGenerationServiceImpl` 的人工或原有生成入口。

### 本轮明确不做

- 跨赛事年度榜、冠军加权、AI 评分。
- 双败正式赛程。配置里若出现双败模板，发布校验继续拒绝。
- 赛中转会。出现转会需求时另开模型，给 `EventPlayer` 或参赛关系加生效区间后再改资格分母。
- 不清理历史 `basket_team_stat` 里已经计入的弃赛场次，除非另外得到一次明确的数据修复批准。

### 验收

- T19 按上一节的出手规则通过。
- 修订预览能指出“最低局从 4 改成 2”以及因此新增的球队，官网在发布前不变。
- 归档后的 Arena S1 快照不因新建 Arena S2 改变。
- 纠错后同时能查到前后两个 `snapshotId`。
- 重算失败在日志里可见，公开榜仍是上一份成功快照。
- 发布或重算一次后，名人堂记录条数不自动增加。

### 完成边界

需求说明书的 P0 和 P1 在 BO1、以及已经实现的单败/循环 BO3/BO5/BO7 上可交付。双败和转会仍是比赛执行层的后续工作。

## 4. 测试与上线顺序

每轮合并前至少跑：

1. 该轮新接口的服务测试：草稿冲突、资格样例、发布回滚。
2. 一条现有结算回归：审核通过一场后，系列赛比分和阶段积分榜与改动前一致。
3. 第 3 轮增加数据中心页面走查：切换 Division、scope、场均/总计、分页，并看未发布和无人达标。
4. 第 2 轮的 Arena S1 脚本只读。需要对照生产时单独申请只读查询，不写线上库。

上线顺序就是第 1 → 2 → 3 → 4。第 3 轮上线前确认旧 `/team-stat` 仍可用，以便公开新接口出问题时页面可以切回旧接口。这个回切只作为发布手段，不在正常界面保留两套榜。
